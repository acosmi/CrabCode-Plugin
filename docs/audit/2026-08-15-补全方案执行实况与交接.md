## 2. ⚠ 已实证的方案偏差（三处，以代码为准）

方案原文写于审计轮，执行中实跑发现三处需要修正的判断。**接手会话请以本节为准。**

### 2.1 P1 的工作量被低估：`bash -n` 只是第一层

方案只做到语法检查。实跑后另有**四个同级缺陷**，方案完全没抓到（已全部修完，记此为教训）：

1. `validate-agent.sh` 的 `description: |` 是 YAML **块标量**，原提取器只读到标题行 `|`
   ⇒ 恒报「1 characters / 太短」。修了语法它照样不可用
2. `((n++))` 在 `n=0` 时返回退出码 1，`set -euo pipefail` 当场杀进程
   ⇒ 脚本在**第一条 warning** 处静默中止。`hook-linter.sh` 同款（它因被 `if !` 包住而
   侥幸幸存，但 `((total_errors++))` 不在被测上下文里，有错时不打印总结且多脚本只跑第一个）
3. **Windows 版 jq 输出 CRLF**，未剥离的 `\r` 让每次字符串比较与 `.hooks[$event]`
   取值静默落空 ⇒ 合法配置被判 4 处错。已统一经 `jqr()` 剥离
4. 示例 hook 把路径直接内插进 JSON 字面量，含引号的路径会产出非法 JSON（已改 `jq --arg`）

**教训**：`bash -n` 通过 ≠ 能用。改完脚本必须拿真实输入跑一遍。

### 2.2 P1.3 的**理由**对但需补一条：三个 agent 自己违反自家教义

方案说「`<example>` 检查与本插件 flat prose 规范相反」——**结论正确**
（`agent-development/SKILL.md` 的 `:28/:94/:340/:348` 明确教 prose 触发场景），
但方案没提：**plugin-dev 自己的三个 agent 描述全用 `<example>` transcript 形**，
与自家 SKILL.md 教义相反。

**本轮处置**：只删了校验器里那条与教义相反的检查（改为检查 prose 触发描述），
**没有改三个 agent 的 description 形态** —— 那会改变 agent 触发行为，属行为变更而非
「修真话」，超出方案 §5「只修真不加新」。**留给用户裁决**，不要自行改。

### 2.3 P3 的虚构格式**已渗入本仓校验器**（方案未预见）

`src/policy/referenceValidator.ts` 原本显式豁免 `plugin_` 开头的 server，注释写着
「`mcp__plugin_...` 是插件工具命名空间」——**那正是虚构格式**，它以「豁免规则」的形式
被写进了闸门。于是把文档改成真格式 `mcp__p_<24 hex>__` 反而被判 4 处 ERROR。

已按真事实纠偏（豁免改为 `/^p_[0-9a-f]{24}$/`），并补 `tests/validators/reference-mcp-namespace.test.ts`
四条用例（一条正向 + **三条反向对照**：假 server 名 / `p_` 非十六进制 / 摘要长度不对，
三者都必须仍然 ERROR，防豁免悄悄放宽）。

> 这是本轮最值得记的一条：**同一个虚构在文档、示例、校验器三层复现**，
> 而校验器那层把虚构固化成了「规则」。改文档前先查闸门里有没有同款假设。

确认变更集**恰好等于你本轮改过的技能**（数量与身份集合哈希应保持不变），再改

### 行尾

`.gitattributes` 强制 `* text=auto eol=lf` 且 `*.sh text eol=lf`（注释里写明理由：
CRLF 会让 `#!/usr/bin/env bash` 变成 `bash\r`，Linux 上 exec 失败）。
Windows 编辑器会引入 CRLF，**提交前检查**：


```bash
# frontmatter：sed 区间会贪婪配对全文 ---，正文分隔线后的内容被当成配置读进来
# 实测：正文含 --- 与 enabled: false 时提取出两行 enabled ⇒ 下游 =="true" 失败 ⇒ 插件静默自禁用
awk 'NR==1 && /^---$/ {c=1; next} c==1 && /^---$/ {exit} c==1'   # 正确

awk 'c==2{print; next} /^---$/{c++}'                              # 正确（print 规则带 next 是承重的）
```
