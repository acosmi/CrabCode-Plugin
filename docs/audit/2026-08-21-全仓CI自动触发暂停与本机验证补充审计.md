# 全仓 CI 自动触发暂停与本机验证补充审计

> 日期：2026-08-21
> 适用仓库：`acosmi/CrabCode-Plugin`
> 决策：暂停 CI 的自动触发，改为全局 GitHub Actions API 人工调度；开发验收全部在本机执行

## 1. 前置审计结论

结论为“有条件通过”。最小且可验证的实现不是删除 CI，而是：

1. 从 `.github/workflows/ci.yml` 移除 `pull_request` 和 `push`；
2. 只保留 `workflow_dispatch`，由有权限的维护者通过全局 Actions API 显式触发；
3. 本地先执行完整测试矩阵中可由当前主机复现的所有测试套件；
4. 保留远端工作流作为按需、提交绑定的跨平台证据，不再自动消耗 Actions 额度；
5. 同步修订镜像审计对 CI 运行记录的查询，避免它只识别已经停用的 `push` 事件。

`publish-to-cn-mirror.yml` 的 `push main` 是发布动作，`notify-mirror.yml` 的
`schedule` 是只读镜像健康审计，二者不是 CI 测试触发器，本次不暂停。若要连发布和
镜像监控也改成人工触发，应另行审计发布时效、镜像 SLO 和部署密钥责任，不在本补充
授权范围内。

## 2. 人工 API 入口

GitHub 标准入口：

`POST /repos/acosmi/CrabCode-Plugin/actions/workflows/ci.yml/dispatches`

请求体：

```json
{"ref":"需要验证的分支或标签"}
```

使用 GitHub CLI 的等价命令：

```bash
gh api --method POST repos/acosmi/CrabCode-Plugin/actions/workflows/ci.yml/dispatches -f ref='需要验证的分支或标签'
```

调用者需要仓库 Actions 写权限。令牌只能由 GitHub 或组织级凭据系统保存，不得写入
仓库、日志、Matter Store 或测试夹具。`workflow_dispatch` 也会在 GitHub Actions
页面提供人工按钮；API 与页面按钮进入同一工作流，不存在两套测试定义。

## 3. 本机验证基线

开发者应在待提交 SHA 对应的干净隔离树中记录 `git rev-parse HEAD`、主机系统、
Bun/Python/Java 版本及以下命令的退出码。

### 根仓库

```bash
bun install --frozen-lockfile
bun run typecheck
bun test ./tests/
bun run build
bun run lint:brand
bun run scripts/lint-brand.ts dist
bun run validate
```

### CrabCode Security

使用 `SOURCE-LOCK.json` 指定的只读上游提交，在本机临时目录检出后执行：

```bash
bun run scripts/verify-crabcode-security-port.ts "$UPSTREAM_CHECKOUT"
bun run scripts/build-crabcode-security-port-patch.ts --check "$UPSTREAM_CHECKOUT"
CRABCODE_SECURITY_UPSTREAM_CHECKOUT="$UPSTREAM_CHECKOUT" bun test ./tests/crabcode-security/
sh -n plugins/crabcode-security/hooks/banner_hook.sh
```

### 独立插件

在各自目录先执行 `bun install --frozen-lockfile`，再运行：

```text
crabcode-html-video:
  bun run typecheck
  bun run build:mcp
  bun test ./tests ./packages
  bun run check:distribution

crabcode-media-ops:
  bun run typecheck
  bun run check:distribution
  bun run test
  bun run test:qa
  bun run qa:release
  bun run validate

crabcode-media-publisher:
  bun run lint
  bun run test
  bun run qa:nu
  CRABPUBLISH_SKIP_VISUAL=1 bun run test:browser
```

浏览器、Java、系统字体、ffmpeg 和操作系统差异可能造成主机特有结果。一次本机运行不能
替代 Linux/macOS 与 Python 3.9/3.13 的真正矩阵；需要跨平台证据时，应在本机通过后
再人工调用上面的全局 API。

## 4. 关联方影响

| 关联方 | 影响 | 控制措施 |
|---|---|---|
| 贡献者 | PR 与 push 不再自动出现 CI 结果 | 提交本机验证命令、SHA、环境和退出码 |
| 管理员 | 需要决定何时人工调度远端矩阵 | 使用统一 API；不得启用自动合并 |
| 分支保护 | `workflow_dispatch` 的成功 suite 不被 PR 合并引用 required checks 接受 | 移除 required-status-check 合并门，保留管理员、会话解决、禁止强推和禁止删除保护 |
| 镜像审计 | 原实现只查询 `event=push` | 改为读取 main 上全部成功 CI 记录，兼容人工与历史运行 |
| 镜像发布 | 仍在 main push 后发布 | 由管理员确保合并前已有本机证据；发布触发策略未变 |
| 安全与法律复核 | 不因 CI 关闭而降级 | 仍保留人工安全、许可证和法律专业复核门 |

## 5. 风险与非目标

- 本机验证的最大风险是环境漂移和结果无法天然绑定远端提交；必须保留 SHA、干净度和
  命令记录。
- API 人工调度减少无效 Actions 消耗，但增加遗漏触发的风险；分支保护和交付清单应
  明确责任人。
- 本次不修改 GitHub ruleset、组织令牌、Secrets、Runner、镜像部署密钥或自动合并。
- 本次不把 CI 拆成新的服务，也不建设自托管全局调度平台；仓库现有标准 Actions API
  已满足一个入口人工触发全部远端检查的要求。

## 6. 验收条件

- `ci.yml` 的顶层触发器只有 `workflow_dispatch`；
- 不再存在 CI 的 `push`、`pull_request` 或 `schedule` 自动触发；
- 镜像审计不再把 CI 事件限定为 `push`；
- 自动触发策略有确定性测试防回归；
- 本机根仓库及各独立插件测试完成并记录实际限制；
- PR 保持人工评审、不得自动合并。

## 7. 2026-08-21 本机实测记录

实测环境：macOS 26.5.2 arm64、Bun 1.3.11、Python 3.14.5、Java 21.0.10。所有仓库改动均在
`/tmp` 隔离克隆中执行；未从共享工作区纳入其他任务文件。

|---|---|

| CI 策略测试 | 2 pass，确认 CI 仅有 `workflow_dispatch`，镜像审计不再限定 `event=push` |

Security 的 1 项 skip 专门验证“缺失的 partial checkout 应被拒绝”；当前上游目录是完整
浅检出，因测试前提不成立而按设计跳过。它不是功能失败。

为补齐本机浏览器和音视频覆盖，执行了两项本机环境修复：

- 下载 Playwright 1.61.1 对应的 Chromium/Headless Shell v1228 与其精简 ffmpeg 到
  `~/Library/Caches/ms-playwright`；
- 将原本因 x265 ABI 失配而无法启动的 Homebrew ffmpeg 重装为 9.0.1，并更新其直接
  运行依赖。Homebrew 随后计划连带升级 Whisper/LLVM/PyTorch 依赖，该阶段已被中止；
  `openai-whisper` 保持 20250625_3，未被升级。

Media Publisher 的非 CI 默认模式固定要求 Chrome 150，而本机系统 Chrome 为 151。
首次运行的 39 项均在浏览器版本前置断言处停止；按仓库现有 CI 等价参数
`CRABPUBLISH_SKIP_VISUAL=1` 重跑后，39/39 页面、可访问性、响应式与浏览器用例通过。
没有修改或放宽仓库的版本断言和截图基线。

分支推送后，新 HEAD 没有自动生成 `push` 或 `pull_request` CI。合并前因经典分支
保护仍要求旧的 8 个 check context，使用全局 API 对最终工程 HEAD 人工调度了一次：
run `32579055627`，8/8 success。GitHub 仍把这些人工 suite 显示为 PR 合并引用上的
`expected`；把 `strict` 改为 `false` 也没有解决事件来源不兼容。为避免所有未来 PR
永久不可合并，最终移除了 main 的 `required_status_checks` 子规则；管理员更新限制、
会话解决、禁止强推和禁止删除等其余保护保持不变。
