## 1. 结论先行

微博官方 CLI 确实存在,且它的能力**恰好沿着本插件已有的那条断层线一分为二**——这不是巧合,而是整个方案的设计支点。

- **读侧能力**(热搜 / 趋势 / 搜索 / 用户画像)= 天然的*情报输入*,可无缝接进现有 research/trends 管线,风险低、价值高。
- **写侧能力**(发博 / 评论 / 点赞 / 关注 / 营销)= 实名身份下对真实平台的*不可逆动作*,这正是插件**刻意不做**的 "Gate B"(`publish-runbook.md:13`、`PRACTICE.md` 规则 9、`README.md:143-144`:"不提供真实平台 API 发布…不得伪造发布成功")。

**核心命题**不是"要不要接",而是:**如何让微博 CLI 成为现有门禁的真实末端,而绝不成为绕过门禁的第二条弱发布路径。** 用户已决定三层全接(Tier 0+1+2),因此本方案的重点从"要不要跨 Gate B"转为"跨过去之后如何让每一层都自洽于插件的不变量"。

**跨 Gate B 有三个机器级落点(rev.2 补)**:插件今天用三处**机器可读**的方式对外承诺"我不发布"——`capabilities.dangerousCapabilities:{publish:false, autoComment:false}`、每个平台的 `apiPublishGate:'gate-b'`、`doctor` 的 `credentialReadiness:'not-configured'`。**逐一翻转这三处,才是"真的开始发布"的诚实时刻**;每一处都是一个"不能再宣称已失去的安全属性"的点。详见 §6.9。

## 2. 第一性原理拆解

把两边都还原到不可再分的内核:

**插件的存在理由(不可动摇的不变量)**:可审计 · 逐级门禁 · 真人审批 · 身份绑定 · 职责隔离 · **绝不伪造成功** · **绝不自动发布**。

**微博 CLI 的本质**:它是一个**外部能力/凭证载体**,把微博开放平台 70+ API 封装成子进程可调、可 `--output json` 的命令行。它带来两类本质不同的东西:

| 维度 | 读/分析类 | 写/动作类 |
| --- | --- | --- |
| 本质 | 把外部世界的信号*拉进来* | 以你的实名身份对世界*推出去* |
| 可逆性 | 完全可逆(只是数据) | 公开、准不可逆 |
| 对不变量 | 相容(当作**不可信外部数据**即可) | 直接触碰 Gate B |
| 花费 | credits/配额(**非零**,见 §4 Tier 0 修订) | credits/配额 + 声誉 + 合规 |

**两条地基级结论**:

1. 微博 CLI 的**输出**必须被当作**不可信数据**(`PRACTICE.md` 规则 1)——热搜标题、搜索结果、他人评论本身可含提示注入,须走服务端快照 + 哈希 + 不可信标记,绝不直接当事实或指令。
2. 微博 CLI 的**登录态**必须被当作**一个密钥,而不是一个治理主体**——它绝不能被误认为插件的审批身份(MCP OAuth subject / host_principal)。这两个是**两个独立信任域**。`identity.ts` 已把这条钉死:写工具只认 MCP subject 或显式受信宿主 principal,调用参数里的姓名一律被 `issuer:principalId` 覆盖。

## 3. 官方 CLI 全量能力盘点(看官方文档的结果)

### 3.1 权威事实(npm registry 元数据 + 四源交叉印证)

- 包名 **`@weibo-ai/weibo-cli`**,当前 **v0.8.3**,MIT,**Node ≥18**,二进制名 **`weibo`**
- 安装:`npm i -g @weibo-ai/weibo-cli` 或 `curl -fsSL https://open.weibo.com/cli/install.sh | bash`
- 鉴权:**OAuth,且需先过微博实名认证**;内置 token 自动刷新、分页处理、错误重试
- 命令范式:**`weibo <group> <action> [flags]`**
- 全局标志:`--output json|table|yaml|raw`(部分文档含 `csv`)、`--token <token>`、`-h/--help`
- 计费:free **5 次/小时**;付费四档 credits——**¥29(3,000)/¥69(7,500)/¥299(32,000)/¥899(100,000)**
- 官方将 70+ API 归为 **6 模块**:内容发布 / 互动管理 / 内容检索 / 趋势分析 / 受众画像 / 营销自动化(抽奖·批量分发)

## 4. 定性方案:三层分级接入

### Tier 0 —— 读侧情报(先落地,价值/风险比最高)

把 `search / wbindex / statuses(timeline) / users / me / tags(读) / comments(读)` 封装成**能力受限的证据适配器**,喂给现有 `trends.ts` + `media-topic-research` + intake/research 管线。

- **落点(rev.2 订正)**:读侧情报是**数据源**,**不是发布平台**——应注册进**源注册表** `src/sources/`(`capabilities.ts` 的 `buildSources()` / `availableSources` 路径),**不碰** `platforms/registry.ts`。`PlatformDescriptor` 通篇是发布语义(limits/requiredCredentials/apiPublishGate/rules/渲染),读侧不需要它。原稿把"新增 weibo 平台"记在 Tier 0 名下是分层错位:那坨改动只在 **Tier 1** 才需要(见 §4 Tier 1 与 §12-A4)。
- **机制**:`shell weibo … --output json`,像 `research.capture` 那样**对结果做服务端快照 + 字节/文本哈希**,整体标记**不可信外部数据**。**注意区分两条既有子系统**:热搜/指数这类*话题信号*进 trends/research;而**引用他人某条微博作为素材/来源**时,必须走**引用防火墙** `mediaops.reference.register`(`PRACTICE.md` 规则 4:分类角色/权利/允许用途,原文只存受保护集合,写作者只拿 referenceId),不能绕过它另开捕获路径。
- **治理(rev.2 订正)**:**低风险,但非"零"**。认证读同样**计费**(free 仅 5 次/小时)、**按实名留痕**、`/other` 后缀是**查他人数据**(触第三方隐私/ToS)。且 free 的 5/hr 是**读写共用池**,读侧情报会与计划中的发布**抢配额**——配额治理器须**跨 Tier 预算**。约束:配额 + 注入防护 + 引用防火墙。

### Tier 1 —— 发博(微博长文)作为 Gate B 的真实末端

让微博发文成为**已完整过完 Media Gate + 审批链之后**的真实投递器。

- **内容形态已定(rev.3 决断):Tier 1 只发「微博长文」,短状态移出 Tier 1。** 第一性依据是插件唯一不可破的不变量——**发布口只能是"已过完整人审门禁链的忠实末端",不得存在第二条更弱的发布路径**(§2、Gate B)。用它筛两个原生形态:
  - **微博长文** ✅:发出去的就是那份**已 approved 的 ArticleDoc**,发布口仍落在门禁链末端、`approval.decide` 下游,不变量成立;代价只是"给 `weibo` 加一个渲染档",是**沿现有机器纹理的加法**(wechat/xhs/toutiao 本就这么挂),不破坏任何对称性。**这是唯一保住不变量的形态。**
  - **短状态** ❌:`statuses update` 发的是一条**没有 ArticleDoc、没走过门禁链的裸写**;要"正经发"就得另造一套轻量门禁——**恰是不变量禁止的那条第二弱路径**(何况 2000 字短博≈文章长度,门槛画哪儿都是洞)。故移出 Tier 1;其真实用途("发条短博给长文引流")本性是**分发/营销**,归 **Tier 2 分发轨**(§4 Tier 2 / §5),不做 Tier 1 捷径。(即便"写极短 ArticleDoc 过完整门禁再当短博发"技术上保住不变量,对 140 字跑多视口 QA + 全套编辑评审也荒谬到没人用,只会逼出绕行——short-form 不是 Tier 1 的职责。)
- **命名澄清(rev.3,消除撞名)**:微博长文 = **新浪微博站内的原生长文功能**(历史品牌名"头条文章",编辑器约在 card.weibo.com/article),**与字节跳动「今日头条」——即插件已有的 `toutiao` 平台——毫无关系,仅"头条"二字撞名**。全文一律用"微博长文",防止实施者把它错接到 `toutiao`。最终命令名以前置① `weibo commands list` 为准(微博或已改名)。
- **上游代价(A1,非纯末端追加)**:当前交付层渠道产物**硬编码成微信富文本**(`delivery.ts:253` 固定 `wechat-richtext.html`/`wechat-richtext@1`),渲染器只产 `web@1 / wechat-richtext@1 / markdown-backup@1` 三档(`renderer.ts:325`),**没有微博产物**;审批把渠道产物**哈希绑定**进批准(`capabilities.ts:74` `approvalHashBinding` 含 `channelArtifacts`)。故忠实投微博长文,**必须先在上游** `delivery.render` 造**微博渲染档** → `delivery.verify` 做 QA → 被 approval 哈希绑定,会动到原稿声称"不碰"的上游几环——这是 Tier 1 的**必做项**,不是纯末端追加。
- **落点**:新增 `mediaops.publish.dispatch.weibo`(须进 `identity.ts` `POLICIES`,复用 `publisher` 角色),只消费**已 approved、已打包、哈希绑定**的候选;要求 `publisher` 角色 + **逐条真人显式确认**;调用后把 CLI 返回的**真实 mid/永久链接**作为 Gate B 权威证据回绑 packageId/contentHash;两阶段可恢复、幂等、失败 fail-closed。
- **红线**:无 CLI 真实成功载荷,**绝不**报"已发布"(呼应 `不得伪造发布成功`)。微博官方自身亦建议"对发文等写操作保留人工确认",与插件哲学同向。

### Tier 2 —— 互动/营销自动化 + 短状态分发(用户已选纳入;详见第 5 章平行治理轨)

`comments(发) / attitudes / friendships / 抽奖 / 批量分发`——与插件"不虚构读者反馈"、反操纵价值观**冲突最强**的一层,须建独立治理轨,不能复用文章门禁。**rev.3 追加**:从 Tier 1 下放的**短状态**(`statuses update`,如给长文引流的导流短博)也归此轨——它虽是**自有广播、不涉操纵**,但同样**缺 ArticleDoc 门禁血统**,作为**轻量文本分发子流程**治理(真人确认 + AI 标识 + 配额 + 引用/statement 台账),不吃完整文章门禁。

## 5. Tier 2 专章:它打破了前两层保住的两个对称性

- Tier 0 是**读**,安全。
- Tier 1 发的是**你自己那篇已过完 originality/editorial/legal/审批的文章**(rev.3 已锁定为微博长文)——被推出去的东西*本身已被治理*,且走在 `approval.decide` 下游。
- Tier 2 的动作(评论 / 点赞 / 关注 / 抽奖 / 批量分发)打破**两个**对称性:
  1. **内容对称性**:它的"内容"不是那篇被门禁过的 ArticleDoc——点赞没有文章;评论往往短而即时;批量分发把触达*乘以*;关注/取关是*关系*动作。
  2. **保护对称性(rev.2 新增)**:它既不在 ArticleDoc 门禁内,**也不在任何"第二真人门禁"下游**。`identity.ts` 的 `SECOND_HUMAN_GATES = {originality.review, editorial.review, approval.decide, profile.confirm}`(`identity.ts:219-224`)在单人 `local-editorial` 模式下保持 pending、挡住不可逆提交;Tier 1 天然继承这层,**Tier 2 掉在它之外**。而 `POLICIES`(`identity.ts:56-76`)里**没有任何 engagement 角色**。

**结论**:现有 Media Gate 围绕 ArticleDoc 建,**天然覆盖不了 Tier 2**。Tier 2 需要一条**平行的、专为互动而建的治理轨**——否则退化成"刷量脚本",与插件全部价值观对撞。这是接入 Tier 2 后最关键、也最不显然的一条。

### 5.1 Tier 2 净新增的治理原语(缺一不可)

1. **互动策略对象(engagement policy)**:按 brand 配置——允许哪些动作、时/日配额上限、目标 allowlist/denylist、冷却时间、禁止关注 churn。部署者设定、版本化、像 `platform.rules` 一样查时效。
2. **专属角色 + 第二真人门禁(rev.2 新增,直击保护对称性)**:`engagement.dispatch.weibo` 必须在 `identity.ts` **显式声明新角色**(如 `engagement_operator` 发起 / `engagement_approver` 批准),并**显式挂进 `SECOND_HUMAN_GATES`**——否则单人即可自我确认地刷赞,正是它想防的。凡上规模(批量分发/抽奖)守 `requester≠approver`。
3. **配额/额度治理器(quota governor)**:同时建模 credits(¥ 真金)+ 微博自身限流 + 策略上限;超限即拒、**绝不重试风暴**(CLI 内置 retry 必须封顶)、显式暴露花费。**权威源:微博才是限流/credits 权威,本地不记账镜像**(必漂移)——治理器做*本地硬上限 + 计划期向微博查实时余额*。Tier 1 亦复用,但 Tier 2 是压力源。
4. **反操纵硬护栏(不可覆盖)**:不伪造 / 不把 AI 代写的互动冒充自然人;不做协同性虚假行为(coordinated inauthentic behavior);不批量关注陌生人;评论若含事实主张,仍走 reference 防火墙 + statement 台账;负面/商业/敏感回复仍路由 `crablaw-cn`(见 §12-C3:属既有 advisory 先例,**不得**升级成机器强制阻断门禁)。
5. **写动作的独立确认模式**:逐条或逐批真人确认 + 真实预览;成功只认 CLI 返回的真实 ID/permalink(同 Tier 1,不伪造成功)。
6. **微博 ToS/合规规则集**:hard-limit——AI 标识、实名、**抽奖须符合微博抽奖规则 + 中国有奖促销/广告法**、禁止平台 ToS 定义的自动化 spam。
7. **审计**:每个 Tier-2 动作连同真实平台响应,哈希链入同一 SQLite 审计日志。互动策略/额度台账/微博审计行是**净新增持久化 schema**,须各自版本化 + 迁移(即便 content `SCHEMA_VERSION=2` 不动)。

### 5.2 Tier 2 落点

## 6. 关键张力与红线(第一性风险清单)

1. **身份域隔离**:微博 OAuth(实名)与插件 MCP-OAuth/host_principal 是**两个信任域**。微博登录态 = 密钥,**不得**冒充 requester/approver;`requester≠approver` 隔离不因接微博而松动。
2. **密钥管理**:token 存活于**部署者信任域**,不入库、不进日志、**不交给子代理**(既有铁律:子代理只回结构化数据,不碰 mediaops 状态/git)。微博 CLI 自管其 token 文件(部署者域),与插件仅传 `MEDIAOPS_DATA_DIR` 的 `.mcp.json` 设计天然相容。
3. **不可逆 & 不伪造**:发博/互动=公开准不可逆;成功判定只认 CLI 真实返回的 mid/permalink。
4. **credits = 真金白银 + 限流**:5/hr 免费、四档付费;非交互编排易烧额度,CLI 内置重试须**封顶**,成本/配额在 doctor/capabilities 显式暴露。
5. **供应链纪律(rev.2 订正范例)**:weibo-cli 是 pre-1.0、个人维护者(pythias)的第三方 npm。**不并入插件依赖图/dist/SBOM**——**按 Chromium/Java 先例**(非 npm 包、PATH 探测、不进 SBOM),**不是** Playwright/vnu 先例。⚠️ 关键更正:Playwright/vnu **是**声明依赖、**在** SBOM 里(`validate-media-plugin.ts:180-187` 强制每个直接依赖必须出现在 SBOM);若照"像 Playwright 那样"把 `@weibo-ai/weibo-cli` 塞进 `dependencies`,它就进 `bun.lock` → 被 SBOM 门禁**强制收录**,与初衷正相反。正确做法:PATH 上 `Bun.which('weibo')` + `spawn weibo … --output json`(复刻 `doctor.ts:58` 探 java、`delivery-qa.ts` spawn vnu 的模式),缺失即 `DEPENDENCY_NOT_READY`,**零 npm 依赖增量**,dist 自包含与 SBOM 都不动。
6. **AI 标识合规**:发微博须携带**平台原生 AI 生成内容标识**(中国生成式 AI 标识规定),作为 `weibo` 平台一条 `hard-limit` 进 `platform.rules.get`。注意:AI 标识目前**在插件内处理**(平台规则 + 后台人工核对),若要改走 `crablaw-cn` 预审,其 `cn-ai-governance` 目标技能**尚未登记进 capability-routing**,须先补登记(见 §12-C3)。
7. **法律/实名**:实名身份下发布/互动,负面/商业/隐私内容继续路由 `crablaw-cn`,门禁不降级。
8. **读→写注入面(rev.2 新增)**:最危险的不是单侧,而是**组合**——Tier 0 的不可信读出(热搜标题、他人评论正文、搜到的 user id)**流进 Tier 1/2 的命令行参数**(自动回评含注入的评论、按搜出的 id 定向)。这是典型 confused-deputy / 命令注入面。硬约束:**写命令的任何参数只能来自受治理、经真人确认的值,绝不可由 Tier 0 原始读出直接拼接**。
9. **三个机器级"不发布"声明必须同步翻转(rev.2 新增)**:`capabilities.ts:41-44` `dangerousCapabilities:{publish:false, autoComment:false}`、每平台 `apiPublishGate:'gate-b'`、`doctor` `credentialReadiness`。Tier 1 翻 `publish`、Tier 2 翻 `autoComment`——必须在 `capabilities` 输出里**如实降级**,否则就成了插件最痛恨的"伪造安全姿态"。

## 7. 落地次序(风险升序 0→1→2)

| 阶段 | 内容 | 为什么这个顺序 |
| --- | --- | --- |
| 1. Tier 0 | 读侧情报接入 sources/research/trends | 低成本、低身份足迹下先把"子进程调用 + `--output json` + 配额治理器 + 不可信快照/防注入/引用防火墙"这套管道跑硬(注:非零成本,读也计费,见 §4 Tier 0) |
| 2. Tier 1 | **微博长文**作为成熟文章门禁的 Gate B 末端 | 单个高价值写动作;内容形态已锁定长文(§4 Tier 1),**需先补微博渲染档**(A1) |
| 3. Tier 2 | 互动/营销自动化 | 依赖前两步验证过的 doctor 发现 + credits 治理器,再叠加净新增的"互动治理轨"(角色 + 第二真人门禁) |

此次序让配额治理器与依赖探测**先在便宜的读流量上硬化**,再让任何涉及金钱与声誉的写动作上线。
