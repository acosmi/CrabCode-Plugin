## 2. 本地 vs 远程一致性

`git remote -v` 实测：`origin` 的 fetch 与 push **同为** `https://github.com/acosmi/CrabCode-Plugin`。
⚠️ 与主仓 `D:\crabcode` 刻意区分：主仓 `origin` 的 fetch/push 指向两个不同仓库（企业仓 / 个人仓），
本仓**没有**该陷阱，故 `git ls-remote origin` 在本仓是可信的。但为习惯统一，push 实证仍用显式 URL。

| 分支 | 本地 | 远程 | 判定 |
|---|---|---|---|
| `main` | `988b228` | `origin/main` = `988b228` | 一致，无分叉 |
| `task/weibo-cli-mediaops-plan-20260723` | `3476c4e` | 同 | 一致 |
| `rescue/html-video-audit-62b0125` | `62b0125` | **无** | 见 §2.1 |
| — | — | `origin/codex/release-mirror-health-20260814` = `07c8316` | 见 §2.2 |

**冲突面**：零。`main` 无分叉、无未推送 commit、无未合并的远程改动；工作树在本次开工前干净。

### 2.1 🟠 `rescue/html-video-audit-62b0125` —— 纯本地未保存

- 独有 commit：`62b0125 docs(audit): html-video 外部二进制成本与嵌套超时预算立项审计`
- `git merge-base --is-ancestor 62b0125 main` → **NO**（未并入 main）
- `git branch -r --contains 62b0125` → **空**（远程无任何分支包含它）
  - 正向对照：`git branch -r --contains 988b228` 非空，证明该命令本身有效
- ⇒ 这份立项审计文档**只存在于本机**。机器故障即永久丢失。
- 建议：确认内容是否仍需要 → 需要则 `git push -u origin rescue/html-video-audit-62b0125`；
  不需要则显式删除并记录，**不要放着不管**（「≠HEAD 且 ≠main」不等于「可丢」，
  真判据是 blob 是否可达于**任何已推送**的提交 —— 本例答案是「否」）。

### 2.2 🟡 `origin/codex/release-mirror-health-20260814` —— 远程陈旧分支

## 3. CN 镜像健康

镜像契约真源：`.github/workflows/notify-mirror.yml`（公仓只读审计器，`schedule: 47 2,8,14,20 * * *`）。
发布器在私仓 `acosmi/crabcode-source` 的 `sync-plugins-to-mirror.yml`（poll 01:23/07:23/13:23/19:23 UTC）。
镜像根：`https://updates.acosmi.com/crabcode/plugins/crabcode-plugins-official`。
新鲜度 SLO：`FRESHNESS_SLO_SECONDS = 28800`（8 小时）。

### 3.1 🔴 缺陷 1 —— 过期，超 SLO 约 15 小时

| 事实 | 值 |
|---|---|
| 镜像 `latest` 指针 | `e6a457b72a5900b1314b292edeb88d036091b436` |
| 该 commit 日期 | 2026-07-27 03:21:41 -0700（= 10:21 UTC） |
| `latest` 文件 `Last-Modified` | Mon, 27 Jul 2026 10:23:14 GMT（commit 后 2 分钟，说明当时发布及时） |
| `main` 领先量 | **10 commits** |
| 这 10 个 commit 的日期 | 全部 2026-08-14（08:40 → 11:03 -0700） |
| 最新 commit 距今 | ≈ **22.8 小时** |
| SLO | 8 小时 ⇒ **超出约 14.8 小时** |

⇒ 定时审计每天 4 次，自 2026-08-15 约 02:47 UTC 起每次都应在
「Validate the served pointer and freshness SLO」步骤 fail（`mirror is stale: pending green … SLO 28800s`）。

注意：2026-07-27 → 2026-08-14 期间 main **没有新 commit**，所以那 18 天镜像是**正确且最新**的，
不是「19 天没管」。真正的失效窗口从 2026-08-14 18:03 UTC（最后一个 commit）开始。

### 3.2 🔴 缺陷 2 —— 两个必需校验和产物 404

审计器要求（main 版 `notify-mirror.yml`）：

```
fetch -o "${WORK}/${SHA}.zip.sha256"           …  || fail "mirror archive checksum … is unreachable"
fetch -o "${WORK}/marketplace.json.sha256"     …  || fail "mirror marketplace checksum is unreachable"
```

实测：

| 产物 | HTTP |
|---|---|
| `latest` | 200 |
| `marketplace.json` | 200 |
| `<e6a457b>.zip` | 200（10,328,423 B） |
| **`marketplace.json.sha256`** | **404** |
| **`<e6a457b>.zip.sha256`** | **404** |
| `<988b228>.zip`（对照，应缺席） | 404 ✓ 与陈旧指针自洽 |

该要求是 **2026-08-14** 由 `07c8316 fix(release): make CI and mirror health fail closed` 引入的：
`git show e6a457b:.github/workflows/notify-mirror.yml | grep -c sha256` → **0**（当时不要求），
main 版则多处要求。

⇒ **加固只落在审计侧（公仓），发布侧（私仓 `sync-plugins-to-mirror.yml`）没同步产出校验和**。
这是典型的「契约单边升级」：审计器变严，发布器没跟，于是即便新鲜度问题修好，审计仍会在
校验和步骤 fail。**两个缺陷必须一起修，只修新鲜度不够。**

### 3.3 ✅ 已验证健康的部分

- `latest` 是严格 40 位小写 hex，`Cache-Control: no-cache` —— 满足 `0e6f558` 新增的
  「latest 必须可重验证」契约。
- `marketplace.json`：`Cache-Control: public, max-age=300`，未超审计器的 300s 上限；
  与 `git show e6a457b:.crabcode-plugin/marketplace.json` **逐字节相等**
  （双方 sha256 均为 `492cc9ddadb2851b30841497bf887acb8d5965d355880f78ef2da34ec8bec98c`）。
- `<e6a457b>.zip`：`immutable, max-age=31536000`，满足内容寻址产物的一年不可变策略。
- ⇒ 镜像**不是损坏，是冻结**：它服务的那个版本本身完全自洽。

### 3.4 🟡 卫生问题 —— ZIP 重复发送 Cache-Control 头

`<sha>.zip` 的响应里出现**两条** `Cache-Control`：
`max-age=31536000` 与 `public, max-age=31536000, immutable`。
当前审计器把所有 cache-control 行用逗号拼接后取 `min(ages)`，两条 age 相同故能通过；
但重复头属源站配置不整洁，且一旦两条数值分叉，`min()` 判据会取到较小值而误判。建议源站收敛为一条。

### 3.5 用户可见影响 —— 有限

- `.crabcode-plugin/marketplace.json` 在 `e6a457b..main` **零改动**；插件数 **76 → 76** 不变。
  ⇒ 目录索引仍然准确，不存在「新插件装不到 / 已删插件仍可见」。
- 落后的只有 **一个插件**的内容：`crabcode-media-publisher`（62 文件、+6262 行，
  editor imports / Hub UI fixture / 配套测试）。
- ⇒ 症状是「从 CN 镜像装到 07-27 的旧版 media-publisher」，不是「装不上」。

### 3.6 ⚠️ 未验证缺口 —— `988b228` 的 CI 是否绿

镜像**只发布 CI 成功的 commit**（审计器与发布器同判据）。因此存在两种互斥解释：

- **解释 A（镜像/发布器故障）**：CI 绿了但发布器没发 ⇒ §3.1 是真缺陷。
- **解释 B（CI 红）**：`988b228` CI 未通过 ⇒ 镜像停在最后一个绿点是**正确行为**，
  真问题是 CI 红，处置完全不同。

本机**无法区分**：`api.github.com` DNS 完全不通（`getaddrinfo ETIMEOUT`），`gh` token 亦已失效
（`gh auth status` 报 keyring token invalid）。

- 正向对照：`github.com` = HTTP 200、`updates.acosmi.com` 可达 ⇒ 不是全网不通，是 api 子域被墙/DNS 失败。

⇒ **需在能访问 api.github.com 的环境复核**：

```bash
gh run list -R acosmi/CrabCode-Plugin -w ci.yml -b main -L 10
gh workflow run notify-mirror.yml -R acosmi/CrabCode-Plugin   # 手动审计（要求恰好等于最新绿点）
```

不过 §3.2 的校验和 404 **与 CI 状态无关**，无论 A/B 都成立，是已确证的独立缺陷。

## 4. 建议处置顺序

1. **先查 CI**（区分解释 A/B）—— 决定 §3.1 是缺陷还是正确行为。
2. **修发布器产出校验和**（私仓 `sync-plugins-to-mirror.yml`）—— 无论 1 的结论如何都必须做，
   否则审计永远 fail-closed。
3. CI 绿则触发一次发布，随后 `gh workflow run notify-mirror.yml` 手动审计确认回到 `exact`。
4. 源站收敛 ZIP 的重复 `Cache-Control` 头。
5. 处置 `rescue/html-video-audit-62b0125`（推送或显式废弃）与远程陈旧分支
   `codex/release-mirror-health-20260814`（删除）。

> 与本轮 doc 修复工作的关系：本分支的文档修复合入 main 后，
> **在发布链修好之前同样到不了 CN 镜像**。
