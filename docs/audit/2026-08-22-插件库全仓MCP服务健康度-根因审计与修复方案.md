## 0. 修订规则与最终裁决

本修订版不保留设计待决。外部审批、真实租户、供应商资格或端到端测试尚未满足时，默认动作统一为：

```text
不发布可执行连接器
不显示 OAuth CTA
不写 connected/usable
runtime reasonCode = 对应 blocker
```

`not-tested` 是证据状态，不是上线状态；任何 `not-tested` 连接器在生产中固定为 blocked。

最终裁决：**全仓 MCP 端到端健康度不合格，严重级别 P0；原始方案不能直接实施，本修订版是实施真源。**

故障不是单一端点事故，而是以下合同连续断裂：

```text
插件发布
  → 插件启用
  → MCP 独立激活
  → 配置与本地依赖就绪
  → 认证 profile 明确且可完成
  → initialize/tools-list
  → 逻辑工具名可发现
  → 用户显式调用成功
```

当前最高优先级事实：

1. `https://acosmi.com/oauth/crabcode-client-metadata` 的 404 已定位为 Go 后端缺路由，不是 DNS、TLS 或 Nginx 丢路由；
2. 只发布 JSON 不能修好现有 CIMD：宿主使用随机 `localhost` 回调，而静态文档需要稳定、可验证的注册回调；
3. Acosmi 自己的两份 OAuth metadata 广告 `client_id_metadata_document_supported=true`，服务端却不接受 URL client ID；
4. SettingsPage 的鉴权状态也不可靠：当前 worker 把所有 HTTP/SSE 默认投影为 `notLoggedIn`；
5. GUI OAuth 成功后只更新展示状态，不清同配置 connection memoize，也不自动 reconnect/tools-list；
6. Asana standalone 仍使用已退役 SSE，HubSpot 仍使用 `/anthropic` 供应商绑定路径；
7. Slack 受 Marketplace/内部应用资格限制；Asana、HubSpot、BigQuery 需要预注册凭据；
8. Snowflake、Databricks、Benchling 引用 6 个不存在的 manifest `userConfig` 字段；
9. 12 个 LSP 不实现 MCP，不能通过改 manifest 一步变成全端可用 LSP；
10. 跨插件 token 共享、运行时远程 connector `$ref`、自动业务 canary 和本批建设 OAuth broker 均从本方案删除。
11. 当前仓库不存在 `mcpConnectorProfiles.json`、Skill/prompt capability inventory 或 `mcp-release-lock*.json`，本次审计也未取得跨账号 DR/WORM/OIDC 双人审批已验收证据；它们是实施交付，不是当前能力。

## 1. 健康与证据口径

### 1.1 端到端健康

一个生产连接器同时满足以下条件才是 healthy：

1. marketplace、manifest、`.mcp.json` 路径和 schema 有效；
2. 用户能理解并完成 MCP 独立激活；
3. required/optional/sensitive 配置和变量引用一致；
4. 本地依赖在激活前完成 doctor；
5. 认证 profile 是机器可读单值，不依靠 transport 猜测；
6. OAuth/Bearer/外部登录在当前客户端真实完成；
7. `initialize` 和 `tools/list` 在预算内成功；
8. 实际 tools/list 中 required tools 与 certified snapshot 的名称/schema hash 一致；
9. 模型能用安全的逻辑别名找到 canonical wire tool；
10. 用户显式调用时成功，错误能被准确分类；
11. 发布资格、供应商条款和组织管理员前置条件均满足。

以下状态必须分开：

```text
published ≠ installed ≠ plugin-enabled ≠ mcp-activated
          ≠ configured ≠ authenticated ≠ connected
          ≠ discoverable ≠ callable ≠ provider-approved
```

### 1.2 探测结果枚举

机器可读证据只允许：

```text
pass | fail | not-tested | not-applicable
```

解释规则：

- HTTP 200 只证明该请求成功；
- HTTP 401 只证明该 URL 在探测时可达并拒绝匿名请求；
- 401 只有同时具备有效 `WWW-Authenticate`、RFC 9728 Protected Resource Metadata、Authorization Server Metadata 才称有效 OAuth challenge；
- `initialize/tools-list` 成功不代表业务工具已授权；
- 技术调用成功不代表 Acosmi 获得了使用第三方托管端点的生产资格；
- `not-tested` 固定阻断生产发布。

### 1.3 发布支持与运行时状态分离

本方案不新增 `supported/degraded/blocked` 第二套运行时状态机。发布面和运行面分别处理：

- 发布面：远程与 `providerInteraction=external-service` 的 stdio `publish/block` 都进入本地 `.crabcode-plugin/connector-profiles.json`，只有 generation=2 宿主能在 effective publish/lease 通过后物化；只有 `providerInteraction=local-only` 的 stdio `publish` 进入 `.mcp.json`；tombstone 不进入任何运行/管理生成物；

### 4.2 回调 URI 合同不闭合

当前宿主：

```text
生成: http://localhost:<49152-65535随机端口>/callback
监听: 127.0.0.1:<同端口>
```

前置实施审计已否决全局固定 `3118`。纠偏后的候选默认策略为：

```text
CIMD 文档注册值:
  http://127.0.0.1/callback

宿主每次授权:
  先 bind(127.0.0.1, port=0)
  再使用 http://127.0.0.1:<os-assigned-port>/callback

DCR / 预注册 profile:
  默认使用同一 loopback ephemeral 模型；只有供应商真实注册与 E2E
  证明必须固定端口时，才在该 provider profile 单独声明固定 callback
```

该策略只在实际授权服务器已证明会按 RFC 8252 loopback 例外比较 redirect URI 时才可用：scheme、loopback IP literal 与 path 精确一致，port 允许使用请求时的本机临时端口。CIMD 本身不定义“portless 模板”；Notion、Linear、Canva、Synapse 必须逐 provider 提交真实 AS 授权证据，未证明时保持 `provider-e2e-unverified`。禁止 `localhost`、非 loopback address、动态 path、query 或 fragment。PKCE/state 必须启用，但它们不能阻止其他本地应用复用合法 CIMD `client_id` 发起自己的授权。所以 provider E2E 还必须录制同意页清晰显示 redirect hostname/本地回调风险的证据，并记录供应商 trust policy；支持时评估 attestation 或非对称客户端认证。`application_type=native` 是 OIDC/provider 互操作候选字段，在对应 AS E2E 和跨仓合同修订前不擅自改写已合入的 Acosmi 六字段 JSON。

进入 singleflight 和分配 credential generation 之前，control service 必须先执行 `discoverAuthPolicy`。`authDiscovery=fixed` 从 catalog 读取 issuer/resource；`authDiscovery=challenge-first` 则从无凭据 challenge/metadata 得出 issuer/resource。scope 独立按 `scopePolicy` 处理：`fixed` 只用 catalog fixedScopes，`challenge-first` 执行一次无凭据 initialize/HTTP challenge，按 `WWW-Authenticate scope → Protected Resource Metadata scopes_supported → minimumScopes` 得出。任何网络 discovery 只对已通过 endpoint/template SSRF gate 的 resolved endpoint 执行，并按 RFC 9728 取回 Protected Resource Metadata 和 Authorization Server Metadata。该阶段禁止 DCR、打开浏览器、绑定 callback、读/写 secure credential 或分配 generation；metadata GET 禁止 redirect，单文档上限 64 KiB，issuer/resource 必须为 public HTTPS 且通过 origin/SSRF policy。发现的 scopes 按 Unicode NFC、trim、去重、UTF-8 字典序规范化，且必须是 catalog maximum/fixed scope policy 允许的子集；issuer/resource/scope 缺失、歧义或越权时返回 `oauth-discovery-policy-mismatch`。只有 discovery 成功后才计算 authPolicyFingerprint/scopeFingerprint 并进入下述 request-intent singleflight；失败时 generationHighWatermark 不变。

immutable discovery snapshot 固定为 `JCS({authDiscovery,issuer,resource,authorizationEndpoint,tokenEndpoint,registrationEndpoint|null,tokenEndpointAuthMethods,codeChallengeMethods,normalizedScopes,protectedResourceMetadataSha256|null,authorizationServerMetadataSha256})`；URL 都是验证后 canonical 值，方法/scope 数组去重后按 UTF-8 字典序排序。`discoverySnapshotSha256` 是该 JCS 字节 SHA-256，不包含 challenge header 原文、cookie、authorization URL query 或任何凭据。

MCP `2026-07-28` 的 wire 门禁是上述 snapshot 生效的必要条件，不得由“已保存字段”代替：

1. Authorization Server Metadata 必须显式包含 `code_challenge_methods_supported` 且其中有 `S256`；缺失、只有 `plain` 或 metadata 未验 issuer 时，在打开浏览器前返回 `oauth-discovery-policy-mismatch`。
2. 打开浏览器前，客户端将已验证 metadata 的 exact `issuer`、PKCE verifier 和 state 绑定到同一 flow record。回调中存在 `iss` 时必须按 RFC 9207 与记录 issuer 做 simple-string comparison；metadata 广告 `authorization_response_iss_parameter_supported=true` 而回调缺 `iss`时也必须拒绝。失败时不向任何 token endpoint 发送 code，也不展示未验证的 error 字段。
3. 经 RFC 9728 得到的 canonical MCP `resource` 必须按 RFC 8707 同时进入 authorization request 和 token request；两处缺失、不一致或与 fingerprint 不同时拒绝。
4. issuer-bound credential、step-up scope union 和上述 `iss/resource/S256` 均必须有正负 wire 测试；只测内存字段不构成验收。

generation=2 的所有交互式 OAuth 与 credential CRUD 统一进入每个 OS 用户唯一的 MCP control service；GUI、TUI、CLI 都是经身份校验的 IPC client，不直接读写 secure index 或绑定 callback 端口。control service 计算 `requestIntentKey=sha256(JCS([credentialOwnerId,connectorProfileId,connectionInstanceId,authPolicyFingerprint,scopeFingerprint]))`：已有同 key leader 时 follower 不分配 generation，只返回 `oauth-flow-in-progress` 并订阅；不同 intent 使用各自的 OS-assigned loopback 端口和 state，不得仅因另一 flow 存在就返回 busy。只有 leader 按第 4.7 节分配唯一 `newGeneration`，然后形成 `flowIdentity=JCS([requestIntentKey,newGeneration])`。实现可设置有界并发上限，达到上限才返回 `oauth-callback-busy`。

交互流期间更新/清除 client ID、client secret、registration 或 policy 时，credential mutation 先把该 intent 的现有 leader 标记为 stale，等待其关闭 listener，再执行新操作；新请求不得订阅已 stale flow。动态 listener 必须让 OS 分配端口，绑定失败即关闭该 flow，不回退 `localhost` 或非 loopback address。credential registration 记录持久化 `callbackProfile=loopback-127.0.0.1-ephemeral` 与注册基值 `http://127.0.0.1/callback`；只有 AS/provider fixture 已证明 RFC 8252 port 例外时才能跨授权复用 registration。generation=1 的既有 registration 不自动迁移。

control service IPC 安全合同固定为：

- service 作为 generation=2 宿主产物一同签名/打包；macOS 由 per-user LaunchAgent、Windows 由 per-user startup task、Linux 由 `systemd --user` socket activation 启动，禁止系统级共享 daemon。首客户端只能通过 OS 级 singleton lock 启动一个实例，3 秒内 socket/pipe 未 ready 即返回 `control-service-unavailable`；
- macOS 使用 `$HOME/Library/Application Support/CrabCode/run/mcp-control-v2.sock`，父目录 owner=当前 UID/mode=0700，socket mode=0600，通过 `getpeereid` 验证 peer UID 与 service UID 相同；
- Linux 只使用 `$XDG_RUNTIME_DIR/crabcode/mcp-control-v2.sock`，要求 runtime dir owner=当前 UID/mode=0700，socket mode=0600，通过 `SO_PEERCRED` 验证 UID；`XDG_RUNTIME_DIR` 缺失/权限错误时不回退 `/tmp`；
- Windows 使用 `\\.\pipe\CrabCode\McpControlV2\<current-SID-hash>`，DACL 只允许当前用户 SID，启用 `PIPE_REJECT_REMOTE_CLIENTS`，服务端通过 client process token 再次比对 SID；
- 三平台都禁止 TCP/HTTP/WebSocket fallback，禁止跨用户共享 socket/pipe；
- 协议只接受 4-byte big-endian length + UTF-8 JSON，`protocolVersion=2`，单帧上限 1 MiB，超限/未知 method/未知字段直接断开；method allowlist 只包含 status、OAuth start/cancel、credential set/update/clear、connection replace/select，不提供 token/secret export/read method；
- 每条 IPC 连接由 service 生成 256-bit `sessionNonce`，client 请求必须带该 nonce、UUIDv4 requestId 和从 1 递增的 uint64 sequence；service 缓存当前连接已见 requestId，拒绝 nonce 不符、重放、跳号/回退，断线后 nonce 立即失效；
- secret/token/code 只在内存请求对象和 OS credential backend 之间流转，IPC access/error/debug log 只记 method、requestId、脱敏 owner hash、result code 和 latency；
- socket/pipe 不存在、所有者/权限错误、peer UID/SID 不符或协议版本不匹配时返回 `control-service-unavailable`，不回退到客户端直接读写凭据。

必测负向用例为：伪造/不同 UID、不同 Windows SID、remote named-pipe client、错误 socket owner/mode、TCP 连接、>1 MiB 帧、未知字段/method、旧 nonce、重复 requestId、sequence 回退/跳号。全部必须在凭据读写前拒绝，且日志中 secret/token/code 命中数为 0。

### 4.3 不实施每次登录本地预检后切 DCR

客户端能 GET CIMD 不等于授权服务器能 GET；按单次网络结果在 CIMD client ID 与 DCR client ID 间切换会制造身份、token 和注册记录分裂。

固定策略：

- `clientRegistration=cimd` 始终使用 CIMD；文档不可达即返回 `cimd-document-unavailable`；
- `clientRegistration=dcr` 始终使用 DCR；
- `clientRegistration=preregistered-user` 始终使用用户配置的 client ID；
- 登录过程中不切换 registration；
- profile 变化通过 `authPolicyGeneration` 触发迁移。

DCR registration 只允许由用户显式 `nextAction=oauthLogin` 触发；安装、插件启用、状态列表、doctor、release probe 和普通 reconnect 均不得注册 OAuth client。

### 4.5 SettingsPage 与 worker 鉴权状态错误

当前 `mcp-status-list.ts`：

```text
HTTP/SSE → oauthCapable=true → notLoggedIn
```

该推断把以下连接器混在一起：

```text
anonymous
bearer token
OAuth
ADC/CLI/external identity
unknown
```

结果：

- 匿名/unknown HTTP 在没有显式 authStatus override 时出现 OAuth 按钮；
- Bearer 配置没有被 lifecycle 正确投影时出现 OAuth 按钮；
- plugin `authState=unknown + lifecycle=ready` 显示按钮，后端点击后又拒绝；
- 手工 HTTP/SSE 没有 lifecycle 时会被当前 authorization guard 放行并误启动 OAuth；
- `performMCPOAuthFlow` 在真正完成新授权前会删除旧本地 client/token，误点可破坏现有会话。

1. worker 不再按 transport 生成 `notLoggedIn`；

3. runtime 401/discovery 将 `unknown` 收敛为 `requires-login`；
4. 只有 `nextAction=oauthLogin` 时显示 CTA；
5. 重新授权使用 pending credential slot；新 token 成功后原子替换，失败保留但不发送 legacy token；
6. 旧 token 最佳努力撤销，撤销失败记录脱敏审计但不回滚新 token。

### 4.6 OAuth 成功不等于连接恢复

当前 GUI 链路：

```text
performMCPOAuthFlow success
  → mcpServer/oauthLogin/completed
  → GUI store 显示 success
```

缺失：

```text
exact connection cache eviction
active config revalidation
reconnect
initialize
tools/list
startup status
```

`mcp reload` 会清认证负缓存，但 `clearStaleServerCachesForConfigs` 对 active exact key 直接保留，旧 memoized `needs-auth` Promise 仍存在。

固定修复由 control worker 完成：

```text
token success
  → 重读 active config
  → 复算 authPolicyFingerprint 并核对 pending generation
  → 检查中途 disable/remove/policy blocker
  → evictExistingServerCache(exact key)
  → reconnect
  → initialize/tools-list
  → startupStatus/updated
  → oauthLogin/completed
```

多窗口不各自发起 reload；只有 identity 匹配的窗口接收该 flow 结果。

callback 收到 code 后、token exchange 之前，以及 credential entry 写入后、index swap 之前，worker 都必须重读 catalog/active config/index，并同时满足：`computedAuthPolicyFingerprint=flow.authPolicyFingerprint`、`index.pending.generation=flow.newGeneration`、`index.pending.policyFingerprint=flow.authPolicyFingerprint`、`index.pending.discoverySnapshotSha256=flow.discoverySnapshotSha256`、内存 immutable discovery snapshot 重算 SHA 与该值一致、`index.currentState=legacy`、profile 未 disable/remove/block。不在 callback 中重新联网发现并悄然改变 flow；若 control service 已获得不同的新 discovery snapshot，必须先将旧 flow 标记 stale。任一不符时立即销毁内存 code/token，删除该 flow 已写的 pending credential entry，保留代际高水位和 legacy current，只向该 `flowIdentityHash` 发送 `oauth-flow-stale`；禁止 swap、reconnect 或广播 success。

### 4.7 凭据 key 缺少认证策略 generation

当前 `getServerKey` 只纳入：

```text
serverName + type + url + headers
```

它没有纳入 client ID、registration、issuer、resource、scope policy、callback profile。`clientInformation()` 又优先返回已存 client ID，因此存在旧记录时会继续使用旧 CIMD/DCR 身份。

固定新增：

```text
authPolicyGeneration = 2
authPolicyFingerprint = sha256(JCS([
  "mcp-auth-policy-v2",
  profilePolicyFingerprint,
  authMode,
  clientRegistration,
  preregisteredClientIdOrNull,
  issuer,
  resource,
  normalized scopes,
  callbackProfile,
  discoverySnapshotSha256
]))
```

fingerprint 只含 credential mutation/generation 分配前可获得的 catalog 与第 4.2 节无凭据 discovery 结果；完整 discovery snapshot 的 SHA-256 写入 pending 审计字段，但不写 raw response header/query。DCR 服务的 `preregisteredClientIdOrNull=null`，动态注册得到的 client ID 和 `credentialGeneration` 都不进入 fingerprint，避免 secure-storage 寻址自举循环。

`authMode!=oauth` 时 fingerprint 中 issuer/resource/normalizedScopes/callbackProfile/preregisteredClientIdOrNull 使用字面 `not-applicable`，`discoverySnapshotSha256` 使用 64 个零字符；禁止省略元素导致不同 authMode 的 tuple 长度不同。Bearer 的 config schema/binding 已由 profilePolicyFingerprint 覆盖，实际 token 值仍不进任何 fingerprint。

每个稳定 credential index record 保存：

```text
schemaVersion=2
revision
generationHighWatermark
currentState=active|legacy|deleted
currentPolicyFingerprint
currentCredentialGeneration|null
currentCredentialEntryKey|null
currentRegistrationEntryKey|null
providerSubjectHash|null
pending|null|{operation,policyFingerprint,discoverySnapshotSha256|null,generation,baseCredentialGeneration|null,credentialEntryKey|null,registrationEntryKey|null,expiresAt}
```

`generationHighWatermark` 是 index 内持久化、只增不减的代际高水位；`credentialGeneration` 不得作为下一代计算来源。OAuth client secret、Bearer/PAT、DCR client secret 的新增、更新、清除，authPolicyFingerprint 变化，以及 OAuth token refresh 都分配 `newGeneration=generationHighWatermark+1`。失败、超时、进程崩溃和清除操作都不得回退高水位或复用代际号。

`revision` 是每次 index 更新都 +1 的乐观并发版本。control service 对 `credentialIndexKey` 取跨进程命名互斥（macOS `flock` 锁定 app-state 下仅含 index hash 的 0600 lock file；Windows named mutex；Linux `flock`），锁内重读 secure index，只在 `revision=observedRevision` 时原子替换为 `revision+1`。revision 不符时丢弃未写入结果、重读并重新分配；禁止 last-writer-wins。control service 崩溃时 OS 释放互斥，下一进程按 pending 恢复规则接管。

index 状态语义固定为：

- `active`：只有 current policy fingerprint 匹配且 current entry 读回校验成功时才可发送；
- `legacy`：current entry 仅为撤销/审计保留，generation=2 永不发送；
- `deleted`：本地不存在可用凭据，current credential/registration pointer 均为 null；`currentCredentialGeneration` 保留该次删除代际，防止旧写入复活。

迁移/轮换顺序：

1. index 不存在时在 per-index 跨进程互斥内建立 `revision=1,generationHighWatermark=0,currentState=deleted`的空记录；
2. `authorize|replace|clear` leader 在同一互斥内重读 index，分配 `newGeneration=highWatermark+1`，以 revision compare-and-swap 原子持久化新高水位、`currentState=legacy`、`pending=null`，再读回校验；从这一步起旧 current 只保留但不得发送；CAS 失败时不得沿用已计算 generation；
3. 把含同一 `newGeneration` 的 pending 描述原子写进 index；`operation` 只能为 `authorize|replace|refresh|clear`，非 refresh 时 `baseCredentialGeneration=null`；OAuth authorize/replace/refresh 的 `discoverySnapshotSha256` 必须等于第 4.2 节该 flow 的不可变 discovery snapshot，Bearer/clear 为 null；
4. PKCE/auth code/token/新 secret 只保存在进程内 pending slot，TTL=5 分钟；DCR registration 写 pending registration entry；
5. 新 credential entry 写入并读回校验；已读回校验的 DCR registration 可先原子更新 `currentRegistrationEntryKey`，因用户拒绝/超时而重试时必须复用，不再注册；
6. `authorize|replace` 成功时单次原子更新 index：`current=pending,currentState=active,pending=null`；
7. `clear` 操作在本地删除决定后单次原子更新：`currentCredentialGeneration=newGeneration,currentCredentialEntryKey=null,currentRegistrationEntryKey=null,currentState=deleted,pending=null`；provider revoke 失败只记录脱敏 failure code，不得使本地旧凭据复活；
8. index swap 成功后最佳努力撤销并删除旧 credential/registration entry；
9. `authorize|replace` 授权/写入失败时清理 pending entry 并置 `pending=null`，但必须保留 `generationHighWatermark` 和 `currentState=legacy`；禁止恢复旧 current 为 active；
10. 进程启动发现未过期 pending 时按 operation 分流：`authorize|replace` 只有在 entry 读回、policy/subject 校验全部通过后才执行第 6 步；`clear` 完成第 7 步的 deleted 写入；`refresh` 使用下述 refresh 恢复规则。发现过期/损坏 `authorize|replace|clear` pending 时删除 pending entry 并保持 `currentState=legacy`；
11. 无 pending 但 `currentState=legacy|deleted` 时，启动恢复不得发送 Authorization header；
12. 记录 `auth-policy-migrated`、`credential-rotated`、`credential-refreshed`、`credential-cleared` 或对应 failure code，不记录 secret/token/code/state。

refresh 不使用上述“先把 current 置 legacy”的主动替换语义，其固定流程为：

1. control service 按 `[credentialIndexKey,currentCredentialGeneration,currentPolicyFingerprint]` 做 per-index refresh singleflight；同 key follower 订阅，不发起第二个 token request；
2. leader 在跨进程互斥内重读 active index，以 revision CAS 分配 newGeneration、提高 high watermark，写入 `pending.operation=refresh,pending.baseCredentialGeneration=currentCredentialGeneration`，但保持 `currentState=active` 和旧 current pointer；
3. 锁外调用 token endpoint；响应含新 refresh token 时写入新值，不含时必须从旧 entry 复制原 refresh token，禁止写空；新 access/refresh token 只写 newGeneration entry 并读回校验；
4. 重新取互斥并同时校验 `pending.generation=newGeneration`、`pending.baseCredentialGeneration=currentCredentialGeneration`、policy fingerprint 未变、pending/immutable `discoverySnapshotSha256` 一致和 observed revision，才 CAS 切换 new current、保持 active、清 pending；任一不符则删除该 new entry，迟到/乱序响应不得覆盖已切换 current；
5. timeout、网络错误或 provider 5xx 时清 pending/new entry，保留 high watermark 与旧 active current；`invalid_grant|invalid_client` 或 provider 明确 revoked 时，清 pending 后把旧 current 置 legacy 并收敛为 `requires-login`；
6. 进程恢复发现 refresh pending 时，只有新 entry 完整、未过期且第 4 步全部条件仍成立才切换；否则清 pending/new entry 并保留旧 active current。

### 4.8 凭据 owner 与账号/租户隔离

generation=2 禁止裸字符串拼接。全部 identity 先按 RFC 8785 JSON Canonicalization Scheme 编码为 UTF-8，再做 SHA-256。

```text
hostPrincipal = 已登录时 ["account", tenantId, userId]
              = 未登录时 ["installation", installationId]

credentialOwnerId = hex(sha256(JCS([
  "mcp-owner-v2",
  hostPrincipal,
  pluginId,
  connectorProfileId,
  connectionInstanceId
])))

credentialIndexKey = "mcp2:index:" + hex(sha256(JCS([
  "mcp-credential-index-v2",
  connectorProfileId,
  credentialOwnerId
])))

credentialEntryKey(generation) = "mcp2:credential:" + hex(sha256(JCS([
  "mcp-credential-entry-v2",
  credentialIndexKey,
  generation
])))

registrationEntryKey(policyFingerprint) = "mcp2:registration:" + hex(sha256(JCS([
  "mcp-registration-entry-v2",
  credentialIndexKey,
  policyFingerprint
])))
```

credentialIndexKey 不含 clientId、policyFingerprint 或 generation，因此进程重启前即可由非敏感 connection binding 定位 index；secure storage 只保存 hash key，不保存可枚举的原始账号 tuple。

`pluginId` 使用宿主现有 source-qualified `getPluginStorageId` 结果，不使用可碰撞的 display name。

生成规则：

1. 已登录 CrabCode 时使用结构化 `hostPrincipal=["account",tenantId,userId]`；
2. 未登录时使用结构化 `hostPrincipal=["installation",installationId]`，其中 installationId 为 256-bit random 且只存 OS credential backend；
3. `connectionInstanceId` 是用户显式创建连接时生成的 UUIDv4，持久化在非敏感 `pluginConfigs[pluginId].mcpConnections[connectorProfileId][]` binding；同一连接重启保持，用户 disconnect 后永久废弃；
4. 一个 connectionInstanceId 只绑定一个 provider account。provider 返回稳定 subject/account ID 时把 SHA-256 写入 index；refresh/reconnect 发现 subject 变化即关闭连接、撤销 token、返回 `provider-subject-mismatch`，不得把同一 instance 改绑新账号；
5. provider 不返回 subject 时仍按 connectionInstanceId 隔离，禁止退回 profile-wide token；
6. CrabCode 登出、账号切换、tenant 切换立即关闭旧 owner 的内存连接并清缓存，不读取其 secure entry；
7. 登出不自动删除旧 owner 的落盘凭据；用户选择 disconnect 才执行 revoke/delete；
8. plugin disable 关闭连接但保留 owner-scoped 凭据；plugin uninstall 执行 disconnect，最佳努力 revoke 后删除本地 credential；两者都不把 credential 转移给其他 pluginId。

OAuth/Bearer profile 的 `credentialOwnerScope` 固定为 `host-principal+plugin+profile+connection-instance`；none/external/unsupported profile 固定为 `not-applicable`。

切换 provider account 必须 disconnect 旧 instance 并创建新 connectionInstanceId。回归使用两个 CrabCode 用户、两个 tenant、两个 pluginId、两个 profile、两个 connectionInstanceId 的 32 种 tuple，所有 key 必须不同；每个 instance 再分别绑定一个 provider subject 并验证 subject mismatch。额外加入冒号、斜线、Unicode 和空字符串编码负测。账号/tenant 切换后的首个请求不得携带旧 Authorization header。

### 5.1 Profile 结构

eligibility verdict 不进入 `catalogCommit` 或 generator 输入/包；release validator 在 catalog/plugin artifacts 完成后才输出 `.crabcode-plugin/release-staging/provider-verdicts/<sha256>.json`，与 lock/envelope 一样被 Git ignore 并从 root setup/package include list 排除，随后作为 lock `artifacts[]` 公开内容寻址产物发布。因此纯 lease 续签不改 catalogCommit/plugin/marketplace digest。provider authorization basis、public terms 取证结果、provider/app/client/distribution/scope/region 集合、reviewerId、private locator、自由文本摘要、批准函/合同/联系人/价格都是 `release-private`，禁止进入 Git、插件包、公开 lock 或 generator 输出。公开 `officialReference` URL 必须为 HTTPS 且无 query/fragment，只作导航，不作资格证据。

插件 manifest 新增固定字段：

```json

    "connectorProfilesSha256": "<sha256>",
    "connectorSkillsSha256": "<sha256>",
```

`issuerPolicy/resourcePolicy` 对 OAuth fixed 使用 catalog canonical URL，对 OAuth challenge-first 使用字面值 `discovered-public-https`。`clientIdentityPolicy` 对 CIMD 使用固定 metadata client URL，对 DCR 使用 `dynamic-registration`，对 preregistered-user 使用 `user-configured-client-id:<clientIdConfigSchemaSha256>`，禁止纳入任何用户 clientId/clientSecret 值或 live discovery snapshot。`authMode!=oauth` 时 `issuerPolicy=resourcePolicy=clientIdentityPolicy=not-applicable`；Bearer token 字段约束已由 credentialSource/configSchemaSha256/configBindingsSha256 覆盖，external identity 由 credentialSource 与对应 variant 的 doctor SHA 覆盖。因此 Asana/HubSpot/BigQuery 的不同 BYO client 共享同一 profile 资格 verdict，但仍在下述 authPolicyFingerprint/credentialOwnerId 层按实际 client/账号/实例完全隔离。

release policy 再构成互斥 union：

```text
PublishPolicy:
  releaseDecision=publish
  canaryContract=required
  blockedReasonCode=forbidden
  certifiedToolsSnapshotRef/Sha256=required
  costOwnerTeam=required

BlockPolicy:
  releaseDecision=block
  blockedReasonCode=required
  canaryContract=optional
  certifiedToolsSnapshotRef/Sha256=optional
```

`canaryContract` 存在时固定结构为 `{toolName,args,assertion,fixtureRef}`，四字段必须齐全，`args` 为 canonical JSON。`assertion` 只允许 `{jsonPath,op,expected}`，其中 `op=equals|exists|isArray|nonEmpty`，不执行任意脚本。`officialReference` 是非空数组：第三方 profile 只接受无 userinfo/query/fragment 的 HTTPS 官方文档 URL，第一方 profile 只接受仓库相对 `docs/` 或 `README.md` 路径。

`certifiedToolsSnapshotRef` 指向 release lock `artifacts[]` 中永久保留的 JSON；每个工具记录 `{logicalToolName,inputSchemaSha256,annotationsSha256}`，按 logicalToolName 排序。snapshot 只能由通过认证的 release fixture 实际 `tools/list` 生成，generator 不联网、只校验 snapshot SHA 和 requiredTools 子集。

blocked→publish 的认证循环由仓库外产品运行面的独立 release harness 打破：`scripts/certify-mcp-profile.ts` 只在受控 release job 中接受单一 profile ID。无凭据 contract-only 模式可验证 schema/doctor；需携凭据的 auth/initialize/tools-list/canary 模式只允许当前 blocker 为 `cimd-document-unavailable|host-oauth-reconnect-missing|oauth-client-config-missing|secret-config-schema-missing|provider-e2e-unverified`。tombstone，example/退役/vendor-specific/Claude-hosted denylist，以及 `provider-app-approval-required|provider-contract-missing|auth-profile-unclassified|endpoint-tls-unreachable|region-access-denied` 一律在读 credential 前 hard fail。

provider 资格循环固定分两步：先在零凭据/零网络的 release-private job 中完成 basis/evidence/HMAC/双签 verdict，经 `provider-integrations-approver` 审核后只把 blocker 从 `provider-app-approval-required` 改为 `provider-e2e-unverified`，releaseDecision 仍为 block、runtime config 仍为 0；之后 harness 才允许读 fixture credential 执行 E2E。禁止为了跑 probe 直接把 provider-approval blocker 跳到 publish。

凭据 probe 前必须先在 release-private validator 内验证互斥 `authorizationBasis=public-terms|written-approval|internal-app`。`public-terms` 要求当前公开条款明确覆盖 client/distribution/scopes/regions；`written-approval` 要求 provider/授权代理方的有效书面批准；`internal-app` 要求 Acosmi 或指定企业 tenant 管理员对 appId/tenant/distribution 的有效批准。本报告的公开 marketplace 不允许 internal-app effective publish；它只能用于另行隔离的 enterprise-private marketplace/lock，本仓 profile 继续 block。三种 basis 都必须验证 provider/app/client/distribution/scope/region 精确集合、issuedAt/expiresAt/reviewDueAt/revokedAt、法务决定与原始证据 SHA；source URL/附件/联系人/reviewer subject/private locator 全部只留在 private WORM。

```text
PrivateProviderEvidence{
  schemaVersion=2,
  connectorProfileId,
  profilePolicyFingerprint,
  authorizationBasis,
  providerId,
  appId|null,
  tenantIds[],
  allowedClients[],
  distributions[],
  scopes[],
  regions[],
  coverageMode=entire-profile-domain|subset,
  profileConfigDomainSha256,
  coverageProofSha256,
  sourceDocuments[{sourceUrl,contentSha256,retrievedAt,attachmentObjectSha256|null}],

```

`public-terms` 要求 appId/providerApprovalSubject=null；`written-approval` 要求 providerApprovalSubject 为 provider/授权代理 subject；`internal-app` 要求 appId、tenantIds 和管理员 providerApprovalSubject 非空。所有集合去重并按 UTF-8 字典序排序，sourceDocuments 按 contentSha256 排序，签名覆盖除 `signature` 外的全部 JCS 字节；`expiresAt/reviewDueAt` 必须晚于 issuedAt，`revokedAt` 非 null 或 `legalDecision=block` 时禁止生成 approved verdict。

公开 marketplace 的 approved verdict 还必须 `coverageMode=entire-profile-domain`：`profileConfigDomainSha256=sha256(JCS({profilePolicyFingerprint,configSchema,configBindings,distribution=public-marketplace}))`，`coverageProofSha256` 指向 private WORM 中的机器覆盖结果。枚举字段必须证明 evidence allowed set 是 schema enum 的超集；regex/template/BYO client 等非有限值域必须有条款/书面批准明确覆盖整个公开值域/用户自备应用类别的签名 domain proof，禁止用一个 fixture 租户/app 推导整个值域。`coverageMode=subset` 或 tenantIds/appId/regions/allowedClients 只覆盖公开 schema 子集时，本仓 profile/verdict 必须 block；只能在 enterprise-private marketplace 新建一个不同 connectorProfileId、将该子集编进运行可见 configSchema 的限定 profile，重算 profilePolicyFingerprint，不得依赖 runtime 看不见的 hidden membership 放行用户值。

scope 覆盖也是 domain proof 的必须项：`scopePolicy=challenge-first` 时 private evidence scopes 必须是 catalog maximumScopes 的超集，`scopePolicy=fixed` 时必须是 fixedScopes 的超集；只覆盖 minimumScopes 不得生成 approved verdict。runtime 任何实际/step-up scopes 必须同时是 maximumScopes 与当前用户同意集合的子集。

完整 private evidence 按 RFC 8785 canonical 后计算 `evidenceCommitment=HMAC-SHA256(providerEvidenceCommitmentKey,JCS(privateEvidence))`；HMAC key 只存在 release/legal validator 的受保护 secret backend，每次发布从 private primary/DR 双取回原文并重算 commitment。禁止使用无盐 SHA 公开 provider/scope/region/distribution 低熵集合。

private evidence 只按 `privateAuditId` 写入 `oss://acosmi-private-release-evidence-cn-hangzhou/provider-evidence/<privateAuditId>/<sha256>.json` 和中国境内独立账号/异区域 DR `oss://acosmi-private-release-evidence-dr-cn-shanghai/provider-evidence/<privateAuditId>/<sha256>.json`；release-private audit index 为 `{privateAuditId,primaryRef,disasterRecoveryRef,sizeBytes,sha256,evidenceCommitment,commitmentKeyId,verdictSha256,validatedAt,validatorRunId}`，同样双写 WORM。该 index/ref 不进入公开 lock；公开面只能通过 HMAC commitment 与双签 verdict 证明 release validator 已验证，不能定位原文。供应商合同/批准函/联系人/reviewer subject 原文禁止写入 AWS 或中国境外 DR；其 WORM 保留截止日期固定为合同/批准到期、撤销日或最后一次生产引用日三者中最晚日期再加 7 年，只允许经 `legal` 签名 legal-hold 延长，禁止缩短。

release validator 只向 Git-ignored release staging/公开内容寻址 artifact 与 lock 输出：

```text
ProviderEligibilityVerdict{
  schemaVersion=1,
  connectorProfileId,
  profilePolicyFingerprint,
  eligibilityStatus=approved|blocked,
  blockedReasonCode|null,
  leaseNotBefore,
  leaseNotAfter,
  evidenceCommitment,
  commitmentKeyId,
```

`verdictPayload` 固定为上述 verdict 排除 `signatures` 的对象，两个 signer 都对 `JCS(["mcp-provider-eligibility-v1",verdictPayload])` 签名；必须同时有 `legal` 和 `security` 两个独立 key 的有效签名。`leaseNotAfter<=min(private expiresAt,private reviewDueAt,issuedAt+30 days)`；blocked verdict 的 leaseNotBefore/leaseNotAfter 为 `not-applicable`。公开 verdict 不包含 authorizationBasis、provider/app/scope/region/distribution hash、reviewerId、privateWormRef、sourceUrl 或自由文本。release candidate 输入的 verdict file ref/SHA 只写入 lock `profileAuthorizationLeases.eligibilityVerdictRef/Sha256`，不写入 plugin profile/catalog 运行字节；因此纯 lease 续签不改 plugin/marketplace artifact。runtime host 验两个 verdict 签名、connectorProfileId/profilePolicyFingerprint/时效绑定，不重算 HMAC；release validator 负责重算 HMAC 并验该 commitment 已被 verdict 和 release lock 同时覆盖。

harness 只在 private basis/evidence 通过后读临时 fixture credential，禁止使用用户 settings/credential；出站防火墙只放行 profile 解析后的精确 scheme/hostname/port，template profile 只放行 private evidence 指定的 fixture tenant，3xx 改变 origin、DNS 重绑定到私网/特殊 IP 或任一额外 egress 均中止；credential 只允许 private evidence 内的 provider/app/distribution/scopes/regions。该脚本不进入插件包或 CrabCode runtime，失败/成功都不自动修改 catalog 或 releaseDecision。QA 与 provider approver 复核输出后，只能通过代码审核的后续 commit 写入 snapshot hash/canaryContract/releaseDecision。

### 5.2 生成物与凭据隔离

build-time catalog 生成两类本地发布物：

```text
remote publish/block                         → 进入 `.crabcode-plugin/connector-profiles.json`
stdio + external-service + publish/block    → 只进入 `.crabcode-plugin/connector-profiles.json`
stdio + local-only + publish                → 进入 `.mcp.json`
stdio + local-only + block                  → 只进入 `.crabcode-plugin/connector-profiles.json`
tombstone                                   → 两类生成物都不进入
```

`.crabcode-plugin/connector-profiles.json` 是 generation=2 宿主的本地、schema-validated remote/leased-stdio profile 输入：effective publish 只能在 activation/config/auth/provider-lease gate 后物化为 runtime config/spawn，block 只供管理 UI 展示。generation=1 忽略该文件；remote 和 external-service stdio 永不进入 `.mcp.json`，因此旧宿主不会绕过 generation=2 lease gate。

generation=1 的真实 marketplace 安装/加载链 `pluginLoader/createPlugin.ts` 与 `pluginLoader/installSources.ts` 调用非 strict `PluginManifestSchema`，会剥离未知顶层字段并忽略 `mcpConnectorProfiles/mcpGeneratedArtifacts`；安装链不调用 `validatePlugin.ts` 的 strict schema。旧版手工 `crabcode plugin validate` 会 strict fail，但不参与 marketplace 安装。P0 包由 generation=2 validator 构建后发布；generation=1 只消费已构建包并读取 `providerInteraction=local-only` 的 stdio `.mcp.json`，所以兼容合同不矛盾。

profile `configSchema` 是连接器变量的单一真源。宿主管理 UI 将其与插件普通 `userConfig` 分区展示并写入同一插件 secure-config namespace；manifest 普通 `userConfig` 禁止重复声明 profile 已拥有的 key。generator 根据 profile schema 生成 `${user_config.KEY}` 引用，禁止手写第二份 schema。

生成合同：

- 安装时不联网解析 connector `$ref`；
- 老版本宿主不会因目录服务不可达而失去配置；
- CI 对生成物 digest 做双向校验；
- URL/auth/config 不允许手工复制漂移；
- token 继续按 plugin instance + account/tenant + AS + client ID + resource + scope 隔离；
- 不跨插件共享 token、refresh token 或撤销状态。

DCR 注册结果写入 `registrationEntryKey(authPolicyFingerprint)`，保存 client ID、服务端返回的 client secret、issuer、`callbackProfile`、注册基值和 policy fingerprint，不保存 token。当次 `runtimeRedirectUri` 只与 flow record 绑定，不用下次随机端口覆盖注册基值。写入读回成功后原子更新稳定 index 的 `currentRegistrationEntryKey`；相同 fingerprint 的后续授权只在 AS/provider fixture 已证明 callback policy 时才复用，用户拒绝/超时不得再次注册。issuer/fingerprint 变化后创建新 registration entry，旧 entry 只在新授权成功后删除。

不实施：

- 单次登录 CIMD↔DCR fallback；
- GUI 收广播后全局 reload；
- 自动打开内嵌 WebView；
- client secret 写 `.mcp.json`、settings JSON、日志或命令行；
- 误点 OAuth 时先删除现有有效 token。

### 7.5 `mediaops` 身份

固定产品行为：

1. 默认保持 fail-closed；
2. 只读 `capabilities` 可在无 principal 时调用；

## 8. Release、凭据迁移与回滚顺序

发布顺序不可交换：

```text
0. 在整改树上完成本机全闸，API 手动触发 exact-main CI；只有 testedCommit/testedTree/log SHA 全部绑定才可继续
1. API 手动触发现有官方镜像发布器，按 `latest + <sha>.zip + .sha256` 发布 P0-0E；公网读回和旧→新安装+宿主重启 fixture 通过前状态为 blocked
2A. `[ACOSMI-SRC/REL 独立]` 完成 R→A→B 源码/bundle；只在 `ACOSMI-REL-BASE`（backend stores+四环境+OIDC+fixture）通过后部署 A→B 与 B→A→B 演练。该路径不等 P0-0A-BOOTSTRAP
2B. 与 2A 并行：`P0-0A-BOOTSTRAP` 只验 public lock/evidence DR、WORM、key set 与 bootstrap canary；失败只阻断未来 trust path
2C. 与 2A/2B 并行：P0-0B catalog/capability 硬化只产生 remote-dependent callable=0 的 safe artifacts
3. `GENESIS-INTEGRATION` 仅在 2B、2C 及 lock 实际引用的 2A artifact record 通过后，组合/签名/发布 genesis；然后才用 lock 验其引用 artifacts，禁止反向依赖
4. 2A 和 3 都通过后，CrabCode 发布内置 genesis trust anchor 且实现 MCP `2026-07-28` `iss/resource/S256` 门禁的 authPolicyGeneration=2
5. 三平台/CLI 验收 OAuth、targeted reconnect、ToolSearch、capability gate、release-head gate
6. 单 profile 的 provider basis/auth/reconnect/tools-list/canary/同意页证据通过后，先上传内容寻址 profile/config 与 plugin ZIP，再发布更高序号 lock/head，最后按宿主已消费的真实 `latest` 合同切换 runtime，并在其后更新非权威 marketplace projection；只改该 profile
7. generation=2 管理面读到 catalog-publish 与 approved/未过期 verdict lock 后才显示 CTA；用户授权只影响当前 owner/connectionInstance，不反向控制全局 releaseDecision
```

旧客户端处理：

- generation=1 宿主安装 P0 新插件包后只读到 local-only stdio `.mcp.json`，看不到 remote 或 external-service stdio connector profile，因此不能绕过 blocker/lease；

- generation=1 已安装的旧插件副本仍含远程 `.mcp.json`，服务器无法远程改写；P0 支持口径固定要求升级插件并重启 CrabCode，宿主 targeted eviction 上线前不宣称热更已止血；
- 客服文案明确要求“升级插件并重启 CrabCode”；
- 旧 token 不自动迁移到新 client identity；
- 新宿主检测 fingerprint 变化后执行受控重授权；
- 连接器更新不静默扩大 scope。

`profileAuthorizationLeases` 按 connectorProfileId 升序且 ID 唯一，只能包含 catalog 中 `providerKind=third-party,providerInteraction=external-service,releaseDecision=publish`的 profile（remote 或 stdio）；每个此类 profile 必须恰有 1 条，local-only、first-party、catalog block 和 tombstone 必须 0 条。entry 的 profileId/profilePolicyFingerprint/ref/SHA/status/reason/notBefore/notAfter 必须与双签 ProviderEligibilityVerdict 逐字段一致，verdict ref/SHA 必须精确命中 `artifacts[]` 一个 `artifactKind=release-content,component=composition,visibility=public,validationAudience=release-and-runtime`的 primary/DR 双副本。`approved` 必须 `blockedReasonCode=null,leaseNotBefore<=issuedAt<leaseNotAfter`，`blocked` 必须 `blockedReasonCode=provider-app-approval-required`且两个 lease 时间为 `not-applicable`。有效第三方外部服务发布的实际判定是 `catalog releaseDecision=publish AND verdict=approved AND now<leaseNotAfter`；blocked/过期 verdict 只收回该 profile，不需改写 plugin/marketplace 字节。

`artifactKind` 只允许 `release-content|component-approval-evidence`，provider private evidence 禁止进入公开 lock `artifacts[]`。`visibility` 只允许 `public|release-private`，`validationAudience` 只允许 `release-and-runtime|release-validator-only`。`release-private` 必须对应 `release-validator-only`；public 产物默认 `release-and-runtime`。`providerVerdictKeySet.keySetId=sha256(JCS(["mcp-provider-verdict-keyset-v1",legal,security]))`，两个 team/keyId 必须不同；它由最终 lock 2-of-3 签名认证，变化时 signing component subject 必须变化。production lock 的 `environment` 只允许 `production`；`P0-0A-BOOTSTRAP` canary 使用独立 BootstrapCanaryEnvelope，不得出现在正式 head/chain。`issuedAt` 使用 UTC RFC 3339 且必须晚于前一 lock；全局 release lock 不设短周期 `validUntil`，避免签名/审批基础设施短时故障导致所有无关 provider 同时中断。只有 `providerKind=third-party,providerInteraction=external-service,releaseDecision=publish` 的 profile（remote 或 stdio）使用自身 provider eligibility verdict `leaseNotAfter`做运行时时效门；local-only 与 first-party 不进入该 lease 集合。lease 日期不得晚于私有 evidence 的 expiresAt/reviewDueAt，且不得晚于 verdict 签发后 30 天。某 profile lease 到期/提前撤销时只把该 profile 改为 `provider-app-approval-required`，关闭其 connection/capability，不改变其他服务。`releaseCandidateCoreSha256` 固定计算为 `sha256(JCS({schemaVersion,environment,lockPhase,lockSequence,previousLockSha256,issuedAt,catalogCommit,catalogSha256,bindingSnapshotSha256,releaseKeySetId,previousReleaseKeySetId,keySetTransitionRef,keySetTransitionSha256,thresholdPolicy,providerVerdictKeySet,artifactsWithoutComponentApprovalEvidence,crabCodeHost,acosmiBackend,marketplace,safeBaseline,previousApproved,profileAuthorizationLeases}))`，其中 `artifactsWithoutComponentApprovalEvidence` 只排除 `artifactKind=component-approval-evidence` 的条目。component approval 不统一签整个 core，而是签下述 component-specific subject；证据本身依旧不进入其 subject，随后最终 lock 再纳入 component evidence artifact digest，detached release threshold signature 覆盖完整 lock，不存在自哈希。

每个 ComponentApproval 的 `approvalSubjectSha256` 必须等于对应上式。任一 release-content artifact 的 role/component/artifactRef/runtimeMirrorRef/disasterRecoveryRef/sourceCommit/size/SHA/保留/成本字段变化都改变对应 subject，禁止只哈希 role 指针。subject 未变时允许在新 lock 中复用旧证据；subject 任一字段变化都必须重做 owner/approver 证据。必测 fixture 对 public plugin/marketplace/host 的 runtimeMirrorRef 各篡改 1 byte，必须导致对应 approvalSubjectSha256 变化且旧 component approval hard fail。纯 `profileAuthorizationLeases` 的 verdict artifact 必须标记 `component=composition`，因此只使 composition subject 变化，其他五个 component 只有在各自 subject 不变时才可复用。

owner/approver 证据均由企业私仓 protected-environment/OIDC attestation job 使用企业 IdP 主体产生，固定含 `{schemaVersion=1,approvalId,componentName,approvalSubjectSha256,reusable=true,decision=approve,actorTeam,actorId,actorRole,approvedAt,protectedEnvironmentRunId,issuer,keyId,signature}`。`ownerId/approverId` 使用企业 IdP 稳定不透明 subject ID，不使用姓名/邮箱，两者必须不同。release validator 先从 evidenceRef 取回并校验 SHA-256、OIDC attestation 公钥、actor team/role 及 approvalSubjectSha256；evidenceRef/SHA 必须与 `artifacts[]` 中一个 `artifactKind=component-approval-evidence`、`visibility=release-private`、`validationAudience=release-validator-only`、永久且有 DR 的 artifact 逐字节一致。复用时必须逐字节比对 componentName/approvalSubjectSha256/actor team/role，不得仅按 approvalId 复用。单纯填写 team 字符串不构成批准。

```text

  sequence=1 时 previousLockSha256=null；sequence>1 时必须指向前一 lock
  effective remote publish profile = 0
  effective external-service stdio profile = 0
  crabCodeHost.artifactRole = not-applicable
  acosmiBackend.artifactRole = not-applicable
  previousApproved.hostArtifactRole = not-applicable

  backendArtifactRole 必须指向 P0-1 后、CIMD 200 且未广告虚假 CIMD 的 safe backend
  previousApproved 两个 role 必须存在于 artifacts[]
```

首份 P0-0 lock 固定 `lockPhase=bootstrap,lockSequence=1,previousLockSha256=null`，它是 generation=2 宿主编译时钉住的 genesis lock，不引用 P0-1 前的旧 backend。P0-1/P0-2 验收后生成首份 `remote-capable` lock；若 genesis 后没有 bootstrap/rollback lock，它通常为序号 2，但机器规则固定为 `lockSequence=currentHighest+1,previousLockSha256=currentHead.lockSha256`，禁止写死序号 2。远程 profile 只有在 remote-capable lock 下才能 publish。此后每份 lock 序号恰好 +1 且 `previousLockSha256` 逐字节指向前一份；分叉、跳号或回指更旧 lock 均 hard fail。

首份 remote-capable lock 中，`crabCodeHost.artifactRole` 与 `previousApproved.hostArtifactRole` 都指向刚验收的 generation=2 safe host；`acosmiBackend.artifactRole` 指向 B=`cimd-enabled`，`previousApproved.backendArtifactRole` 必须指向 B approval 中三个 safe rollback 字段绑定的唯一 A=`metadata-safe` bundle，A/B 两个完整 bundle 都必须在该 lock `artifacts[]` 中且通过 primary/DR/内层 manifest 验收。A 无 CIMD 端点时宿主只能 fail-close，不得改走 DCR。后续 lock 才把 previousApproved 指向上一份 lock 的当前角色。

该快照只包含第 6.1 节安全基线：remote runtime=0、external-service stdio runtime=0、remote-dependent callable capability=0，且唯一可发布 MCP 为 `html-video` local-only stdio。`safeBaseline.marketplaceArtifactRole` 指向完整 76-entry marketplace JSON；与 `plugins-manifest.json` 比对时，marketplace 的 76 条只与 `marketplacePublished=true` 子集做 entry name/sourcePath/version/digest 双向差集，期望值为 0；两个 local-only 包只做包内 size/SHA 守恒，禁止要求它们出现在 marketplace。两个 safeBaseline role 必须在同一 lock 同时批准，禁止只回滚单个插件后继续使用旧 marketplace。


`signedAt` 使用 UTC RFC 3339，必须满足 `issuedAt<=signedAt<=issuedAt+15 minutes`；envelope 的 environment/releaseKeySetId/previousReleaseKeySetId/keySetTransitionRef/keySetTransitionSha256/thresholdPolicy/lockSequence/previousLockSha256/issuedAt 必须与取回 lock 逐字段一致。

envelope 另含 `signatures[{keyId,signatureAlgorithm=Ed25519,signature}]`；每个 signature 都对上述同一 RFC 8785 canonical payload 签名，正常发布必须有当前 releaseKeySetId 中 3 把 key 的至少 2 个不同 keyId 有效签名，重复 keyId 只计 1 个。`lockArtifactRef=https://updates.acosmi.com/crabcode/mcp-safe/<lockSha256>/mcp-release-lock.json`，`lockRuntimeMirrorRef=https://acosmi-mcp-safe-dr-us-west-2.s3.us-west-2.amazonaws.com/crabcode/mcp-safe/<lockSha256>/mcp-release-lock.json`，`lockDisasterRecoveryRef=s3://acosmi-mcp-safe-dr-us-west-2/crabcode/mcp-safe/<lockSha256>/mcp-release-lock.json`。detached envelope 以完全相同字节永久发布到 primary/public S3 mirror/private S3 DR 的内容寻址目录以及 `heads/<lockSequence>.json`，这些不可变对象固定 `Cache-Control: public, max-age=31536000, immutable`。再将同一字节 Put 到 `https://updates.acosmi.com/crabcode/mcp-safe/head.json`、`https://acosmi-mcp-safe-dr-us-west-2.s3.us-west-2.amazonaws.com/crabcode/mcp-safe/head.json` 和底层 primary/S3 object；所有 mutable `head.json` 的 origin/CDN/object metadata 固定 `Cache-Control: no-store`，每次 Put 必须生成新 object version，旧 head version 受 WORM 保留。宿主取 head 必须发送 request `Cache-Control: no-cache`，禁止使用 HTTP cache 的 stale head。宿主只编译内置 offline-root 公钥、初始 releaseKeySet、genesis lock SHA-256 和两个公开 HTTPS head locator，不内置对象存储凭据/不访问 private URI；当前 lock/envelope 禁止进入该 lock `artifacts[]` 所哈希的任何 plugin、marketplace、host 或 backend 产物，也禁止进入 root setup 包。

`.crabcode-plugin/mcp-release-lock.json`、`.crabcode-plugin/mcp-release-lock.detached.json` 和 `.crabcode-plugin/release-staging/provider-verdicts/*.json` 都是 catalog commit 完成后的 Git-ignored release staging 输出，不提交进 `catalogCommit`、不进入任何当前产物的 package include list，避免 Git commit/envelope/artifact 自引用并保持纯 lease 更新不改 plugin 字节。发布顺序固定为：公开 verdict/primary/AWS DR 与 lock/envelope 内容寻址字节全部上传并读回校验 → 更新 AWS head 并立即验证无认证 GET 返回新字节+`no-store` → 更新 primary 底层 object/CDN head 并立即从底层 object、`updates.acosmi.com` 各执行无认证 GET，两处都必须返回新字节+`no-store`。任一旧字节/错 header 即发布失败。

宿主并行尝试两个公开 HTTPS head，单次 GET 超时 5 秒、禁止 redirect、head 上限 64 KiB、lock 上限 2 MiB，不发送 cookie、Authorization 或任何 connector/user ID。两者都可用时，同序号不同 SHA 返回 `release-head-equivocation`；序号不同时只接受能通过 `previousLockSha256` 链回本地高水位（首次安装则链回编译内置 genesis）的最高有效序号。只有一个可用时可用该源，但仍必须验门限签名/验 SHA/验链；首次安装两源都不可用且没有编译内置 genesis 可用时返回 `release-head-stale`，remote 保持 blocked。runtime host 验证 envelope/lock 门限签名、每个成功取回的 lock size/SHA、前链、公开 artifact 和每 profile 的签名 eligibility verdict/lease；对 componentApprovals 只校验完整字段/evidence digest 被 lock 门限签名覆盖，不访问 private evidence。全部 runtime 适用项通过后，把 `{lockSequence,lockSha256,lastSuccessfulHeadCheckAt}` 原子写入 OS credential backend 的 `mcp2:release-lock-high-watermark`；安全存储不可用时所有 remote profile 保持 blocked。低于高水位、同序号不同 SHA、无法连回本地高水位/genesis 的 lock 均拒绝。合法回滚必须发布“更高序号 + 前链正确 + 指向 safeBaseline”的新 lock，不得重新接受旧 lock。

generation=2 control service 在应用启动、插件安装/更新、marketplace refresh、新建 remote connection 前尝试取回 head；存在任一 third-party external-service profile 时每 60 分钟做一次最佳努力刷新。公开两源短时失败时，已缓存且验证过的全局 lock 继续有效，不会因 Acosmi 控制面短时不可达关闭无关 provider。每个 `providerKind=third-party,providerInteraction=external-service` tool boundary（remote 或 stdio）都校验该 profile verdict `eligibilityStatus=approved`、`now<leaseNotAfter`、`verdict.profilePolicyFingerprint=catalog.profilePolicyFingerprint`，再校验当前 connection 的 authPolicyFingerprint 是由同一 profilePolicyFingerprint 与该用户实际 client/discovery 值按第 4.7 节生成；禁止要求 verdict fingerprint 与每用户 authPolicyFingerprint 相等。过期/撤销时只关闭该 profile 的 connection 与 dependent capability，返回 `provider-app-approval-required`。签名 head 是 release trust metadata，不包含 connector runtime config；connector catalog 仍只在 build-time 使用。新高序号 lock 一旦在在线客户端验证为 external-service effective publish=0，立即执行 exact connection/stdio process eviction；在线自动传播上界为 60 分钟。这只对 generation=2 宿主生效，generation=1 旧客户端仍必须升级。

external-service stdio 在 doctor/spawn/initialize 之前就必须通过上述 verdict/lease，禁止“先启进程再检查”。control service 对每个已 spawn 实例在 `leaseNotAfter` 设置本地 deadline timer，并在每 60 秒状态 tick 复核；到期/blocked 时即使用户没有调用工具，也必须先从 tools/resources/prompts/callable capability 注册表移除，再发送正常 shutdown，5 秒未退出则强制终止，清除该 process 的 credential injection 与连接缓存。验收必须证明“零 tool call 的后台 stdio 进程在 lease 到期时仍被 kill，此后零 provider 网络请求”。

这是明确的可用性/撤销取舍：同时阻断 primary 与 AWS 直接 head 的攻击者可以让已安装客户端暂时看不到新 rollback lock，但无法降低本地 lock 高水位、伪造 2-of-3 签名或延长任一第三方 profile 已签名的最长 30 天 lease；所以这不把 Acosmi 短时控制面变成新的全局故障点。当前目标集不允许 first-party remote publish；未来若新增，必须引入同等 per-profile safety lease，否则构建 hard fail。

profile authorization lease 由 Acosmi ops 调度器每日 00:15 UTC 逐 profile 检查，不使用已停的 GitHub nightly。D-7 由 `provider-integrations`负责获取/复核新证据、`legal` 与 `security` 签发新 eligibility verdict，通过更高序号 lock 更新该 profile lease；D-3 仍未更新时向 `provider-integrations-approver|legal|security|support` 升级；D-1 仍无有效 verdict 时，更高序号 lock 只把该 profile 转为 block 并提前通知用户；D0 即使新 lock 未及发布，runtime 也按已签名 `leaseNotAfter` 只关闭该 profile。纯 lease 更新不改 plugin/marketplace/host/backend/signing artifact digest；这些未变 component 的审批证据可按下述 component-specific subject 复用，只重做 provider/legal/security verdict、`lock-composition` owner + `marketplace-approver` approver 的 composition 证据与 release 2-of-3 签名。

必测：两个 profile 的 leaseNotAfter 分别到期只影响对应 profile；D-7/D-3/D-1/D0 状态转移；纯 lease 更新的未变 component approval 复用和 composition 新审批；公开 head 双失败时已缓存 lock 继续工作，但过期 profile lease 仍按本地时钟 fail-closed。

`releaseKeySetId=sha256(JCS(["mcp-release-keyset-v1",keySetSequence,thresholdPolicy,sorted([{keyId,algorithm=Ed25519,publicKey}])]))`，普通 lock 固定 `previousReleaseKeySetId=null,keySetTransitionRef=null,keySetTransitionSha256=null`，其 envelope 的有效 keyId 只能属于 releaseKeySetId 且必须 2-of-3。key set 变更使用下列互斥 union：

```text
ReleaseKeySetUpdate common:
  schemaVersion=1
  mode=normal | recovery
  keySetSequence
  previousKeySetSha256
  newReleaseKeySetId
  newPublicKeys[3]
  thresholdPolicy=2-of-3
  activateAtLockSequence
  issuedAt

normal:
  currentKeySignatures[>=2 distinct current keyId]
  newKeyProofSignatures[>=2 distinct new keyId]
  offlineRootSignature=forbidden
  recoverySecurityEvidenceSha256=forbidden
  recoveryReleaseEvidenceSha256=forbidden

recovery:
  currentKeySignatures=not-applicable
  newKeyProofSignatures[>=2 distinct new keyId]
  offlineRootSignature=required
  recoverySecurityEvidenceSha256=required
  recoveryReleaseEvidenceSha256=required
```

normal 用于仍可取得当前 2-of-3 的常规轮换，只需当前 2-of-3 授权 + 新 2-of-3 持有证明，offline root 明确禁止使用。recovery 只在两把当前 key 均已由 `security` 与 `acosmi-release` 两份 IdP+WORM 证据确认永久不可恢复或已妥协时使用；短时 HSM/网络/人员不可用不属于 recovery 条件。offlineRootSignature 对 `JCS(["mcp-release-keyset-update-recovery-v1",updateWithoutSignatures])` 签名。recovery 还必须由 `security` 与 `acosmi-release` 两个不同 IdP subject 分别批准，证据写入 private WORM，公开 update 只携带两份 SHA-256；release validator 取回/验签证据，runtime host 依据 offline-root 签名与证据 digest 字段接受 recovery，不访问 private URI。

过渡 lock 固定 `releaseKeySetId=newReleaseKeySetId,previousReleaseKeySetId=当前 set,keySetTransitionRef=<ReleaseKeySetUpdate public artifact>,keySetTransitionSha256=<update raw bytes SHA-256>`，ref/SHA 必须命中 `artifacts[]` 中公开 release-content 的 primary/DR 双副本。normal 过渡 envelope 必须同时携带旧 2-of-3 和新 2-of-3；recovery 过渡 envelope 不要求已丢失的旧签名，但必须携带新 set 2-of-3，且 keySetTransitionRef/SHA 的 recovery update/offline-root/双人 evidence digest 全部通过。下一 lock 才恢复 previousReleaseKeySetId/keySetTransitionRef/keySetTransitionSha256=null 并只接受新 set 2-of-3。单 key 丢失/泄露时由其余 2 把走 normal；recovery 完成后必须将事件/证据写 WORM 审计并更换 root 保管介质。旧的已验签 lock 在新 key set 生效前保持可用。

ReleaseKeySetUpdate 必须先于过渡 lock 发布到两个内容寻址 locator：`https://updates.acosmi.com/crabcode/mcp-safe/keysets/<newReleaseKeySetId>/<keySetTransitionSha256>.json` 和 `https://acosmi-mcp-safe-dr-us-west-2.s3.us-west-2.amazonaws.com/crabcode/mcp-safe/keysets/<newReleaseKeySetId>/<keySetTransitionSha256>.json`。宿主遇到未知 releaseKeySetId 时只从已被 envelope/lock 覆盖的 keySetTransitionRef 与对应 AWS locator 取回（禁止 redirect，上限 64 KiB），先校验 raw SHA=keySetTransitionSha256、newReleaseKeySetId 按公钥集重算一致、keySetSequence 恰好 +1、previous hash 与 activateAtLockSequence；`mode=normal` 要求 offlineRootSignature 禁止，并校验当前 2-of-3 + 新 2-of-3；`mode=recovery` 才校验 offline-root 签名、新 2-of-3 + security/acosmi-release 两份 evidence SHA/结构字段，明确不要求当前门限。只有对应 mode 全部通过才将 `{keySetSequence,releaseKeySetId}` 写入 OS credential backend 高水位。低序号、断链、mode 外字段、未达对应门限或未到 activateAtLockSequence 的 set 一律拒绝。

每个 componentApprovals 子项的 ownerTeam/approverTeam 都必须命中 canonical team map 且不相等，ownerId/approverId 不相等，两份证据的签名、SHA、actor role/team 和 approvalSubjectSha256 全部通过；6 个子项全部有效后 lock 才生效。任何产物 digest 与 lock 不一致时发布立即失败。

### 8.2 回滚触发与执行

以下任一条件触发安全回滚：

```text
blocked/tombstoned profile 被物化为 runtime config
generation=2 对 legacy remote .mcp 发出网络请求
credentialOwnerId 交叉隔离测试命中同一 key
secret/token/code/state 出现在文件、日志或错误响应
发布资产 digest 与 release lock 不一致
同一 certified profile 在两个独立 clean fixture 中均出现 OAuth terminal=success 但 targeted reconnect 未达到 ready
```

事故分类必须在 15 分钟内由 `qa-release`记录为互斥二选一：

```text
connector-path:
  provider/profile/catalog/endpoint/canary/backend 故障
  且 release-head verifier/control-service/eviction/updater 两个 clean fixture 均通过

host-trust-path:
  release-head 验签/取回/高水位/eviction、control service、credential index 或 updater 任一被怀疑
  不允许使用 connector-path 的“先等新 lock”假设
```

`connector-path` 固定执行：

1. `plugin-platform` 先从 primary/DR 取回已批准 78-package safe baseline，对 76 个 `marketplacePublished=true` package 执行与 host-trust-path 相同的 `safeRepackVersion=nextPatch(maxSemVer(事故广告版本,已广告最高版本))`，只改版本/缓存元数据；2 个 local-only 包保持原 safe baseline 字节与 `marketplacePublished=false`。重新生成 78-entry plugins-manifest 和 76-entry marketplace，上传新内容寻址 snapshot/package/marketplace 但暂不切 pointer；
2. 事故涉及 backend 时，由 `acosmi-ops` 执行、`acosmi-release` 批准，按“`/opt/acosmi/releases/<previousApproved-bundle-sha256>/` 已复验只读缓存 → `previousApproved.backendArtifactRole` primary → DR”的唯一顺序取得首个通过 bundle/manifest/version 验证的完整目录，停止服务后原子将 `/opt/acosmi/nexus-backend/current` 切到该目录，重启并验 health/两份 AS metadata；current 与 previousApproved 两个 release 目录在对应 lock 可回滚期内均禁止 cleanup。禁止逐文件恢复、恢复 `client_id_metadata_document_supported=true` 或混用不同 bundle 的 binary/library。三个来源都失效时保持服务停止并进入 P0 incident，不运行半部署字节。事故不涉及 backend 时不改线上 backend；
3. `lock-composition` 在第 2 步完成后以当前已接受 lock 为前驱生成 `lockSequence+1` rollback lock：`previousLockSha256` 精确指向事故 lock，catalog/binding snapshot 固定 remote/external-service stdio effective publish=0、remote-dependent callable capability=0，`safeBaseline` 两个 role 指向第 1 步新 safe-repack 字节，host 记录当前字节；事故涉及 backend 时 `acosmiBackend.artifactRole=previousApproved.backendArtifactRole` 并与第 2 步已恢复线上 bundle 一致，不涉及 backend 时才沿用事故 lock 的当前 backend role。重做变化 subject 的 component approvals 与 2-of-3 签名，先更新 AWS DR head、后更新 primary head；
4. `qa-release` 在 generation=1/2 clean fixture 先验证事故版本→safeRepack 会重新取包，再在两个 generation=2 fixture 显式刷新 primary/AWS head，验证已接受新序号、旧 remote connection 已驱逐、remote runtime/callable 都为 0，并在 backend 事故时断言 lock role=线上完整 bundle role；
5. 验收后用现有镜像工作流先上传 76-entry safe-repack `<sha>.zip` 与 `<sha>.zip.sha256`，公网读回逐字节比对，再复核远端 main/当次 SHA，然后单文件切换 `https://updates.acosmi.com/crabcode/plugins/crabcode-plugins-official/latest`。该步是 generation=1/2 runtime 唯一线性化点。切换后才更新非权威 `marketplace.json` projection 及其 checksum；projection 不一致则整体审计 blocked，但不得将 projection 当 runtime pointer，也不得用新 projection 宣称旧 `latest` runtime 已升级。`latest` 必须符合宿主 `no-cache` 合同，ZIP 为 `immutable`。generation=1/2 clean fixture 必须取得新 ZIP，安装、重启后 remote=0。在 `latest` 切换前任一步失败均不切 pointer；本流程不创建第二套 marketplace pointer，也不改桌面应用 `updater/latest.json` schema。

`host-trust-path` 固定执行：

1. 立即绕过故障 verifier：`plugin-platform` 从已批准 `safeBaseline.pluginArtifactRole` 取回 78-package 安全快照，不读事故 catalog；对 76 个 published package 使用 `safeRepackVersion=nextPatch(maxSemVer(当前事故 marketplace 版本,已广告最高版本))`，只改 manifest/marketplace/package/serverInfo/dist/cache-key 版本元数据，其余文件必须与 safe baseline 内层 SHA 一致；2 个 local-only 包保持原字节。生成新 78-entry plugins-manifest 与 76-entry safe-repack marketplace，经 `plugin-platform` owner/`marketplace-approver` approver 和 generation=1/2 旧版本→safeRepack clean update 验收后，沿现有独立 marketplace 链先上传内容寻址字节、后切换 pointer。该分支是“新 rollback head 前不切 pointer”的唯一例外，禁止把旧 safe SemVer 直接回指当成已安装用户回滚；
2. `provider-integrations` 冻结/撤销所有 Acosmi 控制的 provider app/client 并停止新授权；BYO app/token 不受 Acosmi 控制，无法伪称已中央撤销，由 `support` 立即通知用户 disconnect/revoke，并在后续 hotfix 中强制旧 profile/credential legacy；
3. 禁止 SemVer 降级；`crabcode-mcp` 以 `previousApproved.hostArtifactRole.sourceCommit` 为基线，只合入 fail-close/verifier/control-service 修复，生成从未发布且严格大于事故版本的 SemVer patch hotfix，完成签名/公证和三平台测试；旧 binary 只用于取证/离线 fixture；
4. updater 与 plugin update 未被怀疑时，hotfix 按当前真源分发：CLI/TUI 使用 `.github/workflows/release-pipeline.yml` 及 `src/utils/autoUpdater.ts`/`src/cli/update.ts` native updater；macOS Electron/Chromium GUI 使用 `.github/workflows/release-gui-mac.yml`；Windows Electron/Chromium + NSIS 使用 `.github/workflows/release-windows-cross-repo.yml`，且只由其 finalizer 在全部三平台资产验签后生成/发布 `updater/latest.json`。Tauri/WebView2 退役宿主禁止作为正式回滚路径。safe repack 独立走 marketplace update。任一相应 updater/finalizer 也被怀疑时，第 1 步对已安装用户只能保护之后能成功刷新的实例，禁止声称已完成全量止血。此时只发布新签名/公证的全量安装包及 SHA-256，`support` 要求用户手动升级，禁止继续声明旧宿主/插件已修复；
5. 两个 clean hotfix fixture 在 primary/AWS head 各独立测试通过后，才生成/发布更高序号 safe rollback lock，引用 hotfix artifact 并驱逐旧 remote。

两个分支共同执行：每次回滚把 `{rollbackId,incidentClass,trigger,incidentLockSha256,rollbackLockSha256|null,lockSequence|null,artifactRoles,executorTeam,executorId,approverTeam,approverId,startedAt,completedAt,result}` 作为同一原始字节双写到 `oss://acosmi-private-release-evidence-cn-hangzhou/rollback-audit/<YYYY>/<rollbackId>.json` 和 `oss://acosmi-private-release-evidence-dr-cn-shanghai/rollback-audit/<YYYY>/<rollbackId>.json`，分别读回并记录两个 ref、同一 size/SHA、object version ID，WORM retention=7 年；仓内只记 audit index URI/SHA，不记 actor 原文。不从当前 catalog 临时重算，不恢复退役、供应商专属、Claude 托管或 example endpoint。

回滚原则：

1. Acosmi 回滚不触发宿主改用 DCR；连接器进入 `cimd-document-unavailable`；
2. CrabCode 回滚时 marketplace blocker 不解除；
3. 插件 endpoint 回滚不得恢复 Asana SSE、HubSpot `/anthropic`、Claude 托管端点或 example URL；
4. auth policy 回滚不复用 generation=2 token；
5. token 撤销失败不输出 token 内容。

- 不把 provider basis、合同/批准原文、provider reviewer/provider private locator 或可枚举的低熵集合 hash 发布到 Git/公开 lock；
- 不把 LSP 伪装成 MCP；
- 不在 MCP 启动窗口安装依赖或下载浏览器/镜像；
- 不强制把 PHP、Docker、项目 CLI 打包进插件；

- 不放宽 `mediaops` 主体分离；

## 14. 最终收口标准

| 层 | 当前裁决 | 收口标准 |
| --- | --- | --- |
| 公网端点 | 只有可达性聚合，不能称整体健康 | 每个 publish profile 有逐阶段 pass 证据 |
| 官方镜像 | Git main 安全但 `latest` 仍为止血前提交 | exact-main manual CI → manual publish → manual audit；`latest/<sha>.zip/.sha256/marketplace` 逐字节闭环，旧→新安装并重启后 remote=0 |
| CIMD | 404；回调合同不闭合 | 公网固定 JSON 200 + 候选 portless loopback 策略 + OS-assigned 实际端口 + Notion/Linear/Canva/Synapse 各自证明 RFC 8252 port exception/同意页风险提示/真实授权 |
| Acosmi AS | 虚假广告 CIMD | 两份 metadata 不再广告未实现能力 |
| OAuth UI | transport 推断产生死 CTA | canonical auth profile/nextAction 驱动 |
| OAuth 完成 | 只显示 success；方案漏 MCP `2026-07-28` wire 门 | RFC 9207 `iss` + RFC 8707 双请求 `resource` + AS metadata `S256` + exact eviction/reconnect/tools-list |
| 凭据迁移 | 旧 client/token 可被复用 | generation/fingerprint 隔离并受控重授权 |
| 无登录远程 | 0 个 production-approved 完整正例 | 供应商资格 + 固定 canary 同时通过 |
| 第一方 sidecar | 进程健康，身份/错误语义未闭合 | mediaops 模式和结构错误验收通过 |
| LSP | 12 个伪 MCP | MCP 声明归零；LSP 产品化独立验收 |
| 频道 | 运行时安装且配置缺失 | 自包含发行、secret/平台 doctor 完成 |
| 第三方 wrapper | 外部依赖未闭合 | 固定版本、spawn 前 doctor、无启动时下载 |
| ToolSearch | 逻辑别名缺失 | 私有 alias index、碰撞 fail-closed |
| 门禁 | warning 可掩盖确定故障 | static hard gate + release profile evidence |

真正完成不是“更多行显示 connected”，而是每个被发布的 connector profile 都能走完整条可解释、可复现、可回滚的链路。任何未通过项都必须以精确 blocker 呈现；默认保持不可激活，禁止回退成“登录失败”“条件健康”“待确认”或“稍后处理”。
