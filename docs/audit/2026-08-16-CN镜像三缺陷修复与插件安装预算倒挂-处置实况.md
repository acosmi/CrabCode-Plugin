## 2. 镜像三缺陷 —— 同一个形态的三次重复

三条判据是审计器 `07c8316`（2026-08-14 *"make CI and mirror health fail closed"*）**一次性**加严的，
而发布器 `acosmi/crabcode-source::sync-plugins-to-mirror.yml` **一条都没跟**。这叫**契约单边升级**：
审计侧变严、发布侧不知情，于是镜像即便新鲜、即便校验和齐备，仍**结构性不可能通过审计**。

| # | 缺陷 | 实测证据 | 修法 |
|---|---|---|---|
| 1 | 指针陈旧 | 镜像 `latest` = `e6a457b`（07-27），main 已到 `988b228`（08-14）。发布器上次成功运行 = 2026-07-27，与指针日期逐条吻合 | 根因是 07-27 为省 Actions 额度**移除了 schedule 轮询**，而 `MIRROR_DISPATCH_TOKEN` 是**故意不配**的（公仓→私仓横向提权，撞红线）⇒ 同步已是纯手动，无人手动跑。本轮手动跑通 |
| 2 | 两个 `.sha256` 缺席 | 两者 404；正向对照：同目录 `latest` / `marketplace.json` / `<sha>.zip` 均 200，证明不是路径写错 | 发布器补产，与各自载荷同一次 rsync 上传 |
| 3 | zip 含裸 `marketplaces/` 目录项 | 审计器报 `unsafe archive entry: marketplaces/`。下载线上两代 zip 复核：`e6a457b`（2599 条）与 `988b228`（2684 条）**都只有这一条**越界项 ⇒ 自镜像上线起一直如此，非本轮引入 | 打包目标由 `marketplaces` 改为 `marketplaces/crabcode-plugins-official` |

### 2.1 缺陷 3 的实测对照（Info-ZIP 3.0）

```
zip -ry … marketplaces                           → 越界项 ['marketplaces/']   FAIL
zip -ry … marketplaces/crabcode-plugins-official → 越界项 []                  PASS
```

其余条目逐条相同。它违反的是**发布器自己声明的布局契约**（「zip 内所有文件前缀 =
`marketplaces/crabcode-plugins-official/`」），所以修发布侧而不是放宽审计侧。

### 2.2 自检判据也一并换了 —— 它照不到自己的 bug

发布器原有自检是：

```bash
unzip -l "${SHA}.zip" | grep -q "${ARC_PREFIX}/" || 报错
```

它问的是「**至少有一条**带前缀吗」，而契约是「**每一条**都带前缀」。在「有越界项」与
「无越界项」两种状态下，这条命令给出**同一个答案** —— 所以它在缺陷 3 存在的整段时间里
一直是绿的。已改为按审计器的真判据（全称量词）逐条校验，空 zip 也失败。

同理，`Verify URLs` 步骤原先只断言 `latest` / `<sha>.zip` 两个 URL 返回 200。只断言 200
等于只证明「有个文件在那」—— 发布器写错格式或写错内容时它照样 200，然后由公仓审计器在
几小时后才红，那时已无人在场。现把审计器的两条判据（正则形态 + 摘要匹配真实字节）
**前移到发布当场**。

### 2.3 一个差点踩中的平台陷阱

`sha256sum` 的分隔符**随平台变**：

| 平台 | 输出 | 是否合审计器正则 `([0-9a-f]{64})  ([A-Za-z0-9._-]+)\n?` |
|---|---|---|
| POSIX（文本模式，runner） | `<hash>␠␠<file>` | ✅ |
| Windows / MSYS（二进制模式） | `<hash>␠*<file>` | ❌ |

runner 是 ubuntu 故**当下恰好对**，但「靠平台默认值恰好对」正是换执行池那天静默变红的形态
（对照主仓 §硬约束 #6 铁律 4 的 `runner_pool` 可切换）。发布器已改为只取第一字段、再用
`printf` 显式拼装，与平台无关；本机（二进制模式，更严苛的一侧）实测产出合规，
且原生 `sha256sum` 输出在同一判据下判不合规（负向对照成立）。

## 3. 新发现：官方市场安装的跨语言预算倒挂

**用户实拍报错**（中国区）：反复安装数次才成功，失败时提示

```
安装失败: agent loop: worker.marketplace/add failed:
agent loop: worker.marketplace/add: control worker call timed out after 30s
```

### 3.1 这**不是**「镜像坏了所以退回 git」

诊断期间镜像一直是 200 可达的（只是内容陈旧），所以「镜像不可用 ⇒ 走 git 兜底」这条
因果链**不成立**。真因在预算层：

| 层 | 位置 | 事故时的值 |
|---|---|---|
| 外墙 | `acosmi-app-server/src/dispatcher/marketplace.rs::CONTROL_WORKER_CALL_TIMEOUT` | **30s** |
| 内层 · zip 下载 | `src/utils/plugins/officialMarketplaceGcs.ts` `timeout: isLatest ? 10_000 : 60_000` | **60s** |
| 内层 · latest 指针 | 同上 | 10s |

**内层 zip 预算是外墙的两倍** ⇒ 那道 60s 看门狗**结构上永不可能触发**；任何耗时超过 30s 的
安装都死在外墙上，而外墙的文案对用户零信息量。

更糟的是外墙触发会 `mark_control_worker_unhealthy()` ⇒ 下次调用换一个新 worker ⇒
**下载从零重来、无断点续传**。用户侧表现就是「反复装好几次偶尔才成功」——
与实拍描述逐条吻合。

### 3.2 余量实测：本来就很薄，今天还变薄了

| 事实 | 值 |
|---|---|
| 镜像 zip（`e6a457b`，07-27） | 10,328,423 B |
| 镜像 zip（`988b228`，今天） | 15,134,410 B（**+46.5%**） |
| 本机（良好链路）下载耗时 | **22.9s**，661 KB/s = 30s 预算的 76%，**尚未包含解压与校验** |

⇒ 把镜像修新鲜这件事本身，**让这个超时缺陷更容易被触发**，必须一起修，不能只修一半。

### 3.3 同一个不变式，本仓已经栽过两次

`docs/audit/2026-07-25-crabcode-html-video-…-审计与实施方案.md` §F3 记的是同一件事：

> **F3 嵌套超时倒挂：外层预算 < 内层预算（已确认 2 处）**
> 后果不是挂死，而是：**内层那个参数是死配置**，且用户看到的错误永远是
> `render wall timeout`，而非「第 N 段超时」，定位信息丢失。

换个子系统、换批作者，同一个不变式第三次被违反。该文当时就写明修法要「补一条测试守住
外层 ≥ 内层」—— 但那条测试只守住了 `crabcode-html-video` 自己的两处。

### 3.4 修法（已落地于 `acosmi/crabcode-source` main）

1. 按「是否触网」拆常量：`remove`（本地缓存写）保持 30s；`add` / `upgrade`
   （镜像下载或 git clone）用新的 `CONTROL_WORKER_NETWORK_CALL_TIMEOUT = 180s`。
   定值依据：latest 10s + zip 60s + 解压校验（2684 条目，Windows 上受杀软影响）
   ≈ 最坏 100s 量级，180s 给足余量且仍有界。
2. 新增**跨语言**闸门 `tests/unit/marketplace-install-budget-inversion.test.ts`：
   同时读 Rust 与 TS 两个文件，断言 `外墙 ≥ 内层合计 + 60s 余量`，并钉死三个臂各自
   用哪个常量。
   - **为什么必须跨语言**：事故前这两个数字一个在 Rust、一个在 TypeScript，各自看都很合理
     （30s 是稳妥的 RPC 墙钟；60s 是稳妥的大文件下载预算），**没有任何一处代码或测试
     同时看着它们**。单侧测试再多也照不到这条不等式。
   - 闸门做过变异测试：把外墙改回 30s → 红；把 `add` 换回短常量 → 红；还原 → 全绿且文件
     逐字节一致。**绿本身不证明闸门有区分力，变异才证明。**

## 4. `rescue/html-video-audit-62b0125` —— 诊断的判断需要修正

诊断 §2.1 写它「只存在于本机，机器故障即永久丢失」。**该判断不准确**：

- main **有同路径文件**，只是 blob 不同（`7d697a9a` vs `3ac7a5e1`）。
  诊断当时用的 `git rev-parse` 命令因中文路径被 git 转义而没解析成功，
  两条判据（"main 中不存在" / "blob 不同"）都不可信 —— 需 `-c core.quotePath=false`。
- 逐行比对：main = 316 行「状态：**已实施**」，rescue = 200 行「状态：立项存档，尚未实施」。
  rescue 的 39 行独有内容（跨插件同形表 / F3 段 / 批次 A·B·C / 验收标准）在 main 中
  **逐条保留并更新**；main 另有实施期间新发现的 F3b 段，以及「正文中会误导的两处已就地订正」。
- ⇒ rescue 是 main 的**真子集**且含已知会误导的旧措辞，保留价值为负。已删除本地分支
  （commit 仍可从 reflog 取回 90 天）。

## 5. 复算命令

```bash
M=https://updates.acosmi.com/crabcode/plugins/crabcode-plugins-official

# 镜像四件套（全 200；负向对照：陈旧 SHA 的校验和仍应 404）
for f in latest marketplace.json marketplace.json.sha256; do
  printf '%-26s %s\n' "$f" "$(curl -s -o /dev/null -w '%{http_code}' "$M/$f")"; done
L=$(curl -fsSL -H 'Cache-Control: no-cache' "$M/latest")
curl -s -o /dev/null -w "$L.zip        %{http_code}\n"        "$M/$L.zip"
curl -s -o /dev/null -w "$L.zip.sha256 %{http_code}\n"        "$M/$L.zip.sha256"
curl -s -o /dev/null -w "e6a457b….zip.sha256 %{http_code} (期望 404)\n" \
  "$M/e6a457b72a5900b1314b292edeb88d036091b436.zip.sha256"

# 指针 == 插件仓 main == 最新绿点
[ "$L" = "$(git ls-remote https://github.com/acosmi/CrabCode-Plugin.git main | cut -f1)" ] && echo "✓ 指针 = main"
gh run list -R acosmi/CrabCode-Plugin -w ci.yml -b main -L 1

# zip 无越界条目（期望 []）
curl -fsSL -o /tmp/m.zip "$M/$L.zip" && python3 -c "
import zipfile;z=zipfile.ZipFile('/tmp/m.zip')
print([n.filename for n in z.infolist() if not n.filename.startswith('marketplaces/crabcode-plugins-official/')])"

# 权威判定
gh workflow run notify-mirror.yml -R acosmi/CrabCode-Plugin
```
