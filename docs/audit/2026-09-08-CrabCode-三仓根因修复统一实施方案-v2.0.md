### 1.3 已统一纠正的归因

| 旧说法或容易误读的点 | 本版唯一采用的口径 |
|---|---|
| 市场找到插件就是 MCP 发现成功 | 市场可见、Skill 可读、服务配置存在、握手、工具目录、业务执行、产物交付分别记录 |
| 撤掉安全暂停就能恢复 | 暂停有意收缩发布面；缺身份/兼容/真实执行证据时不能恢复 |

| 法律必须新增 MCP 服务 | 法律主要是 Skill/Agent 与 Python 工作台，不以新增服务作为修复前提 [PLAW] |

| 非零退出一定被静默计成功 | bridge 失败分支会返回 Go error；确认的问题是不可用时的成功占位，另补映射器防御测试 [GBRIDGE] |
| 直接 RPC 格式问题就是主聊天唯一根因 | Rust 有真实消费者，但 GUI facade 注释称其非默认主对话路径；应逐入点确认 [HRUSTINVOKE] [HGUI] |
| 固定返回一个协议版本必然违规 | 对 2025 支持集，支持请求版本须返回该版本；不支持时允许返回自己支持的其他版本 [MLIFECYCLE] |
| 本地稿件必须云登录，或单人等于独立多人复核 | 纯本地低保证编辑与云授权分离；授权代理执行也不等于真人亲自审阅 |
| Currency Watch 已过 90 天 | 2026-06-20 至本审计日期未过 90 天；总日期不能证明每条法源的适用性 [LCURRENCY] |
| 媒体 manifest 没有 agents 字段，便没有子代理 | 已读取根 agents 目录，必须结合默认目录加载规则判断 [PMEDIADIR] |

这些纠正项应进入对照测试，避免新修复把现有正确行为误改。

## 2. 统一设计决策、协议基线与厂商参考

### 2.1 本轮目标与优先级

目标只有四类：**调用与失败真实、领域数据可靠、最小任务确实交付、故障有边界地恢复。**不以卡片数量、Skill 数量、握手或绿色状态代替业务结果。

优先级按能力定义：`P0-common` 保护实际共享的调用/权限/数据边界；`P0-media`、`P0-law`、`P0-cloud` 分别是对应能力开放前的阻断。共同边界只影响实际经过它的能力，不把所有错误都扩大成三仓统一停机。`P1` 是同批闭环，`P2` 是不影响当前保证的质量、覆盖或性能增强。具体测试分组见第 13 节。

| 决策 | 本轮选择 | 偏离该选择需什么证据 |
|---|---|---|
| 本地媒体/法律是否等待云聚合 | 不等待；模型推理和研究所需联网另行申明 | 实际调用 trace 证明该任务确实依赖聚合 |
| 云端聚合还是按 ID 通用代理 | 先修已有 `/api/v4/mcp`；不把第三方 ID 改写为聚合 | 已部署代理的真实消费者、路由与授权映射 |
| 恢复哪些 MCP | 媒体一个合格的第一方配置；其余保持各自状态 | 每个连接器独立的启动、授权、调用、错误和撤销证据 |
| 法律是否立即换数据库 | 先修小范围锁/创建/一致性问题 | 文件提交协议复杂度或实测并发已使成熟数据库更简单 |
| 是否引入新的执行描述 | 先验证既有准入/版本分发；不足才用薄过渡适配 | 被支持旧宿主实际可误执行的版本测试 |
| 是否全面启用 2026 MCP | 不作为恢复前置；有明确兼容需求才单独纳入 | 固定 SDK、支持产品及新协议安装链证据 |
| 是否新增全部厂商 hosted MCP | 不新增未在用的接入路线 | 产品承诺或真实使用场景与所需授权边界 |

### 2.2 三层规则不能互相冒充

**MCP 官方规范**约束固定版本的消息与传输/授权语义；**厂商文档**约束一个具体 API 或客户端的接入子集；**CrabCode 产品政策**约束本项目的暂停、专业复核、发布、数据隔离。论文、产品宣传和其他客户端的“跳过确认”选项都不替代这三类合同。

公开来源已经在本轮重新访问，详见正文引用与末尾“官方资料”。仅访问官方页面并不代表跑过厂商真实账号或产品兼容测试。

### 2.3 四种版本分开记录

| 版本维度 | 写入验收记录的信息 |
|---|---|
| MCP 协议 | 实际支持/协商的版本、transport、可选能力；不只写“支持 MCP” |
| SDK | 真实 lockfile 的包名与精确版本；源码声明范围不是安装事实 |
| 模型接口 | provider、API family、实际模型/接口版本、需要的 beta 标识、MCP 执行者 |
| 插件业务数据 | manifest/profile、内容/来源/案件 schema、渲染与 QA policy 版本 |

当前被审计网关常量是 `2025-11-25`，不能据此推断三个仓所有客户端或依赖都同版。[GTYPES]

官方 `2026-07-28` 文档改变了初始化方式：去掉旧握手，以 `server/discover` 和逐请求协议信息工作；结果、缓存与交互续接也有变化。因此旧 initialize、会话和初始化通知测试只用于对应旧版本支持集，不套到新版本。**本轮仍以原有 2025 路径修复为默认，不因新版本存在就手写双协议栈。**[MCURRENT]

官方 TypeScript SDK 迁移资料说明，v2 的新协议行为需显式启用；升级依赖包不自动等于更换协议。实施先锁定候选 SDK，读取其迁移说明，再测试实际 wire 行为；不能直接复制在线最新版示例到旧依赖。[MMIGRATION]

| 支持清单 | 实施与验收边界 |
|---|---|
| 2025 既有路径 | 校验声明支持的版本、初始化、通知、目录、工具结果及所用可选能力；不新增未需要的 sampling/tasks/prompts 能力 |
| 2026 可选路径 | 只有明确纳入后启用专用合同测试；不得将“收到服务器业务请求”当旧握手，也不得把未完成的交互结果当业务终态 |
| 自定义 transport/IDE | 保留现有范围，单独检查调用入口与安全策略；不是因为实现文件同名就强行迁移 |

### 2.4 OpenAI、Anthropic、Google 的产品级对照

| 官方资料与访问结论 | 对本方案的采用方式 | 不照抄的部分 |
|---|---|---|
| OpenAI Responses MCP/Connectors 区分目录、调用及审批事件，远程接入覆盖 Streamable HTTP 与 HTTP/SSE [VOPENAI] | RC-04/05 保持厂商事件与原始 MCP 结果分层；本地执行和 hosted 执行只选一个负责人 | 不把 API 的审批事件当法律/编辑独立审核；不重复执行 hosted 已执行动作 |
| OpenAI Codex 的 MCP 配置有服务器、工具和超时控制 [VCODEX] | 复用既有配置与生命周期；启动、授权和业务执行预算分开 | 不为了模仿配置文件再建一个管理系统 |
| Anthropic Messages MCP connector 面向工具调用，远程 HTTP 服务可用，本地 STDIO 不能直接接入；token 获取和更新由接入方处理 [VANTHROPIC] | 明确 toolset/server 对应、授权归属和错误续轮；本地媒体继续由 CrabCode client 调用 | 不把 mediaops 命令塞进 mcp_servers 就宣称接通；云 connector 不等于 Claude Code |
| Claude Code 区分配置作用域及不同运行模式 [VCLAUDECODE] | 验证项目/用户/受管配置与非交互行为，不能用显示名代替信任来源 | 不照抄某运行模式跳过确认作为产品默认 |
| Google Gemini Interactions Remote MCP 文档要求 Streamable HTTP，且有服务器命名约束 [VGOOGLE] | 实际使用该 API 时测试 transport 和无碰撞名称映射；保留服务原始名 | 传统 HTTP+SSE 服务在别处可用不等于该接口兼容；Streamable HTTP 内的 SSE 响应与传统 SSE transport 不混淆 |
| Gemini CLI 区分发现/执行并提供工具与环境配置 [VGEMINICLI] | 采用最小环境暴露和分阶段状态；验证显式配置的凭据来源 | 不复制全信任开关，不把 CLI 能力反向算成 hosted API 能力 |

上述对照不是“三家全兼容”的承诺。落地支持表必须写明 `provider + API family + model/SDK + MCP executor + transport + 验收结果`。如果当前使用普通 function calling，厂商 hosted MCP 仅作参考，不增加无实际消费者的开发分支。

### 2.5 协议要求怎样落实为测试

对原有 2025 路径，工具业务失败不能伪装成功；宣告输出 schema 就要提供相符的结构化结果。权限不能来自工具 annotations；模型参数投影不能替代服务端验证。[MTOOLS]

HTTP MCP 的资源授权与 STDIO 凭据处理分开。Acosmi 自有资源的租户/JWT 策略不是第三方 MCP 的通用格式要求；合法 opaque token 不应被通用客户端强制当 JWT 解码。[MAUTH]

HTTP Origin 校验不能用 CORS 代替；初始化通知的响应和版本协商按固定规范验收，而非凭历史注释推断。[MTRANSPORT] [MLIFECYCLE]

完整应用性见 RC-04/08/12、测试 T07/T14/T19–21/T41–43。新增的业务错误码、状态和确认回执只在宿主/第一方业务合同中定义，不占用标准字段或破坏 MCP result 形态。

## 3. 实际调用链、关联方责任与数据边界

### 3.1 五条路径分别定位

```text
插件市场 / 源码 / 预构建发行物 / 发布声明
   → 安装来源与 digest
   → Skill/Agent 可见性与能力依赖（没有执行授权）
   → 宿主当前配置、激活、权限和运行状态
      ├─ 本地 MCP：Agent 或直接调用入口 → worker → stdio 子进程
      ├─ 直接远程 MCP：独立资源授权 → HTTP/SSE 服务
      ├─ Acosmi 聚合 MCP：资源授权 → /api/v4/mcp → DB Skill → 沙箱
      ├─ 法律本地工作台：材料读取 → Python Matter 工具 → 验证 → 内部草稿
      └─ 已实际采用的厂商 hosted MCP：由厂商执行，宿主消费其调用事件

原始 MCP 语义结果
   ├→ 受边界限制的 RPC 返回 → Rust 协议消费者 → GUI/CLI
   ├→ 安全产物持久化 → 文件/预览/Office 消费者
   └→ 模型专用内容投影 → function-call 续轮

模型请求网关负责模型消息适配，不因此成为所有 MCP 的传输代理。
业务对外动作另经有效授权、具体目标和用户确认；本轮不自动开放。
```

独立 transport、平台 DB Skill 执行和法律 manifest 有固定源码依据。[HCONNECT] [GHANDLER] [PLAW] 直接 `tool/call` 的 Rust 反序列化也是实际消费者，但是否是用户主聊天故障入口仍待 trace 确认。[HRUSTINVOKE] [HGUI]

### 3.2 三个小型共享合同，禁止影子控制平台

| 合同 | 最小内容 | 谁拥有最终决定 |
|---|---|---|
| 能力状态 | 发布状态、具体依赖、阻断原因、可达输出、安装/授权 revision | 发布声明只能限制；宿主现有激活和权限机制决定能否连接/调用 |
| 执行结果 | 标准 content、structuredContent、isError；宿主侧已知状态/错误/必要 requestId | 服务给业务结果，宿主保留不确定性；模型文本不改变机器状态 |
| 确认/审阅 | 对象、操作、版本/哈希、真实确认渠道、主体和决定 | 受信用户界面或被授权服务；模型、项目文件和自报姓名不产生人类决定 |

元数据不是权限。现有 `requiredMcpServers` 仍保持其本地必需/自动激活含义，不偷偷改成远程权限依赖。[HLIFECYCLE] 协议 `_meta`、第三方业务 `_meta` 和宿主内部确认字段分开：仅保留各边界允许的字段，不把凭据或内部路径全量送给模型，也不信任调用参数里伪造的“已确认”。

### 3.3 关联方—消费者—责任矩阵

### RC-02：普通插件被渠道白名单误拦【S，条件性；P1】

**实施追踪：**H-S1；验收 T06、T47、T49。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** `mcp-invoke.ts` 使用 `pluginSource && isChannelsEnabled() && !isChannelAllowlisted(...)`，没有在这条条件中确认目标是实际渠道服务。渠道功能默认 false，因此不能归因于所有失败。[HINVOKE] [HCHANNEL]

**修法。** 复用实际渠道声明/授权身份判定，只对真正的消息渠道执行渠道白名单；普通 MCP 仍检查当前激活、项目权限、工具权限和用户确认。主模型调用、子代理和直接 RPC 必须使用同一判定，不通过“所有插件加入渠道白名单”规避。

**验收。** channels 开/关 × 普通/真实渠道 × 已授权/未授权的交叉用例；用户配置服务器不能伪装成渠道免审，消息渠道也不能通过改来源名称绕过门禁。

### RC-03：缓存与身份/配置变更必须同步失效【S+V；P1】

**实施追踪：**H-S1、H-M1、H-C1；验收 T04–05、T13、T43。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**已知事实。** 云发现使用会话级 memoize 并把失败折叠为空集合；MCP 连接以配置形成缓存键；已有 worker reconcile 和缓存刷新机制，不从零重做。[HCLOUD] [HCONNECT] [HINIT]

**扩大修复要求。** 登录、登出、换账号/租户、禁用插件、撤销工具许可、变更 endpoint/command/root 或恢复发布资格，都应使相关连接、工具目录和模型可见清单失效。缓存键应包含主体/租户作用域及授权 generation 的非秘密标识，不使用 access token 本身；连接池不能跨账号复用低保证主体。使用现有 reconcile，在断开旧进程后装入新配置。

**缓存策略。** 成功目录可短期缓存；临时故障记录为“获取失败/上次成功时间”，不可永久记忆成空目录。不跨账号保留 last-known-good。登录后清缓存同时刷新活跃 worker，不只清主进程缓存。失败重试有上限和退避，不能触发配置下载、安装或再次授权循环。

**无需新基础设施。** generation 使用本地现有配置/安装版本派生值或单调修订号即可；无需分布式事件总线、远程租约或第二个注册中心。

**作用域。** 将账号、租户、workspace/cwd、配置 scope、服务器来源与 issuer 分开，不按相同显示名复用凭据。已读 GUI 的 `resolveMcpManagementCwd()` 复用工作区真源，说明项目作用域已有实现，应沿用而非新建。云账号登出只撤销相关授权，纯本地低保证编辑不应被意外变成必须云登录；稿件不随账号切换删除。对跨窗口状态变化用既有刷新/重建机制做实测。[HGUI]

**实现约束。**发布状态、安装状态、用户激活、连接健康、特定工具权限和业务就绪保持不同维度，不用一个 ready 布尔覆盖全部事实。可见性计算须读取实际安装版本，不能由市场当前主分支覆盖旧安装物。管理清单可以展示被禁用的服务，但不能把管理占位配置当可连接 transport。暂停只限制其依赖流程，已明确选择草稿模式时不要在每个步骤反复要求确认同一降级。

**权限与缓存验证。**先确定实际凭据 key 和作用域，新增 generation 只解决已识别的失效问题。云账号失效不能强制清空纯本地工作；同一个模型对话的历史工具目录不能覆盖最新撤权结果。连接健康失败不等于重新授权，重连也不等于允许重放业务写入。

## 5. 宿主：结果、错误、产物、取消与模型续轮

<a id="rc-04"></a>

### RC-04：模型文本投影被误用为 RPC 原始结果【S；实际可达路径的 P0-common】

**实施追踪：**H-R1；验收 T07–09、T39、T49。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据链。**

1. `MCPToolResult = string | ContentBlockParam[] | undefined`。[HVALID]
2. `transformMCPResultWithArtifacts()` 在有 `structuredContent` 时，将其 `jsonStringify` 成 `content`；大结果落盘后也可能返回读取提示字符串。[HRESULT]
3. `callMCPTool()` 返回这个模型专用 content 和可选 artifacts。[HCALL]
4. `mcp-invoke.ts` 用手写断言把函数签名当成 `content: unknown[]`，之后原样返回 `result.content ?? []`。[HINVOKE]
5. 生成的 `McpServerToolCallResponse` 明确要求 `content: Array<JsonValue>`。[HWIRE]

**后果。** 结构化结果/大结果路径可能把字符串送进要求数组的协议；图片等模型块与 MCP 原始块的结构也不能混用。该调用入口没有返回 `callMCPTool` 收集到的 artifacts，存在与主模型路径不同的产物呈现缺口。源码条件链已确认；既有记录未完成 Rust/GUI 联合复现，不声称全部普通文本调用都失败。

**根因修法。** 抽取或复用一个“已授权的原始调用”薄层，返回规范 `CallToolResult`，其下仍使用现有连接和调用逻辑。RPC 分支保留 MCP content 数组、structuredContent、isError 与允许的 metadata；模型分支另做压缩、文本化和产物提取。不得让原始协议结果绕过现有字节/图片/存储安全限制。

**避免表面修补。** 只把字符串包成一条 text block 可以作为受测试的兼容措施，但不是最终根修，因为已经丢失的资源/图片形态与 metadata 不会凭空恢复。删除不实类型断言，消费生成类型；只有合同确实需要改变时才修改 Rust 真源并重新生成 TS/JSON；现有 schema 正确时修生产者，不为错误字符串返回放宽为任意值。禁止直接改生成文件。[HWIRE]

**验收。** 纯 text、structured-only、text+structured、图片/资源链接、空结果、大结果落盘、非法 schema、超限输出，分别经主模型、子代理、直接 worker RPC 和 GUI 验证。原始 structuredContent 与输出 schema 一致，模型压缩不得修改业务成功/失败状态。不能把结构化值截断成半个 JSON；超过协议或内存预算时返回明确大小错误或已经约定的受控引用，不悄悄变更成功输出结构。

**实际消费者。** Rust 的 `crates/acosmi-app-server/src/dispatcher/mcp_invoke.rs` 会把 worker JSON 反序列化为 `McpServerToolCallResponse`，因此不能只修 TS 类型断言。GUI 的 `frontend/tauri/src/appServer/mcpFlow.ts` 只做宽松对象检查后类型断言。两者加入 H-R1 的实际修改/回归责任，生成类型仍由 Rust 真源生成。[HRUSTINVOKE] [HGUI]

**归因限制。** GUI facade 的源码注释标注直接 `tool/call` 非主 GUI 对话路径；注释不等于所有现实调用者都不存在，但足以要求重新找实际 caller 与 trace。源码缺陷可以修，不能因此宣称已定位用户主聊天失败。直接 RPC、主 Agent loop 与子代理的入点应分别验收。

### RC-05：工具错误跨 worker 后失去语义【S；P1】

**实施追踪：**H-R1、G-E1 的对应映射；验收 T09–10、T19。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** `callMCPTool()` 对 `isError` 提取首段文本并抛异常，仅选择性保留 `_meta`；worker 再统一转换成 `WorkerError(-32603, message)`。授权不足、业务校验失败、会话失效等因此难以被上层准确区分。[HCALL] [HINVOKE]

**修法。** 保留三层差异：传输/JSON-RPC 错误、工具业务失败、工作流需要用户操作。标准 MCP 业务失败继续为 `isError:true`；宿主内部使用已有错误通道补充 `code/stage/retryable/executionState/requestId`，并透传经过脱敏与大小限制的结构化详情。模型、GUI、日志与成功率统计都读取同一真值。

**取消/拒绝也是非成功。** URL elicitation 被用户或 hook 拒绝时，当前重试包装器返回普通解释文本，不携带独立完成状态；不能据此报告业务完成。保留“拒绝/取消/待授权”语义，不让 UI 必须理解自然语言。[HCALL]

**兼容。** 老客户端仍得到可读错误文本，新客户端消费结构字段；不要把全部 RPC 错误都改为 HTTP 200 成功，也不要把标准业务错误改成无法恢复的进程崩溃。

<a id="rc-06"></a>

### RC-06：取消、超时与写操作重试没有完整闭环【S+V；P1】

**实施追踪：**H-R1、G-E1 及实际第一方写入口；验收 T10–12、T22、T49。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** worker 调用函数忽略 `_ctx`，创建独立 `AbortController` 却未挂接外部取消；`callId` 未使用，onProgress 未接线。底层另有 5 分钟工具超时；原连接 fetch 层还有请求预算，网关 handler 和沙箱又有自己的预算。[HINVOKE] [HCALL] [HCONNECT] [GBRIDGE]

**修法。** 从真实 GUI/CLI 调用者开始，贯通 session → Rust dispatcher → turn worker → SDK → 执行器。已读 GUI facade 与 worker 都有未使用的取消信号，仅修 worker 不足够。[HGUI] [HINVOKE]

对同一次实际执行传递统一截止时间和剩余预算，但启动、授权发现、等待用户确认、业务执行分别定义预算与可取消状态；不把人类思考时间机械计入几十秒的网络超时。长任务复用既有任务机制。让取消触达 SDK、网络/子进程或执行器，并区分取消请求、已停止和结果未知，不能把停止等待当作业务已回滚。

**写入规则。** 传输断开/超时后，若不能证明未执行，状态为 `outcome-unknown`；先查询操作/任务 ID，不自动重复写入。对平台自己拥有的状态变更接口增加有限幂等键与 payload hash：同键同请求回放原结果，同键不同请求明确冲突。第三方未承诺幂等时不冒充 exactly-once，不通过全局重试中间件解决。

**安全重试边界。** 只读、明确尚未执行的身份挑战、或服务端接受幂等键的操作可自动重试。会话失效的重新连接不等于可以无条件重放业务写入。

### 5.1 模型网关与延迟工具发现的联合核对【V，不冒充已确认缺陷】

每个受支持 provider 至少覆盖一条普通 function-call 续轮：工具名与参数进入模型、tool-use ID 返回、worker 执行、tool-result ID 原样对应、模型收到失败或结果、完成用户交付。对延迟发现同时验证发现的原始 toolName 能映射到本轮实际工具目录；使用显式原始名↔运行名映射，不按字符串猜测还原。

查 schema 变换、`tool_reference`、`defer_loading`、streaming argument delta、tool choice、并行调用和工具结果块。provider 不支持延迟发现时，回退到普通函数目录，而不是丢掉依赖工具。未实际验证的 provider 不算在“全部恢复”的支持列表内。

这部分是恢复验收，不是断言现有每个适配器都有错；顶层 `mcp_servers` 的清洗与本地 MCP 工具链保持分开。

### 5.2 原始结果、元数据和执行负责人的最终边界

原始结果指固定 SDK/协议所定义的语义结果，不要求为所有调用持久化网络原始字节。标准协议字段保留给需要它们的消费者；模型可见文本、UI 产物及内部错误状态分别投影。不得将所有不受信 `_meta` 当成宿主确认凭据，也不得把合法协议字段因粗暴过滤丢失。

输入参数的类型与约束在执行前校验；厂商 Schema 子集需要适配时，保留服务器原始 Schema 作为最终真源。名称映射保留 plugin/server/tool 原始身份，对清洗后重名明确报错；不能靠删除标点反推工具。流式参数必须在完整解析和当前授权后执行，不能每收一个 delta 就触发一次操作。

由 CrabCode 执行的 function-call 与厂商 hosted MCP 只能有一个业务执行负责人。对 hosted 已执行的结果只消费回执，不再次交给本地同名工具执行；厂商不支持某项能力时有界降级或明确不支持，不能静默改变动作含义。测试责任为 H-R1/Q-1，调用者与 API 清单沿用第 2–3 节。

**取消的副作用范围。**优先取消单请求。仅在子进程独属于该调用、或已经明确通知所有受影响调用时才终止整个进程；不能为取消一个工具杀掉共享 sidecar 的其他任务。进度按真实请求/线程路由，不广播到无关窗口。网络等待预算、用户确认等待预算和业务执行预算分开。

## 6. 云端发现、OAuth 与聚合端点

<a id="rc-07"></a>

### RC-07：scope、路径与服务语义漂移【S；生产路由 V】

**实施追踪：**G-A1、H-C1；验收 T13、T16、T39、T43。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** 桌面申请 `ai/skills/account`；`acosmi.ts` 要求 `user:mcp_servers` 后才请求 `/v1/mcp_servers`；代理连接使用固定 `/api/v4/mcp/{server_id}` 而非直接采用发现 URL。已读网关 MCP 路由为 `/api/v4/mcp`，提供 DB Skill。[HOAUTH] [HCLOUD] [HCONNECT] [GROUTES] [GHANDLER]

**实施决策。** 默认先把已有聚合服务作为一个明确命名的第一方 MCP 接入。新宿主通过版本明确的能力描述确认端点、资源标识、支持协议和授权方式；复用现有平台配置能力，不新建庞大服务器目录。

**旧支路。** 只有生产使用证据证明必要时，才实现旧 `/v1/mcp_servers` 与按 ID 代理兼容。映射必须来自明确注册记录；不能把所有第三方 connector ID 发送到聚合 Skill 服务，不能遇 404 便尝试多个猜测地址。

**授权合同。** 定义聚合资源自己的最小读取/调用权限，明确哪些已有 scope 经服务端授权政策允许映射。不能直接用字符串替换把 `skills` 当作无限工具执行权限。若需要资源专用授权，走现有 OAuth 发现、PKCE 与授权入口；不要把桌面 access token 发往任意发现 URL，也不要求用户向聊天提供 token。

**联合顺序。** 服务端资源与授权合同先合并、受限部署并验证；客户端能力开关后启用；最后迁移明确匹配的旧配置。旧账号授权不够应提示补充授权，不自动扩权。[MAUTH]

<a id="rc-08"></a>

### RC-08：资源受众校验存在形态缺口【S；P0-cloud】

**实施追踪：**G-A1、H-C1；验收 T14–16、T42–43、T47。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**实际代码。** `BearerTokenMiddleware` 调用非 strict `ValidateAccessToken` 后，仅在 `aud` 是非空 string 时检查其值。缺失、空值或数组形态未进入这段受众比较。该 middleware 本身不检查具体 scope；`RequireScopes` 是另一个函数。[GMIDDLE]

**扩大核对。** `ValidateAccessToken` 主要执行 token parse 与 keyfunc；同文件另有 `audienceContains` 和 strict 路径。strict 的名称/注释并不代替字段存在性测试，尤其应检查 exp/iat 的缺失处理，不凭“使用 JWT 库”假定必填已经生效。[GAS]

**修法。** 在 MCP 资源边界统一验证 issuer、资源 audience（支持合法 string/array、拒绝缺失与无匹配）、明确算法集合、subject/tenant/授权来源、token 用途、到期及所需 scope。优先复用已有 verifier 和 audience helper，再补缺失断言；不全仓切换 strict 导致桌面登录、合规域或其他服务意外中断。

**禁止的修复。** 为解决不可调用而关掉 audience/scope；把通用网页或桌面 token 当作任何 MCP 的授权；让调用者参数覆盖租户；只按 `client_id` 识别真人。

**第一方与通用协议分界。** `tenant_id`、本平台算法白名单和账户状态是 Acosmi 资源策略，不得要求所有第三方 MCP token 都长成相同 JWT，更不能拒绝合法的不透明 token。第三方凭据按其 issuer/resource 与官方授权机制管理。请求授权不能以 MCP 会话 ID 代替；代理下游使用独立授权，不盲目透传收到的用户 token。[MAUTH]

**证据边界。** 这是校验路径缺口，并未铸造生产 token 或证明可利用跨租户漏洞。验收在测试签发器与测试租户完成，错误 aud、数组无目标、缺 aud、过期、缺必填 claim、错误 issuer、撤销/账号禁用、缺 scope 都必须被拒绝。

### 6.1 端点、基础设施与出站信任边界

`/api/v4/mcp`、OAuth metadata、protected-resource metadata、token resource/audience、反向代理 location、TLS、超时/缓冲、需要时的 CORS 必须作为同一合同验收。公开 metadata 可以只读验证，但它不能证明真实 token 与生产网关已一致。

不要沿用 `oauth.ts` 未核实的旧 TODO 推断路径；不要全局修改 `BASE_API_URL` 影响其他业务 URL。多实例授权码/刷新存储、撤销机制沿用现有实现并做真实双实例测试，仅在失败有证据时补相应缺口，不因此重建 OAuth 平台。

**适用规范与产品边界：**CORS 配置不能替代 HTTP MCP 的 Origin 校验；有不合法 Origin 的请求应被拒绝，本地服务不默认绑定所有网卡。[MTRANSPORT] 现有 RC16 只读到媒体抓取差异，不能外推其他网络路径安全或有漏洞；将 OAuth 元数据发现/重定向、资源链接获取和产物远程引用列为独立有界网络测试，凭据不得跨 origin 随重定向发送。工具说明、annotations 和模型可见 roots 不是权限证明，实际文件/网络权限仍由宿主与资源服务执行。[MTOOLS] [MAUTH]

**受管端点和通用客户端分别实现。**自有 MCP 资源明确所需权限、主体与到期策略，拒绝错误 audience/issuer 和不满足 policy 的 token；通用第三方客户端不假定 token 是 JWT。资源会话 ID、tool annotations 和客户端传入 tenant 字段均不构成授权。刷新与撤销失败保持可诊断状态，不把 403 当作协议不兼容后降级到一个更宽松入口。

**Origin 与跨域。**测试无 Origin 的合法非浏览器客户端、允许 Origin、禁止 Origin；存在且非法时拒绝，不把所有缺 Origin 的机器请求一律误拒。CORS 仅在实际浏览器调用时配置允许来源/头，不采用通配凭据跨域。localhost 例外是明确的本地 transport/部署策略，不是公共网页抓取允许访问任意内网的例外。

**代理与网络检查。**OAuth metadata、授权重定向、远程资源/图标与产物引用不是同一种 URL；按各自用途限制协议、跳转、体积和私网访问。对本项目启用的 loopback 授权回调保留固定规则，不将其当普通网络抓取。不自动把认证头发往未经授权的另一 origin；只读 metadata 成功也不证明真实签发/资源授权一致。这些是 V 合同测试，不是新增的已证实生产漏洞。

## 7. 网关：目录、执行、业务结果与协议

<a id="rc-09"></a>

### RC-09：工具列举与执行资格不同【S；P1】

**实施追踪：**G-E1；验收 T17、T19、T46。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** `tools/list` 与 `tools/call` 的归档条件不同，bridge 对安全等级还有额外拒绝。list 可带 `outputSchema`，call 通常只返回文本。`InputSchema` 当前用 `json.Valid` 检查，只能证明 JSON 可解析，不能证明符合工具 schema。[GHANDLER] [GBRIDGE]

**修法。** 在现有 Skill 服务内提取一个小型资格判定，列举与调用共用：审核/启用/归档、执行种类、所需授权、可支持的 schema。目录只暴露实际可执行类型；纯提示 Skill、远程 MCP、沙箱代码不能仅因同存 DB 就被当成同一种代码任务。调用时重新判定，目录并不授予永久执行权。

**运行健康。** `Available()` 只是 worker/db 非空，不能作为执行健康证明。用现有 worker 健康/队列指标展示可用状态；不要给每次 list 增加真实写操作探针。瞬时健康变化可以导致调用失败，但错误必须真实且可诊断。

**输出 schema。** 成功调用返回符合宣告 schema 的 `structuredContent`，同时按兼容要求提供文本表示。无法保证结果符合 schema 的工具先不宣告该 schema，而不是宣告后返回任意字符串。执行错误保留 `isError:true`，按固定 SDK/协议的错误结果规则处理，不用成功输出校验掩盖原错误。[MTOOLS]

<a id="rc-10"></a>

### RC-10：沙箱不可用的“成功占位”【S；P0-cloud】

**实施追踪：**G-E1；验收 T18–19。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据片段。** `bridge == nil || !bridge.Available()` 时，handler 返回 `result.content` 中的 `sandbox bridge not available`，没有 `isError:true`。[GHANDLER]

**修法。** 删除成功占位，返回真实的 `EXECUTOR_UNAVAILABLE` 工具失败；业务执行失败、结果转换失败、超时、取消分别映射。成功必须至少有明确执行结果/任务终态；`nil result + nil error` 也不允许解释为完成。非零退出防御性检查保留，但不得篡改原 bridge 已返回错误的事实。

**验收。** bridge 缺失、worker 停止、队列满、脚本报错、转换失败、空结果、正常运行，模型/GUI/指标均一致。失败不能产生“已完成”的审阅或发布记录。

<a id="rc-11"></a>

### RC-11：主体归属与取消落地断开【S；P0-cloud/P1】

**实施追踪：**G-A1、G-E1；验收 T11–12、T15、T22。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** handler 使用 `skill.TenantID` 与固定 `mcp-client` 调用 bridge；bridge 将它们写入任务。ctx 被取消时轮询可以直接返回；超时又直接更新任务失败。源码不能证明此时执行器已停止，晚到结果也需要终态约束。[GHANDLER] [GBRIDGE]

**修法。** 从验证后的请求上下文建立调用者与租户；分开记录技能所有者、调用者、执行主体和计费归属。复用既有 Skill 执行前检查及配额/运行约束，不让 MCP 成为绕开其他业务入口的捷径。所有任务读取、取消、结果查询按调用者作用域授权。

使用现有任务取消 API/执行器机制传播取消；任务终态以条件更新/CAS 保护，禁止超时覆盖已完成或晚到成功覆盖已确认取消。无法停下的外部动作如实为“取消已请求/结果未知”，保存 operationId 供回查。

**兼容。** 历史 `mcp-client` 任务保留，不凭猜测追补到某真实用户。新的 caller 字段先加法迁移，授权切换后再移除旧写法。

<a id="rc-12"></a>

### RC-12：手写协议入口的基础兼容问题【S；P1】

**实施追踪：**G-E1，涉及客户端时由 H-R1 配合；验收 T16、T20–21、T41–42。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** `Request/Response.ID` 为 `int64`，不支持合法字符串 ID；handler 用 `ID==0` 判断初始化通知、返回 204；初始化固定返回 `ProtocolVersionLatest`。[GTYPES] [GHANDLER]

**适用规范。** “固定返回一个版本”本身不必然违规：2025-11-25 规则允许服务端在不支持请求版本时返回自己支持的另一版本；如果服务端支持请求版本，则必须返回相同版本。应补测试证明支持集、请求值和实际返回一致，不能仅凭常量判定故障。该通知/初始化规则只适用于本文固定的 2025 支持清单，不能套到 2026-07-28 的无握手路径。[MLIFECYCLE] [MCURRENT]

**最小修法。** 对 HTTP MCP 边界采用现有 SDK 可复用的协议组件或小范围类型适配，保留数字/字符串 ID 并区分缺失 ID，按固定支持集协商版本，接受通知时返回规范状态。不支持 SSE GET 的端点返回相应的 method-not-allowed；限制 body 时检测超限而非悄悄截断后解析；校验请求和 schema 结构。[MTRANSPORT]

先用合同测试定位，再选择薄适配或替换协议壳。不要借机重写全部 MCP 客户端、OAuth 或沙箱。当前 2025-11-25 支持集与第 2.3 节的可选新协议路径分开管理。[GTYPES] [MMIGRATION]

### 7.1 列举不授予权限，Schema 不等于 JSON 可解析

list 与 call 共用稳定的资格规则，调用时再次检查当前版本/权限。瞬时执行器故障允许目录仍描述该工具，但必须有真实健康信息和失败结果，不能为了目录“全绿”每次启动写探针。目录分页、稳定顺序和变化通知沿用支持版本的既有机制；已有正确分页实现不再重写。

`json.Valid` 只证明语法，实际需验证工具定义 Schema、执行参数及声明的输出。无效输入在产生副作用前拒绝；模型端适配不能删除服务端 required/enum/范围等约束。对非本地 `$ref`、深层组合和超大 Schema 给出有界处理，不因读取外部 Schema 任意出站。来源/租户下的技能 ID 与公开工具名映射必须无歧义；发现同名冲突时先明确映射或拒绝，不能选择数据库第一条。

上述属于 G-E1 的限定合同修复。优先调用已有 Skill 执行前校验和授权逻辑，禁止另建一条只因来自 MCP 就跳过配额、运行限制和数据权限的路径。

### 7.2 终态与幂等

同一任务的 completed/cancelled/failed 转换使用既有存储的条件更新，保留执行实际结果。超时发生在结果已落库之后时，返回或回查已知结果，不覆盖成超时失败。客户端结束等待不证明任务停止，更不证明外部副作用回滚。

仅对第一方有副作用操作复用或补充 operationId/幂等约束，并绑定调用者作用域、操作及请求摘要。同键不同参数拒绝，同键同已完成请求回放；查询和取消仍重新授权。账单/配额必须以实际执行身份与操作关联去重，不能因协议重试再次扣费。未知结果先回查，第三方服务没有幂等合同则不自动重放。

协议错误、HTTP 授权错误和业务失败仍分别表达；有效但无内容的只读结果不应因内容空而被误报失败，`nil result + nil error` 的未定义状态则不能以占位 completed 掩盖。

## 8. 新媒体：身份、单人可达交付与内容质量

<a id="rc-13"></a>

### RC-13：启动配置与业务主体缺失【S；P0-media】

**实施追踪：**H-M1、P-M1、P-M2；验收 T04–05、T23–24、T48。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** 媒体真实入口为 stdio；写工具经 `authorizeToolCall` 要求可信主体与角色；旧执行配置只提供数据目录。源码支持 host-principal/local-editorial，禁止模型自报身份；独立真人门禁仍存在。[PSERVER] [PIDENTITY] [PINVENTORY]

**宿主改动。** 经现有本地可信用户入口，授权第一方媒体的本地编辑范围，传给 worker 后再受控创建 sidecar。使用宿主提供/校验过的运行时和规范路径；不假设 GUI PATH 中一定有 bun。只注入插件必需的运行环境、非秘密配置或专属凭据，不继承无关 API key、cookie 与桌面会话 token；项目文件和模型参数不能覆盖受信主体字段。

**低保证边界。** 环境中的本地主体是 `local_editorial`，不能被包装成验证过的多用户 OAuth。拥有本机任意代码执行权限的人可以改变本地文件/进程，这套环境变量方案不提供对其防篡改的强认证。正式团队审阅需不同真实主体和受控决策渠道，本轮不伪造。

**角色授予。** 明确 author/researcher 等本地编辑角色；机械 scan/render 使用服务体。不能授予通配角色来消除报错。相关云身份切换/撤权或本地身份范围改变时，关闭并重建受影响连接；纯本地身份不因无关云登出而被删除或强制云登录；数据目录按明确用户/工作区策略隔离，默认不得把上个账号的稿件投影给新账号。

<a id="rc-14"></a>

### RC-14：单人与团队流程必须有不同的可达终态【S；P1】

**实施追踪：**P-M1、H-M1；验收 T24–25、T38、T44。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

当前单人模式并不意味着所有治理门禁能通过，特别是独立原创、编辑、审批、风格确认需要另一真实主体。[PIDENTITY]

| 模式 | 允许到达的交付 | 不可升级为 |
|---|---|---|
| 草稿 | 真实正文、来源与待核项、HTML/Markdown 草稿 | 已治理/已审批/已发布 |
| 本地单人编辑 | 持久化 revision、来源记录、机器检查、用户确认的本地交付 | 独立多人复核或机构认证 |
| 团队治理 | 正式分离主体完成复核与审批，决策绑定具体内容和产物字节 | 模型填几个人名即可“多人批准” |

**最小实现。** 复用现有 Content/ArticleDoc 和持久化机制（具体存储实现以原发行物为准）；增加受限的“草稿/本地预览导出”操作或模式分支，允许渲染 draft，但把 `releaseStatus=unapproved` 等真实状态写入 manifest，不能推动既有正式 reviewed/approved 状态。先验证现有 `delivery.render` 前提；不能为了预览删除它的正式门禁，也不复制一个新存储或新工作流引擎。

**风格问题。** 单人不能因为缺少团队 profile approval 永远无法写作。允许使用默认模板或个人未批准偏好，明确与组织批准 profile 分开；团队发布仍遵守原确认门。质量检查缺重依赖时可以 static，但不能把 static 标为 full QA。

**最小 E2E。** 选题与平台 → 来源获取 → 论点与反方 → 正文 → 保存/回读同 revision → 用户修改 → 本地 HTML+Markdown → 列出未复核/未发布状态。此闭环不是停在 `capabilities → save → get`；后者只是早期技术门。

<a id="rc-15"></a>

### RC-15：热点来源、稳定标识、时效和排序【S；P2，基础修复随恢复】

**实施追踪：**P-M1 的相关热点子项；验收 T27、T38。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** 内置注册表只有 Hacker News 示例；generic feed 使用 `source:index`，信号只有 capturedAt；跨源直接比较 hotScore。[PSOURCES] [PTRENDS]

**修法。** ID 优先源端唯一键，否则规范 URL 哈希；发布时间、事件时间、首次发现与采集时间分开，缺失就为空，不用当前时间补造发布时间。保留 rawScore/scoreUnit 与来源内排名，再按目标读者相关性、时效及重复事件分组做可解释排序。旧位置 ID 不直接重写历史审计，新增稳定键/映射，后续新记录使用新规则。

中文平台接入走有授权的来源、用户提供数据或已有研究工具。安装后无国内数据时明确显示“未配置”，不能用 Hacker News 成功代表中文热点服务已通；不为这轮构建大规模抓取平台。

<a id="rc-16"></a>

### RC-16：两套出站网络检查强度不一致【S；恢复网络前检查】

**实施追踪：**P-M1；验收 T28、T37、T45。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** `research-capture.ts` 拒绝私网/混合解析、限制端口和凭据，并包含固定解析目标的请求逻辑；generic feed 的入口主要是 HTTPS hostname allowlist，随后直接 fetch、禁止重定向。[PCAPTURE] [PSOURCES]

**判断边界。** allowlist 是现有保护，并非任意 URL 均可请求；但它不等于实际拨号 IP 安全。未做线上 SSRF 利用，风险取决于 allowlist 配置及所允许域的解析。

**修法。** 将已有 capture 的出站验证提炼为媒体内部小工具，feed 与 capture 复用；按用途保留 MIME/正文解析差异。拒绝 URL 用户信息、非允许端口和不允许的地址；解析变化时重新验证并绑定实际拨号目标，不把正常 CDN 轮换一概视为攻击；保持超时、体积上限、脱敏错误。无需新建跨三仓通用网络 SDK。

### RC-24：QA 跳过与通过混用，审核证据等级未闭环【S；P0-media 正式就绪/受影响保证】

**实施追踪：**P-M1-a，正式决定链由 H-M1 配合；验收 T24–26、T38、T44。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。**固定提交 `delivery.ts::writeStaticQaEvidence()` 将没有运行的浏览器检查写成 `status: passed, mode: static-skip`，汇总 qaEvidence 同样是 passed；`verifyHandler()` 根据合并检查计算 verified。`readiness.ts` 消费交付验证与字节校验，其已读路径未显式限定 full 等级。[PDELIVERY] [PREADINESS]

**结论边界。**已确认跳过与通过的代码语义混用，未完整运行 approval/package，也未证明已绕过所有发布控制。这是前轮评审已发现的项，本版将其正式并入实施与验收，不以 README 加一句提示替代修复。

**最小改动。**沿用现有 QA schema，记录 mode、policy/version、requiredChecks、executedChecks 及每项 passed/failed/skipped/not-run。只有实际运行且成功的检查可以 passed；各质量维度分别聚合，不用一个 staticPassed 给安全、语义和可访问性全部授相同等级。字节哈希只证明绑定的内容没有变化，不证明真实跑过检查或有人实际阅读。

**消费者链。**`delivery → readiness → approval → package → GUI/模型/发布说明` 按同一 policy 判定证据是否足够。旧证据缺少 mode/执行信息时为 legacy-unknown，不自动升级 full。static/off 可以产生明示等级的本地草稿，不满足正式流程所需检查时不能推动正式批准。用户后来补齐检查，须绑定同一产物哈希并重新计算当前有效性。

**人类决定。**代理获得用户权限只证明可代表其执行，不证明真人完成编辑、法律或视觉审阅。正式人类声明来自既有可信 UI/授权服务的决策记录，绑定操作、对象、hash/revision、主体与有效期；代理参数、自报人名或可改本地 JSON 不构成证据。只保留个人低保证模式时，明确其保证上限，不为草稿搭建机构级签名平台。

**验收。**静态、关闭、完整执行失败、完整执行通过、伪报 full、旧证据、改稿后重用旧决定分别走上述消费者；验证文件内容与所标 QA 等级一致，真人确认不被自动 tool call 代替。对应 P-M1-a/H-M1 与 T24–26/T44；QA 小修可独立合并，不等待热点功能或团队身份平台。

### 8.1 内容质量评测

保留现有发行物一致性、机器 QA 与视觉测试，它们不能替代文章质量。[PPACKAGE]

首批评测采用少量代表任务：科技观点、商业解读、品牌内容、给定材料改写、无可靠来源时降级、用户自有稿件编辑。结果同时检查信息增量、论点/反方、事实与推断、来源支持、风格、平台适配和最终 HTML 可读性。相同模型/设置做有无 Skill 对照，多次运行，记录真实输入/输出 token、耗时、工具调用和人工干预；不能以字符数冒充 token，不能保证流量增长或平台审核通过。

### 8.2 单人交付的最小依赖清单

无完整 QA 依赖时，不强迫安装 Java/Chromium 才能导出未批准草稿；保留基本安全渲染、路径/体积限制并标明未执行检查。完整 QA、团队复核和平台发布分开列依赖，启动成功不代表这些业务能力就绪。

首批一个真实媒体任务可以用用户给定且获准的材料完成；不以接入全部中文热点源为开工前提。热点稳定 ID/时间字段的基础修正随相关工具恢复，扩展来源与复杂排名为 P2。引用/图片权利与披露状况需如实展示，程序不能从“能下载”推断“有权公开发布”。

模型做研究归纳与创作，程序做确定性数据/渲染，用户作真正决定。尽量复用任务中已有材料和偏好；不要让用户维护几十个中间 JSON，也不要把模型切换几个角色算作独立真人审核。

<a id="rc-17"></a>

### RC-17：不完整扫描被当作没有命中【R-hist；P0-law】

**实施追踪：**P-L1；验收 T29、T34。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**原证据。** `bootstrap_matter.py` 的历史读取捕获 ValueError 后 continue，空命中集合产生 no-hit，并允许实体工作。前轮报告记载损坏 JSON 的隔离复现成立；本版未重跑。[LBOOT]

**历史隔离记录。** 同一人造当事人记录位于 `matters/<id>/parties.json` 时命中，移动到已文档化的 `_archived/<id>/parties.json` 后漏检并放行。合法 JSON `[]` 还会产生未捕获 AttributeError，丢失结构化错误。见第 12 节。该行为不是“已确定无实质法律冲突”，而是扫描覆盖和类型处理问题。

**修法。** 扫描结果必须包含 `complete/partial/failed`、范围、成功/损坏/拒读数量及原因。覆盖客户、当前事项和归档事项的既有布局；对未知旧布局或无权限区域声明覆盖限制。先校验 object/关键字段，再读取名字。资料坏、拒读、路径异常、归档范围缺失都不能生成“全面无命中”结论。

局部扫描可提供候选，但只能称“在已读取范围内未发现匹配”，且禁止由此单独放行需要完整利冲前提的正式任务。程序只提供候选和覆盖事实，最终律师利冲判断仍独立。

<a id="rc-18"></a>

### RC-18：历史扫描绕过父目录路径安全【R-hist；P0-law】

**实施追踪：**P-L1；验收 T30、T34。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** `_matter_common.safe_path()` 检查路径包含关系与符号链接，但 `existing_name_records()` 对 glob 得到的文件直接 `load_json()`，只检查叶文件 `is_symlink()`。[LCOMMON] [LBOOT]

**历史隔离结果。** 在临时 `clients/linked-record` 放一个指向另一个临时目录的父目录符号链接，目标 `client.json` 中的人造名字被扫描并形成命中。只证明扫描读到了配置根外的该测试记录，不证明远程攻击或生产数据泄露。

**修法。** 所有被枚举文件，在 open 前都经同一 canonical/containment/逐级 symlink 校验；客户、活动事项、归档、来源、审阅、清单读取都适用。拒绝符号链接必须进入扫描不完整状态，不能又被静默 skip。若支持真实外部导入，使用显式导入流程复制快照，不能通过 symlink 隐式信任。

避免夸大：路径防护用于防止意外/受模型影响的越界操作；不宣称这些 Python 脚本能对抗拥有同一 OS 用户任意执行权的攻击者。

<a id="rc-19"></a>

### RC-19：案件初始化及增量更新的事务边界错误【R-hist+S；P0-law/P1】

**实施追踪：**P-L1，增量 writer 由 P-L2 配合；验收 T31、T35、T40。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据 A。** bootstrap 在加锁前检查目录是否存在，锁内没有重查，写 helper 使用 `os.replace`。前轮报告中的两个进程受控交错复现记录为：两者均 created，后者覆盖前者。[LBOOT] [LCOMMON]

**证据 B。** `sync_run_manifest.py` 在获取 `.writer.lock` 之前读 document-index/issue-tree/manifest、计算 revision，锁内写回；因此仍有读改写丢更新窗口。与 bootstrap 的 `.matter-store.lock` 还是不同作用域。[LSYNC]

**统一修法。**

1. 在同一个受控写边界内做读取最新状态、前提检查、修改和提交。计算较重时允许锁外准备，但提交时必须校验基准 revision/hash，冲突则重读，不覆盖。
2. create-only 与 update 是不同操作；初始化在锁内检查并独占创建。使用暂存目录/完成标记，在完成全部最小文件并校验后公布为可用事项。进程崩溃留下 pending 状态，不能自动当 active。
3. 跨文件更新使用小型提交记录或提交清单最后落盘，读取方校验一致 revision；先复用 JSON 文件和现有 helper，不建设自研数据库。对当前大小的本地工作台可先选择一个正确的写锁；只有压测证明必要再做 per-matter 并发。
4. 归档/客户变更/利冲索引和 run 更新必须约定锁作用域与固定获取顺序，避免一个操作认为安全而另一个同时移动目录。利冲通过记录绑定覆盖范围与相关资料 generation，后续资料变化不能无限保留原通过状态。

**验收。** 同 ID 并发只允许一次创建；更新竞争明确冲突；任意写入阶段崩溃后，不出现半旧半新被当完整；原已创建事项所有字节不被失败竞争者改变。

<a id="rc-20"></a>

### RC-20：锁崩溃恢复和重复客户噪声【R-hist；P1】

**实施追踪：**P-L1；验收 T31–32。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**锁证据。** 原 helper 通过 O_EXCL 创建锁文件，正常 finally 删除。前轮以 `os._exit` 模拟异常结束，锁残留，后续 CLI 返回 locked。[LCOMMON]

**修法。** 优先评估项目支持平台已有的 OS advisory lock 或成熟可复用锁机制，使进程终止释放锁；若继续文件锁，写入主机/进程启动身份与运行实例，提供受控检查/修复流程。不能单凭文件年龄删除活锁，不实现复杂分布式租约。

**重复客户证据。** 同一客户第二个事项、不同对手方仍仅凭名称重复触发待复核，前轮记录已复现，本版未重跑。[LBOOT]

**修法。** 先做实体候选匹配，再记录命中双方角色、事项和关系。区分同向历史客户、潜在对立关系、同名不确定与关联主体；不把名称命中等同最终冲突，也不把所有同向客户一律视为已获授权。专业规则由明确 policy 和律师决定，不由模型自行清除 hit。

<a id="rc-21"></a>

### RC-21：“已核验来源”谓词过宽及跨事项关联【S/历史局部谓词；P0-law】

**实施追踪：**P-L2-a 先独立提交；验收 T33–34、T37。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**实际代码。** `validate_run.py` 对 `[已核验-来源]` 的依据要求 sourceType 为 official-law/guidance/case，并且 `status != source-needs-check`。schema 允许 unknown、superseded、unreviewed。排除一个状态并不构成验证。[LVALIDATE] [LSOURCE]

```python
source_type in {"official-law", "official-guidance", "case"} \
    and status != "source-needs-check"
```

**来源合同。** 分开来源获取/核验、法源有效性与本事项适用时间、律师审阅状态。unknown 不得成为已核验依据；unreviewed 不必然代表未抓取；superseded 也可能与历史事实相关，必须结合 effective interval、地域与事项时点说明，不能一律删除历史法律。

**最小修法。** 第一批先收紧当前谓词并新增反例测试；旧记录保持可读但缺证据时降为待核。随后由实际来源获取/授权导入动作生成 ID、正文哈希、获取时间、定位与摘录；模型可以填写研究解释，但不能仅改状态字段就伪造工具获取的记录。来源真实获取也不等于结论正确，重要主张仍需引文支持和适用性复核。

**扩大检查。** 校验器在已读区间主要检验 runId 和引用存在性，不能据此保证每个来源/文件的 matterId 都等于当前事项；allowedUsers 非空也不证明当前调用者在里面。补所有相关文档的 matterId/runId 一致性、路径所属、来源与证据身份、跨事项显式导入 provenance，以及当前用户在受控入口的权限检查。[LVALIDATE]

既有审计没有完整构造跨事项材料让全 CLI validator 通过；这里作为必须补齐的合同测试，不声称已经发生资料越权。

<a id="rc-22"></a>

### RC-22：增量失效丢失旧待办，审批未绑定当前字节【R-hist+S；P0-law/P1】

**实施追踪：**P-L2 的增量/审阅子项；验收 T35–36、T40、T44。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**固定源码。** sync 只比较文档哈希，只以该次执行的 changedDocumentIds 生成 stale 集；再把 `manifest.staleIssueIds` 整体覆盖。没有监控 sources.jsonl 的变化，也没有在该路径撤销原 externalRelease/reviewState。[LSYNC]

**原脚本隔离结果。** 第一次改文档后，staleIssueIds 含 issue-test；没有重分析，再次 `--apply` 返回 unchanged、staleIssueIds 变空，但 issue.status 和 manifest.status 仍为 stale。原 `externalRelease=approved`、`reviewState=lawyer-reviewed` 在改文档后仍保留。只改来源文件，该同步入口也返回 unchanged。第 12 节列出精确范围。

**不能夸大的地方。** manifest.status 仍为 stale，原 strict validator 有阻断，因此该记录不证明已绕过最终校验或真实外发；确认的是状态与审批字段可能不一致。

**修法。** stale 集合由“既有未完成原因 ∪ 新影响项”构成，只能由明确完成的重分析移除。扩展现有 run 依赖到被实际引用的来源记录、关键事实/证据及产物版本；不做全仓通用图引擎。父子争点与实际依赖不是完全相同，使用显式 depends-on；子结论变化影响上层汇总时按依赖传播，并对循环/缺失 ID 拒绝或报告。

**审批绑定。** 把历史审阅决定保留为不覆盖的历史记录（本地文件不因此获得对抗同 OS 用户的防篡改保证），单独计算其对当前 revision/digest 是否仍有效。新材料、来源变化、正文重写、模板/产物变化使当前 release capability 失效；不能仅保留 approved 字符串。送审/正式导出/对外释放入口都先检查最新 generation 与依赖哈希；未批准草稿导出只反映当前失效状态，不冒充正式通过，不能只依赖上一次 sync。

**核验与清单。** 文档哈希更新时，不静默更改用户来源记录来掩盖变化；变更后的快照、引用与 read coverage 需要重新建立。再次同步应幂等，不因无变化而清空待办或制造无意义 revision。

<a id="rc-23"></a>

### RC-23：工作台体验、真实专业输出与可信完成边界【S；P1/P2】

**实施追踪：**P-L2，实际宿主/Office 消费者配合；验收 T34、T36–38、T44–45、T49。证据与影响范围以下文为准，具体签收角色见第 3.3 节。

**证据。** 法律共 87 技能、5 个代理；合同 Skill 在阅读正文前要求 Matter Gate。PRACTICE 的仓库 lint 保证引用存在，不等于每次运行均经过可信授权。benchmark 明确附件未打开、Matter/联网操作为零，不能作为真实法律正确率。[PLAW] [LCONTRACT] [LPRACTICE] [LBENCH]

**路径调整。**

| 路径 | 允许输出 | 必须保留的边界 |
|---|---|---|
| 任务接入/法律信息/材料初筛 | 材料清点、解释、初步风险与缺失信息 | 明确辖区、时间、来源和不确定性，不伪造正式利冲通过 |
| 受治理内部草稿 | 条款定位、风险、修改建议、争议分析、来源与复核项 | 真实事项、范围、权限、资料完整性、可追溯引用 |
| 正式专业复核/对外交付 | 经真实复核的指定产物 | 律师决定、版本绑定、用户确认、授权目标；不自动发送/提交 |

复用已有客户和 Matter 信息，除有变化外不反复提问；简单合同不必须启动全部代理。深度分析保留双输入链，但每个 agent 只收到任务必要材料；来源检索优先脱敏，不把客户完整案卷直接发给搜索服务。

**可信完成。** 给现有工作台增加小型 finalize/送审校验边界，复用校验脚本而非创建新的法律 MCP。模型和通用文件写工具不能仅靠写入 `approved` 取得产品级外发许可。可编辑本地案件 JSON 是工作记录，不是身份/签名事实；正式审阅回执由可信 UI/授权服务生成并绑定 digest。本轮先限定内部草稿，无法建立强可信复核时不开放正式外发。

**数据流与保留。** “本地 MCP”不等于材料不会发送给远程模型。任务开始时确定材料将流向本地 store、模型服务、搜索/MCP 服务、诊断日志、临时预览和办公转换中的哪些对象；敏感内容仅按最小必要范围发送。为缓存、日志、临时文件、导出物及备份标清保留/清理责任，不默认长期保存全文，不声称更换传输就满足法律要求。归档扫描需有权限：无权读取的范围返回覆盖不足或经授权的冲突摘要，不能为“全面扫描”破坏案件隔离。

**Office 链。** 开始任务即检查可选办公能力；缺少时交付完整 Markdown 并注明格式限制。已存在的 Office 路由与降级不删除，也不另造文档引擎。[LCONTRACT]

**专业评测。** 真实读取合同、证据定位、条款替换、金额/日期、反方论据、全国/地方规则、旧法适用、事实争议、扫描缺页与恶意附件分开评分。流程文本测试重命名，不再用其 100% 展示实务能力。工程通过和律师专业复核是两道不同门。

### 9.1 数据修复不能顺手扩大授权或丢失审计事实

修损坏记录时先报告、备份并让具备权限的人处理；不自动“补齐”客户名称、律师、利冲通过或法源。扫描归档是覆盖修复，不是对所有案卷授读取权。若操作者只能访问部分范围，返回覆盖不足或由被授权的冲突检查主体给出最小摘要；不能为了完整性读取隔离案件全文。

记录真实获取、内容一致、法源适用、引文支持和律师复核是不同判断。收紧旧谓词的首个 PR 可独立完成；无证据的记录先待核，不以 unreviewed/superseded 任意一个枚举就自动断定全部有效或全部无效。历史事实适用旧法时记录事项时点和理由；重要结论逐一关联支持它的来源/事实，不因整个 run 中出现一条“官方来源”就全部通过。

同一工作区的通用文件写权限不能被当成专业审批权。内部草稿保留可编辑性；产品正式外发凭受信决定和当前产物绑定验证。拥有同一 OS 用户任意代码权限的操作者、独立外部程序和用户自行复制文件不在本地脚本的强防篡改承诺内；本产品自己的外发入口不能绕开限制。

### 9.2 最小写边界与扩展停止条件

所有被改动的 writer 使用同一正确的读—检查—提交边界，reader 使用匹配锁或完整快照校验。单文件 replace 不等于跨文件事务；完成标记必须在必要文件写入并校验后发布。中断可能留下 pending，读取方应拒绝当作完整，恢复步骤不得覆盖已有完整 Matter。

先修必要 helper 与调用方，不把每个报告生成动作改成全库事务。若为实现文件更新开始加入通用 WAL、复杂恢复器或多进程分布式租约，应停止扩展并评估成熟事务存储；“当前不迁数据库”不是禁止使用更简单的成熟方案。旧 writer 与新 writer 并存必须按第 11 节隔离，否则新锁无法保护旧脚本。

增量追踪以本 run 实际依赖为界。仅某条来源或相关事实变化时使其使用方失效，不因无关记录追加而全库重分析；无变化同步不得清空未解决 stale 原因，也不应无意义增加修订。父子树只是组织关系，影响传播按明确依赖处理，防止缺失引用或循环被静默忽略。

### 10.3 每个 PR 必须写明的事实

实现者、验收者和发布/回滚负责人签收实际结果。不能只写“所有门禁通过”“完成度 100%”；历史报告、模型回答中的测试描述和本文件的预期输出都不是候选代码的 PASS 证据。

### 10.4 已识别关联链的变更约束

涉及共享 SDK 或协议结构时，先查真实 import/生成/发布消费者，再决定扩大测试范围；没有消费者证据不扩仓。涉及额度、计费、搜索来源授权、消息渠道或正式外发时，沿既有业务检查处理，不自建旁路。接口合同存在增量变化时，先兼容增加再迁移调用者，删除旧形态须有退出条件与实际无依赖证据。

## 11. 安装、数据迁移、兼容和回滚

### 11.1 插件与宿主升级

**安装事实。** 记录市场来源、插件版本、提交/发行物 digest、宿主 build、协议/能力版本；以实际安装缓存为准，不仅看 GitHub main。更新包原子切换，保留用户数据与显式禁用决定。

**权限继承。** 同名不代表同权限：来源仓库/市场、endpoint、command、产物或请求能力发生敏感变化时重新授权；普通版本号变更不强迫无关重复确认。未经支持的新 profile 在旧宿主上不能变成可执行 fallback。

**恢复门。** 新宿主先发布；媒体新配置随后发布。全部目标平台从干净环境安装、离线启动、缺依赖、路径含空格/中文、权限不足做测试。宣称支持 macOS/Windows/Linux 需各自的发行物证据；未测试平台应明确暂不支持此恢复能力。

### 11.2 法律旧数据

升级前对实际 store 做备份/快照并记录 schema 版本和摘要。先以只读报告列出损坏文件、未知布局、跨事项 ID、旧来源缺字段、半初始化目录、过期锁与原审批记录，不自动修正事实、不补造律师或来源。

新增字段加法迁移；旧来源继续可阅读，但“当前已核验/已审阅/允许释放”由新规则计算，缺证据就待核。历史 no-hit 和 reviewed 不自动升级为新保证等级。归档可只读参与候选匹配，敏感信息仅向有权限主体显示；无权限区域不能假装已扫描。

回滚代码不得把新版本写入的数据交给旧版本误读为通过。**旧二进制不会自动遵守新加的“只读”字段**，因此“旧版本只读”必须有受支持启动器/版本隔离/明确 store 路径隔离的实际证据。做不到时禁止自动降级到旧 writer，提供前向修复或在停写后恢复兼容快照，并核对恢复点之后的新数据。不能只删新字段恢复可写，不能声称可强制控制离线旧客户端或同一 OS 用户手工运行脚本。

### 11.3 云端迁移

先增加调用者/执行状态等字段，再切流量。仅对已确认的第一方聚合连接迁移；非匹配旧 connector 保留不可执行诊断及旧值，不跨服务套用凭据。认证故障回滚时关闭新能力，不以放宽校验兜底。

兼容旧接口必须有退出条件和已有流量证据；没有旧真实使用者，不建设永久兼容层。别名不应自动 HTTP 重定向携带授权到另一 origin。

### 11.4 最小回滚边界

| 失败对象 | 回滚/止损 | 不可做 |
|---|---|---|
| 新媒体恢复包 | 关闭该 profile 执行资格，停止该能力的受影响新写入/外发，保留稿件和历史 | 恢复旧不安全启动配置、删除用户稿件 |
| source 结果/协议改动 | 能力开关降级；保留错误与原始记录；必要时只读 | 将结果未知改成成功、吞掉取消 |
| 法律迁移 | 停止新写入，展示修复报告；按兼容快照或前向修复 | 旧 validator 自动认可新 reviewed 状态 |
| 云资源授权 | 关闭聚合接入/限制灰度用户；修正发行/资源合同 | 禁用 audience/scope 或回退裸跑 |
| 沙箱执行 | 禁止新任务；查询既有任务实际终态 | 认为前端取消就一定无副作用 |

### 11.5 CI 与发布策略

原审计所读插件发布策略仅允许手动 workflow_dispatch。保留该策略，先把新回归接入现有脚本与手动工作流；启用自动 CI 或修改分支保护需另行授权。本文不触发任何 workflow。[PPR21]

“自动 CI 未运行”不等于“没有测试义务”。每个候选必须有按提交固定的执行证据；没有执行的测试如实标为未验证。配套 build/dist、manifest/package/marketplace 版本和已有 SBOM 按现有规则同步，不能仅改源码未更新分发物。[PCONTRACT] [PPACKAGE]

### 11.6 回滚必须可执行，而不只是状态字段

先区分三类回滚：功能开关停用、代码版本回退、数据恢复。关开关可阻止新操作，但不保证取消已在执行的任务；降级代码不意味着能安全读取新版数据；恢复快照也会影响恢复点后的写入。相应负责人在候选测试中至少演练一次适用动作，说明何种状态只能前向修复。

旧宿主兼容只对实际支持列表作保证，不声称能远程约束全部离线旧客户端或同 OS 用户手工启动脚本。凭据/数据路径迁移前确认作用域，迁移失败保留原值和诊断，不用“清空配置重新来”毁掉用户资料。历史批准不可被迁移程序凭推断升级；旧版“只读”限制没有可执行机制时，禁止自动启用旧 writer。

### 11.7 分发供应链与无副作用启动

从最终安装物而不是开发仓工作目录验收：入口存在、运行时匹配、相对/规范路径、依赖锁、发行物与源代码对应、stderr/stdout 分流、离线初始化和退出。若 QA 有额外二进制或浏览器依赖，明确按需安装与用户许可，不在“列举插件”时隐式下载或联网。

暂停基线变更必须是逐项准入，而不是删除整个校验器。更新、卸载、重装需保留或明确处理用户数据、主体授权和显式禁用；同名新来源不自动继承旧连接凭据。测试恢复和回滚都保持这些边界。

### 13.2 三层验收不能互相替代

**确定性合同：**字段、状态、Schema、权限、并发、错误、迁移，用 mock 作故障注入，但真实 producer/consumer 边界必须至少跨过实际类型和代码路径。

**最终安装链：**实际发布候选、真实宿主/worker/stdio 或受限云测试服务，完成一次获授权业务操作与回读并核对文件；只读能力用真实读取证据，不为验收无意义写生产数据。ping、目录和启动不等于交付。

**领域质量：**同模型与设置、有无 Skill 对照、代表任务重复运行，记录实际完成率、核验范围、交互、耗时与 token。文章和合同分别评分；法规适用、推理和行动建议由相应专业人员复核。字符数不冒充 token，schema 不证明专业正确。

### 13.3 支持表与分能力开放门

发布负责人在已有 PR/发布记录中维护一张小表，而不是新服务：

```text
能力与保证等级 | 实际调用入口 | 宿主build | 插件version/digest | 网关版本(如需)
OS/架构/运行时 | MCP协议/SDK | provider/API/执行者 | 适用测试及结果
已知限制 | 实现者 | 验收者 | 发布/回滚负责人
```

| 开放对象 | 必须通过 | 不作为无关前置 |
|---|---|---|
| 状态页与已有草稿入口 | 相关权限/元数据投影正确，无虚构执行；涉及数据旧问题不被放宽 | 云聚合、全部热点、团队批准 |
| 第一方媒体本地编辑/预览 | 实际经过的宿主结果与权限边界、RC-01/13/14/24；网络打开时 RC-16；实际 HTML/Markdown 交付 | 全套团队审批、全平台自动发布、未使用的 hosted API |
| 法律初筛/内部事项草稿 | 明确输出上限；受治理事项适用 RC-17–23、当前源/输入/审批失效正确、实际材料定位和交付 | 云聚合；不将简单信息解释强制套为正式案卷流程 |
| 云聚合真实调用 | RC-07–12 的适用授权/协议/目录/执行/任务合同和对应宿主返回链 | 本地媒体品牌风格、全部法律技能 |
| 正式多人审核或业务外发 | 有真实需求才单列；有效真人决定、政策与产物绑定、目标授权及回执全部验收 | 本轮不默认开放；不能以草稿成功代替 |
| 新协议或额外 OS/厂商路线 | 该组合的独立合同与最终安装链证据 | 不拖住已有组合的小修 |

适用负例测试出现假成功、越权或并发覆盖即不能开放该能力；有限测试通过不证明风险为零。最小媒体/合同任务在每个本批承诺环境连续完成三次作为最低回归门，不据此宣称可靠性百分比。性能预算先采基线，不预填虚假的延迟与成本承诺。

### 13.4 现场最小取证与故障定位

仅采集：实际宿主 build、已安装插件来源/version/digest、配置 scope/cwd 的脱敏标识、逻辑与运行态工具名、transport、协议/SDK/API、发布/激活/依赖状态、主体保证等级、最后成功阶段、标准/业务错误码、必要 requestId/operationId、产物摘要和观测时间。不得默认上传 token/cookie、完整稿件或案卷；错误文本也可能带秘密，按结构脱敏。

```text
市场/Skill 可见？
→ 实际安装物是否包含该能力且允许该宿主消费？
→ 当前激活/权限/依赖是否通过？
→ 按支持版本完成初始化或发现，真实目录是否有工具？
→ 调用有没有发出，由谁授权、谁负责执行？
→ 实际执行结果/状态/文件是否可核对？
→ 是否在worker/Rust/GUI/模型适配途中改变形态或错误？
→ 是否只是合法待复核，而不是连接失败？
→ 只有相应远程跳失败，才关联云资源或模型网关日志。
```

没有实际使用者与 trace 的条目仍是固定源码缺陷或设计风险，不将其写成用户线上故障唯一归因。

## 14. 过度工程约束与关闭标准

### 14.1 明确不建设的系统

本轮不新建通用连接器注册中心、第二授权平台、分布式租约总线、全领域工作流引擎、自研任务队列、影子 MCP 客户端、通用法律数据库、大规模热点爬取系统或办公渲染引擎；不以全面 2026 协议升级作为所有修复前提。

这些约束只适用于本轮恢复范围。若实际合规/安全要求或复杂度证据证明需要更成熟基础设施，应明确资产、威胁、真实消费者与验收，再另立受控范围，不能在未实施时计入当前保证。

### 14.2 每项设计的停止条件

| 易扩张项 | 本轮最低实现 | 应停止并重新评估的信号 |
|---|---|---|
| 能力可用状态 | 复用 inventory/lifecycle，加必要发布依赖和投影 | 开始另造控制数据库或同步总线 |
| 旧宿主隔离 | 验证既有准入；必要时薄描述转换到既有启动链 | 出现第二 loader/连接池/权限系统或私有 MCP wire |
| 法律文件可靠性 | 正确锁、create-only、快照/完成校验、受控恢复 | 提交协议变成复杂 WAL/自研数据库；此时评估成熟事务存储 |
| 原始结果修复 | 修真实错误 producer 和边界转换 | 为了错误返回去放宽正确 Rust schema，或重写全部工具 |
| 幂等与取消 | 第一方副作用路径、现有任务系统与真实信号 | 所有只读操作均需事务ID，或承诺第三方 exactly-once |
| 人类审阅 | 草稿低保证；正式能力按需用既有可信决定入口 | 普通写稿也要求机构 PKI/多人账号体系 |
| 厂商/OS兼容 | 冻结实际本批支持列表 | 没有消费者仍要求全模型×全协议×全OS排列组合 |
| 测试与计量 | 复用脚本、固定fixture、受控手动工作流 | 为验证几个bug先建平台，或未经批准改变自动CI策略 |

轻量化应减少重复状态、冗余中间文件和无收益的重写，不删掉路径安全、当前授权、来源追溯或真实失败。共享 Schema、helper 或小 fixture 只有在至少两个实际消费者确实需要时才抽取；不为了名字“统一”做通用框架。

### 14.3 实施关闭条件

**宿主：**实际被使用的主代理、子代理、直接 RPC、GUI/CLI 路径保持一致授权与结果语义；原始结构不被模型投影破坏，错误、拒绝和结果未知不显示成功。未使用入口明确标识，不冒充全链测试。

**媒体：**支持版本从最终发行物启动受控本地服务，完成保存/读取、修订并交付可打开的 HTML/Markdown；QA 等级、身份保证与未批准状态真实；旧宿主不会意外执行恢复配置。

**法律：**损坏、类型、覆盖、归档、路径、并发、来源与增量反例通过；声明读取范围内的真实材料支持风险和建议；历史批准不自动适用于新字节，初筛/草稿不冒充正式意见。

**云端：**自有资源授权、实际端点与支持版本相符；工具有真实结果和机器可读失败；任务、配额/计费和回查归属于正确授权主体，取消与重试不隐瞒副作用。

**所有关联方：**每项恢复能力都填实第 3.3 节责任链和第 13.3 节支持表。未验证消费者、旧版本、协议或模型组合不计入兼容声明。发布说明具体列出恢复内容、仍暂停项和已知限制，而不是“全部 MCP 恢复”。

### 14.4 最终执行口径

原审计和前轮实验提供修复依据；本版提供统一实施合同；候选代码的实际测试和责任人签收才提供开放依据。三者不能互相替代。完成一个限定能力即可合并并按其保证发布，不因后续扩展未完成而否定已修的小范围成果；也不能用小范围成果提前批准未实现的完整治理。
