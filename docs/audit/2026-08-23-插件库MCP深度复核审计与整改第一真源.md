## 2. 必修缺陷

### `P1-MCP-01` hard gate 未覆盖宿主真实 MCP 加载面

当前 validator/test 只枚举 `plugins/*/.mcp.json`。宿主实际还支持：

- repository-root plugin `.mcp.json`；
- manifest inline `mcpServers`；
- manifest 指向的外部 JSON；
- MCPB 本地路径和 URL；
- marketplace source 指向的任意层级 plugin root。

隔离复现已证明 root `.mcp.json` 与 manifest inline HTTP server 均可令 `validateMcpContract()` 返回 `[]`。

固定修复：validator 必须从 marketplace source + root manifest 构造真实 published plugin roots，拒绝所有 manifest `mcpServers`/MCPB，并全仓递归枚举 `.mcp.json`；唯一允许路径只能是 `plugins/crabcode-html-video/.mcp.json`。

### `P1-MCP-02` 唯一允许配置没有精确锁定

当前规则只检查 server 名、粗 transport 和部分危险字符串。把 html-video 改成 `command=curl,args=[https://…]` 仍可通过。

固定修复：对允许配置做 canonical JSON exact match，逐字段锁定 command、args、env、零额外字段；同时验证 `dist/bootstrap.js`、`dist/server.js` 是普通文件且 realpath 位于 plugin root。

### `P1-MCP-03` 仓库仍分发被禁止的 MCP 脚手架和指导

`templates/plugin-mcp-wrapper/.mcp.json` 仍使用 `npx -y @vendor/server-binary@latest`，并被完整打入镜像 ZIP。plugin-customizer / plugin-dev 仍教用户写远程/SSE/浮动 `.mcp.json`。

固定修复：删除可执行模板配置；模板、示例和技能在 containment 期间只能输出 non-executable proposal/inventory，不能生成 `.mcp.json` 或宣称可连接。

### `P1-UPGRADE-01` 升级不驱逐当前进程，必须重启宿主

宿主更新只切 registry 到新 generation，旧路径标记 orphan；旧目录至少保留 7 天，zip-cache 模式跳过清理。update 返回 `Restart to apply changes.`，UI cache clear 不清 MCP client/process。

关联方复核进一步确认：ManagePlugins/ManageMarketplaces 更新后只调用 `clearAllCaches()`，UI 却提示 `/reload-plugins`；该命令不清冻结的 `inMemoryInstalledPlugins`，不能可靠切换到新 installPath。CLI update 因进程自然退出规避，长驻 GUI 不行。因此 targeted eviction 修复前，`/reload-plugins` 不是本事故的合格止血操作，只能要求完整重启。

固定修复边界：

1. 插件仓所有暂停说明与发布说明必须写“升级插件并重启 CrabCode”；
2. 在 CrabCode host 完成 targeted MCP eviction 前，不得宣称热更新即止血；
3. 增加真实 Git old/safe bytes 的双进程 fixture：进程 A 证明更新后冻结快照仍旧，进程 B 证明重启后读取新 registry 且 active runtime remote=0；当前已发布 generation 1 必须通过，尚未发布的 generation 2 只作为未来 remote 解锁阻断项，不得伪写已跑；
4. orphan cache 中旧字节存在不计为 active runtime，但必须在证据中如实记录。

### `P1-CI-01` workflow trigger 文本解析可被合法 YAML 绕过

合法 YAML：

```yaml
on:
  workflow_dispatch: {}
  "push": {}
```

当前 validator 返回 `[]`，actionlint 也通过。

固定修复：仓内策略采用严格 canonical `on` block。普通 workflow 的唯一非注释子项必须逐字符为 `workflow_dispatch: {}`；publish workflow 因 `P1-REL-01` 必须接收发布证据，只允许无 quoted key、anchor、merge key的 canonical `workflow_dispatch:`，且其唯一子树为机器校验过的 required `ci_run_id` 与 `expected_sha` inputs。任何额外输入、额外事件、`.yaml` 漏扫或第二种等价 YAML 写法都 hard fail。actionlint 同时扫描 `.yml` 与 `.yaml`。

### `P1-CI-02` 声明的 Python 3.9 cell 依赖不可解析

`pdfplumber==0.11.9` 固定依赖 `pdfminer.six==20251230`，后者要求 Python ≥3.10；因此 CI 声明的 Python 3.9 cell 在测试前必然安装失败。固定修复：保留脚本的 Python 3.9 支持门，3.9 测试 cell 锁定兼容的 `pdfplumber==0.11.7`，3.13 cell 继续 `0.11.9`，其余 reportlab/pypdf 版本一致；两个 cell 都必须实际执行强 PDF 测试，不得用未安装依赖的弱校验冒充。

### `P1-CI-03` media-ops Chromium 单值合同误拒绝固定 Linux 镜像

Playwright 1.61.1 的 metadata 锁 Chromium revision 1228/browserVersion `149.0.7827.55`，但固定摘要 Linux 镜像内 Chromium、headless shell 与 `browser.version()` 均真实报告 `149.0.7827.0`；跨平台硬编码 `.55` 使 Linux `test:qa/qa:release` 必红。固定修复：继续锁 Playwright/lockfile/镜像 digest/revision，同时按平台精确映射 darwin=`149.0.7827.55`、linux=`149.0.7827.0`；未知平台和任一错误 patch 均 fail-close，不用前缀或 major-only 放宽。

### `P1-REL-01` 发布前置门没有绑定测试树和批准证据

publisher 只检查 official repo/main 和 marketplace 非空；不校验 CI run、tested tree、证据摘要或批准主体。post-publish 的 notify 不能阻止错误字节先切 `latest`。

固定修复：publish workflow 必须接收并验证成功的 `ci_run_id`，要求：workflow=`ci.yml`、event=`workflow_dispatch`、branch=`main`、conclusion=`success`、head SHA=`github.sha`。发布前再验证当前远端 main 与 `github.sha` 一致。

### `P1-REL-02` 历史发布可重跑并回滚 latest

历史成功 publish run 在 GitHub 重跑窗口内，旧 workflow 可继续读取 repository-level mirror secrets，并用原 `GITHUB_SHA/GITHUB_REF` 切回旧 pointer。

固定修复：在发布 safe mirror 前必须完成下列至少一项不可绕过控制并留证：

- 迁移/轮换 repo-level mirror key 到 protected Environment，旧 key 失效；或
- 删除/禁用危险旧 run 的重跑能力并保留外部审计索引；或
- 由服务器端 forced command/高水位拒绝非快进 pointer。

只改当前 workflow 不能约束历史 run，不得假装已修复。

已完成的 defense-in-depth 不是最终闭环：历史 workflow ID `336369746` 已于 `2026-08-23T03:52:51-07:00` 通过 API 置为 `disabled_manually`；旧路径保留只会失败的 tombstone，加固 publisher 使用新路径/新 workflow ID（新 ID 只有默认分支合并后才注册，合并前状态为 awaiting）。safe publisher 与 mirror auditor 都在运行时核对旧 ID/path/state，并要求 safe path 是 `active` 且 ID 不同。

但旧/新 workflow 仍读取同一组 repo-level `MIRROR_*` secrets；具 Actions write 权限者可 enable→rerun→disable，已 queued/in_progress 的旧 attempt 不因 metadata 恢复 disabled 就被该瞬时检查证明取消。受控 rerun 负测因会真实调用旧凭据而被安全审批拒绝，故不得把它写成通过。`P1-REL-02` 继续阻断 safe publisher，直到管理员明确完成并留证下列之一：删除三条旧 run；迁移/轮换旧 repo key 到仅新 safe workflow 可达的 protected Environment/新 secret name 并令旧 key 失效；或服务器 high-water/CAS 拒绝旧 SHA。禁用状态、distinct ID 与 no-active-run 只能作为附加门，不能替代不可绕过控制。

### `P1-REL-03` content-addressed ZIP 不确定且可覆盖

普通 `zip -ry` 纳入 checkout mtime；同 SHA 重跑可能产生不同 ZIP，却覆盖一年 `immutable` 的同名对象。

固定修复：使用 commit-object 驱动的确定性 archive（固定顺序、时间、权限），相同 SHA 构建两次必须字节一致；若公网同 SHA 对象已存在，必须下载比对，字节不一致时拒绝覆盖。

### `P1-REL-04` mirror auditor 混用历史 push CI

notify 查询所有事件，当前没有成功的 manual CI；其“最新绿灯”实际可落到旧 push commit。若 pointer 回到该旧 commit，审计可错误判 exact green。

固定修复：只接受 `event=workflow_dispatch`；没有 exact successful manual CI 时 fail-close。删除已经无 schedule 的 grace/SLO 死分支。

### `P1-REL-05` mutable marketplace projection 先于 runtime pointer，伪称跨文件原子

旧发布顺序先改写全局 `marketplace.json`/checksum，隔一轮网络与 main 复核后才切 `latest`。若 main 在中途前进，workflow 会退出但新 marketplace 已留下，形成“网站声称安全、generation-1 仍从旧 latest 取得危险 ZIP”。纯 rrsync/static-file 合同只有逐文件 rename，不提供跨 `latest`/marketplace 的 transaction；`--delay-updates` 也不是 CAS 或多文件原子提交。

固定修复：先上传并从公网逐字节读回 immutable `<sha>.zip` + ZIP checksum；重验 main 与旧 pointer 后，只切换 `latest` 这一 active-runtime 线性化点；成功后再更新 Acosmi 网站使用的 non-authoritative marketplace projection + checksum。projection 不一致时 workflow/全系统审计仍 fail-close，但最坏状态只能是“runtime 已安全、网站仍旧”。严格跨消费者原子性留给服务器端 generation/CAS transaction，或由网站同批改为 `latest → <sha>.marketplace.json`；当前不得伪称已有多文件事务。

### `P1-AUTH-01` 未来 authPolicy v2 缺 MCP 2026-07-28 必需控制

远程解锁方案必须补齐：

- RFC 9207 `iss` 精确验证及缺失/mismatch 负测；
- RFC 8707 `resource` 同时进入 authorization/token 请求；
- authorization metadata 必须存在 `code_challenge_methods_supported=S256`；
- issuer-bound credential 与 step-up scope 的 wire 测试。

该项不阻断 emergency mirror 发布，但阻断任何 remote profile 解锁。

### `P1-AUTH-02` portless loopback 只能是条件性 provider 策略

OS 临时端口符合 RFC 8252；但 CIMD redirect 校验仍需真实 AS 正确应用 loopback port exception。六字段 JSON 不是第三方普适兼容保证，且 localhost-only CIMD 存在本地应用冒充风险。

固定修复：保留 portless 策略为候选默认；Notion/Linear/Canva/Synapse 分别 E2E；同意页显示 redirect hostname/风险提示；必要时 provider profile 使用经证明的 fixed redirect。`application_type=native` 是否进入 CIMD 作为 provider/OIDC 兼容项验证，不在无 E2E 时擅自改 Acosmi 已合入合同。

### `P1-PLAN-01` P0-0A 解耦仍矛盾并形成 genesis 循环

文档一处称 P0-0A 不阻断 A/B，另一处仍把 backend stores、四 environments、OIDC 归入 P0-0A；又要求先有签名 lock 验 public artifacts，同时要求 P0-0A 通过后才生成 genesis。

固定拆分：

```text
ACOSMI-REL-BASE
  backend stores + four environments + OIDC + fixture
  只阻断 Acosmi A/B

P0-0A-BOOTSTRAP
  key/WORM/DR/bootstrap canary
  只阻断未来 trust path

GENESIS-INTEGRATION
  safe artifacts + bootstrap 均通过后生成首份 lock
```

### `P1-PLAN-02` 方案依赖不存在的 marketplace pointer

文档使用 `/crabcode/marketplace/current.json`，公网为 404；generation 1 真实消费 `/crabcode/plugins/crabcode-plugins-official/latest`。
